## 1. 位置づけ — 非目標をひとつ撤回する

このフェーズは4つの追加を含むが、独立した寄せ集めではない。1本の因果で繋がっている。

```
水を置く（湖・川）
  → 通れない場所ができる → 地図が割れうる → 連結性を生成が保証する必要がある
  → 水そのものは何も産まない → 水辺にだけ生える植物（薬草）が水に意味を与える
  → 薬草に使い道が要る → 病気と治療
  → 治療の速さを決めるものが要る → 既存のスキル機構（JobType が1つ増えるとスキルも1つ増える）
```

### 1.1 撤回するもの

[design-next.md](design-next.md) 6 章は「医療・部位・病気」を**明示的に非目標**として挙げてきた。
理由は [design-phase2.5-animals.md](design-phase2.5-animals.md) 1 章が損傷のモデルを `health` 1つに
固定したことにあり、捕食者を入れるための逸脱をこれ以上広げない、という判断だった。

**このフェーズはその判断を撤回する。** ただし撤回するのは「病気という層を持たない」ことだけで、
**`health` 1つに固定するという規律そのものは維持する** —— 部位も、傷の種類も、感染も入れない。
病気は「`health` を継続的に削り、放っておけば既存の死亡経路で死ぬ状態」であり、
それ以上の解像度を持たない。撤回の理由と、実装後に測った値は [design-notes.md](design-notes.md) に残す。

### 1.2 将来に向けて開けておくもの、開けないもの

要望には「将来的には水生生物、漁業ができるようにする」とある。このフェーズでは**どちらも作らない**が、
水を2種（浅瀬・深水）に分けておくことで、漁場を「深水に隣接する浅瀬」として後から足せる形にしておく。
逆に、**水を1種にして「深さ」を `Tile` の新しい数値フィールドにする案は採らない**（2.1）。

## 2. 水 — 深さは新しいフィールドではなく地形2種で表す

### 2.1 なぜ `Tile.depth` を作らないか

要望は「深さ要素も取り入れて、深さに応じて通行不可や農場不可にする」。素直に読むと
`Tile.depth: number` を足したくなるが、採らない。理由は3つある。

1. **実際に必要な区別は2段階しかない。** 「歩けて建てられない浅瀬」と「歩けない深水」。
   連続値を足しても、それを読む側は結局2つの閾値に潰す。
2. **`walkable` の書き込み経路が既にある。** `makeTile`（`worldgen.ts:74`）が
   `walkable: !isRock(terrain)` を書いており、地形から通行可否が決まる形は全地形で一貫している。
   深さを別フィールドにすると、通行可否が「地形」と「深さ」の2つから決まることになり、
   `walkable` を書き換える既存の6箇所（採掘・壁の建設と撤去・魔導抽出・岩喰い・襲撃者の破壊）が
   すべて「深さも見る」必要が出る。
3. **`GameState` のフィールドを増やす前に、既存の何かで済まないか考える**（CLAUDE.md）。
   `TerrainType` にメンバーを2つ足すのは、`Tile` にフィールドを1つ足すより安い。

したがって `TerrainType` に `'shallowWater' | 'deepWater'` を足す。

### 2.2 `isRock` に入れてはいけない

`state.ts:233-241` の `isRock` は、いま**3つの意味を兼ねている**——
「通行不可」「`mine` の対象」「建築不可」。水は1つ目と3つ目に当てはまるが、2つ目には当てはまらない。

`isRock` に水を足すと、`veinYieldOf`（`constants.ts:216-224`）の既定が石を返すので、
**水を掘ると石が出る**。したがって `isRock` の隣に `isWater(terrain)` を新設し、
`isRock` の呼び出し 11 箇所を1つずつ見る。結果は次のとおり:

| 呼び出し元 | 水を足すか | 理由 |
| --- | --- | --- |
| `worldgen.ts:74`（`walkable`） | **別式で扱う** | 深水だけが通行不可。浅瀬は歩ける |
| `actions.ts:178`（建築の可否） | **足す** | ここが建築の唯一の地形ガード。足さないと湖の上に壁が建つ |
| `actions.ts:124`（`mine` 指定） | 足さない | 水は掘れない、が正しい |
| `worldgen.ts:337`（結晶の埋まり深さ） | 足さない | 岩の話 |
| `worldgen.ts:470`（霜花の「岩の際」） | 足さない | 岩の話。薬草は別の判定を持つ（4章） |
| `generator.ts:112` / `:463`（`mine` の有効性） | 足さない | 同上 |
| `mana.ts:295`（自動採掘の対象） | 足さない | 水は採掘対象ではない |
| `testUtils.ts:260` ほかテスト | 足さない | 岩の話 |

放牧（`actions.ts:347`）は既に `terrain !== 'grass'` で除外しているので変更不要。
貯蔵ゾーン（`actions.ts:325`）は `!tile.walkable` を見ているので深水は自動的に除外され、
**浅瀬には置ける** —— これは意図どおり（浅瀬は歩ける地面である）。

### 2.3 経路探索は変更不要

`isWalkable`（`pathfinding.ts:10-13`）は `Tile.walkable` を読むだけで、`terrain` を見ない。
`makeTile` が深水に `walkable: false` を書けば、A\* は既に水を避ける。
**`pathfinding.ts` には1行も触らない。**

### 2.4 生成

`worldgen.ts:186-191` に5本目のノイズ（`valueNoise2D(genSeed + 5147)`）を足し、
`:201-232` の地形決定に湖を入れる。優先順は「水 → 岩 → 森」——
水は岩より先に決める（湖の中に岩壁が立たない）。

`distToCamp > 6` の拠点クリアリング保護がそのまま効くので、拠点が水没することはない。

**深水はノイズの芯だけ、その縁は浅瀬**にする。これにより湖の岸は必ず歩けて、
薬草（4章）の生える場所が生まれ、将来の漁場の置き場所にもなる。

バイオームごとの湖の量は `BiomeProfile` に `waterThreshold` を1行足して表で決める
（`biome.ts:22-58` に足すと、4つのバイオームの行が埋まるまで**コンパイルエラーで止まる**。
これが狙いどおりの forcing function）。

### 2.5 既存セーブへの後付けはしない

結晶（9→10）と鉄（18→19）は既存の岩へ**レトロフィット**した。理由は「鉱脈の無いセーブは
そのフェーズに一度も入れないから」で、水にはその事情が無い。

そして水のレトロフィットは**能動的に危険**である。既に入植者が立っている・建物が建っている・
経路が通っているタイルを、後から通行不可にすることになる。移行（`migrations`）は
`createSimContext` の**前**に走るので、region の張り直しも退避もできない。

したがって移行は「何もしない」1段（`saveFile.ts:371-383` の 20→21 と同じ形）。
**古い植民地に湖は無い。新しい世界だけが水を持つ。**

## 3. 川と連結性 — 地図を割らないことを生成が保証する

### 3.1 川は浅瀬で作る

川の本体は**浅瀬**にする。深水は湖の芯だけに置く。これで「川は渡れる」が既定になり、
川が地図を2つに割ることが構造的に起きない。

見た目の上でも、幅1〜2タイルの帯が地図を横切って湖と地図端を結ぶ形は、
値ノイズの湖だけでは出ない「流れている感じ」を安く作る。

### 3.2 それでも連結性は生成が保証する

湖が偶然に地峡を塞ぐことは起こりうる。`derived.ts:143-190` の `RegionIndex` は
連結した歩けるタイルにラベルを振り、`isReachable` はそのラベル比較でジョブの候補を絞っている。
**地図が割れると、幾何的には近い森が「到達不能」になり、仕事が静かに消える** ——
CLAUDE.md が名指しで禁じている「プレイヤーに見えない失敗」そのものである。

そこで、生成の最後に**連結性の下限を保証する**。`enforceCrystalFloor`（`worldgen.ts:315-348`）が
「生成してから下限を満たすまで足す」形を既に持っているので、同じ形をなぞる:

1. 拠点のタイルから歩ける範囲を塗る。
2. 歩けるタイル全体の 90% 以上が拠点と同じ region なら、何もしない。
3. 満たなければ、拠点の region と最大の孤立 region を隔てている最も細いくびれを
   深水 → 浅瀬に落として繋ぐ。繋がるまで繰り返す。

この検査は生成時に1度だけ走る。実行時のコストはゼロ。

## 4. 薬草 — 水辺に生える3つ目の野生植物

### 4.1 新しい機構はゼロ

野生植物は既に2種ある（ベリー・霜花）。どちらも `BuildingType` の1行として置かれ、
`growCrops`（`simulation.ts:155-183`）で育ち、**既存の `farm` ジョブ**で収穫される。
霜花はフェーズ5で、`ResourceType` も `JobType` も `GameState` のフィールドも増やさずに入った。

薬草も同じ形をなぞる。違いは2つだけ:

- **生える場所**: 霜花の「岩の際の草地」（`worldgen.ts:461-469`）を「**水の際の草地**」に置き換える。
  これが水に意味を与える —— 湖のある世界にだけ薬が育つ。
- **産出**: ベリーも霜花も `food` を返すが、薬草は返さない（4.2）。

### 4.2 `food` の variant にはしない

`Item.variant`（`types.ts:88-94`）は既にあり、調理済みの食事が `food` の variant として入っている。
薬草も variant にできそうに見えるが、**採らない**。

理由は1つで、**腹を空かせた入植者が薬を食べる**から。`variant` は「されたこと」であって
「それが何か」ではない、と型のコメント自身が書いている ——
`food` の variant は「あらゆるジョブ・フィルタ・交易にとって依然として食料」である。

したがって `ResourceType` に `'herb'` を1つ足す。鉄（フェーズ10）が同じ形で
`ResourceType` を1つ増やした前例があり、貯蔵・運搬・ゾーンのフィルタはすべて
`ResourceType` に対して一般に書かれているので、追加のコストは
「移行でゾーンの `accepts` に1つ足す」だけで済む（`saveFile.ts:316-347` が前例）。

### 4.3 3種目は表にする

`berryBush || frostbloom` という2種前提の or は、いま**4箇所**にある
（`generator.ts:126`・`:468`、`execute.ts:175`、`simulation.ts:163-172`）。
3種目を足す前に、フェーズ10 が `VEIN_YIELD` でやったのと同じことをする ——
「植物 → 産出資源・量・成長速度・季節表」の対応表を1枚置き、4箇所がそれを引く。

**新しい機構ではない。** 既にある分岐の置き場所を、4箇所の or から1枚の表に変えるだけ。
以降、野生植物を足す作業は「表に1行・型に1メンバー・生成に1判定」になる。

## 5. 病気と治療 — 既存の `health` と既存のスキル機構に乗せる

### 5.1 状態はフィールド1つ

`Colonist` に **`illnessTicks: number`** を1つだけ足す（0 = 健康）。
これは導出できない（過去に何が起きたかの記録である）ので、保存対象になる。

重症度も、病名も、部位も持たない。1.1 で述べたとおり、`health` 1つに固定する規律は維持する。

### 5.2 効果はすべて既存の数値への乗数

| 効かせ先 | 形 | 既存のどこに乗るか |
| --- | --- | --- |
| 体力 | 毎 tick わずかに `health` が減る | 既存の負傷・餓死と同じ経路。**死に方を増やさない** |
| 作業速度 | 乗数が下がる | 気分・スキル・道具と同じ掛け算の列に1つ足す |
| 気分 | 思考が1つ増える | `mood.ts` の `thoughtsOf`。既存の思考の仕組みそのまま |

**発症**も新しい確率機構を作らない。`events.ts` のインシデント枠に1本足し、
頻度は既存の乗数（冬・気分・空腹）を引く。

### 5.3 治療 —— `JobType` を1つ足すとスキルが1つ生える

`SkillName = Exclude<JobType, 'deconstruct' | 'repair'>`（`types.ts:492`）。
つまり **`JobType` に `'treat'` を足すだけで、`treat` スキルが自動的に生まれる**。
要望の「入植者のスキルにも追加」は、これ以上の機構を必要としない。

- 作業優先度表に1列。既定優先度は `research` / `craft` と同じ最低（3）——
  プレイヤーが上げるまで、誰も勝手に医者にならない。
- 患者のタイルへ行き、`herb` を1個消費して `illnessTicks` を減らす。
  速さは `treat` スキルが決める（既存のスキル→速度の仕組みそのまま）。
- 供給は既存の `haul` で足りる（研究台・作業台と同型）。

### 5.4 アラートを1件足す

「病人がいる」を `alerts.ts` に1件。クリックで現場へ飛ぶ。

これは省けない。病気は**入植者が静かに弱っていく**形の変化で、
気付かないうちに死ぬのは CLAUDE.md が名指しで禁じている「プレイヤーに見えない失敗」である。
1つの問題に1つのアラート、という既存の原則（フェーズ13）に従う。

## 6. データモデル

| 追加 | 場所 | 移行 |
| --- | --- | --- |
| `TerrainType` に `shallowWater` / `deepWater` | `types.ts:53` | 何もしない1段（2.5） |
| `BiomeProfile.waterThreshold` | `biome.ts:22-58` + 4行 | 不要（`GameState` ではない） |
| `isWater(terrain)` | `state.ts`（`isRock` の隣） | 不要 |
| `BuildingType` に `herb` | `types.ts:268-282` | 不要（霜花が前例） |

水も薬草も、既存の `Tile.terrain` と既存の `Building` に乗る。

`schemaVersion` は現在 24。このフェーズで段階ごとに1ずつ上げ、**24 → 27** になる。

## 7. バランス初期値

すべて**見積もり**であり、実測で詰める（測定条件を添えて design-notes.md へ）。

| 項目 | 出発点 | 根拠（見積もり） |
| --- | --- | --- |
| 水タイルの割合（草原） | 全体の 4〜6% | 岩（既存）より少なく、地図に1〜3個の池が見える程度 |
| 深水:浅瀬 | 1:2 程度 | 岸が必ず1タイル以上あること |
| 拠点 region の占有率の下限 | 90% | 3.2 の保証。破ったら生成が繋ぎ直す |
| 薬草の株数 | 60×60 あたり 10 | 霜花（14）より少ない。水辺にしか生えないので実効はさらに減る |
| 薬草1回の収穫 | `herb` 3 | 治療1回が `herb` 1なので、1株で3回分 |
| 薬草の再生 | 1 / 6000 tick（2日） | ベリー（4日）より速く、霜花（1.5日）より遅い |
| 発症頻度 | 1人あたり 20日に1回程度 | 1年（20日）で植民地に数回。多すぎると作業台と同じ「常時対応」になる |
| 病気の `health` 減少 | 治療なしで約5日で危険域 | プレイヤーが気付いて動く時間があること |
| 治療1回 | `herb` 1・`treat` 相当の作業時間 | 研究1バッチと同程度 |

## 8. 段階と「動いたと言える条件」

段階ごとに条件を**先に**テストにしてから実装する（design.md 10 章）。

### 段階 W-1: 水地形（浅瀬・深水）

1. 浅瀬は歩け、深水は歩けない（`isWalkable`）。
2. 水の上にブループリントが置けない。
3. 水を `mine` に指定できない（指定できたら石が出てしまう）。
4. 拠点から森・岩へ **region で**到達できる（幾何距離ではなく `isReachable` で測る）。
5. 1年（20日）回して誰も水の上に立っていない。
6. ミニマップに水の色がある（`Minimap.test.ts:54-71` が自動で捕まえる）。
7. セーブ往復で地形が保たれ、旧セーブが拒否されずに読める。

### 段階 W-2: 川と連結性

1. 200 シードで、拠点の region から森を10タイル以上・岩を1タイル以上・
   マナ鉱脈のある岩塊へ到達できる。
2. どのシードでも歩ける陸地の 90% 以上が拠点と同じ region にある。
3. 川が地図を横切っているシードが実際に存在する（保証が効きすぎて川が消えていない）。

### 段階 H-1: 薬草

1. 薬草が**水辺の草地にだけ**生える。
2. 既存の運搬で倉に入る。
3. **空腹の入植者が薬草を食べない**（明示的にテストする）。
4. 野生の食料合計が畑を上回らない（`berries.test.ts:63-73` が壊れていない）。

### 段階 M-1: 病気と治療

1. 無操作1年（`longrun`）で、**病気だけを理由に全滅しない**。
2. 薬草があれば治り、無ければ治らない。
3. `treat` スキルが高いほど治療が速い（`skills.test.ts` と同型）。
4. 病人が出たらアラートに出る。
5. セーブ往復で `illnessTicks` が保たれる。

## 9. リスクと非目標

### 9.1 織り込み済みのリスク

**地形生成のループを触ると、固定シードの地図が総入れ替えになる。**
`season.test.ts:112` と `longrun.test.ts:112` に、鉄鉱脈を入れたときに同じことが起きて
再較正した記録が残っている。`worldgen.test.ts:44-52` の地形構成の下限（森10・岩0超）は
**測り直す**前提で進める。

**病気は「静かに効く」層である。** アラート（5.4）と気分の思考（5.2）を省くと、
プレイヤーには「なぜか入植者が弱っていく」としか見えない。この2つは機能の一部であって、
後回しにできる装飾ではない。

### 9.2 非目標

| 入れないもの | 理由 |
| --- | --- |
| 水生生物・漁業 | 今回は場所だけ用意する（1.2）。生態を足すのは別フェーズ |
| 橋・渡し | 浅瀬が渡れるので、当面は不要。深水を渡る需要が実測で出てから |
| 泳ぐ・溺れる | 深水は通行不可なので、そもそも入れない |
| 部位・傷の種類・感染 | `health` 1つに固定する規律は維持する（1.1） |
| 病気の伝染 | 発症を個人の確率に留める。伝染は「1人の不運が全滅になる」形で、予告と対処の設計が別に要る |
| 医師専用の建物（病院・診療所） | 治療は患者のベッドで足りる。家具（フェーズ10）が既にベッドの質を持っている |
| 薬の調合（作業台のレシピ） | 薬草をそのまま使う。レシピを足すのは、薬草が余ると実測で出てから |
