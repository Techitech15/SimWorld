# SimWorld 追加検討ノート

[design.md](design.md) は**仕様**——いま何がどう動くか——を書く場所で、このファイルは**なぜそうしたか**を書く場所。
MVP のあとに足した要素について、検討したこと・測った値・案から変えた点・壊してから学んだことを残す。

分けている理由は単純で、仕様と理由は寿命が違うから。仕様は実装が変われば書き換わるが、
「なぜ牧場の受け入れ資源を食料だけにしたか」は実装が変わっても消えてはいけない記録になる。

数値はすべて**実測値**であり、推定ではない。測った条件（シード・日数・試行数）も一緒に残してある。

# 差分と現況

## 当初の型に足したフィールドと、その理由

設計書 4 章はいま実装に追随して更新されているので、そこを読めば**現在の型**は分かる。ここに残すのは
**なぜそのフィールドが要ったか**——当初の型定義から足したものと、その必然性。「メソッドを持たない
プレーンデータ」という原則は一度も崩していない。追加箇所は `src/core/types.ts` に `[ext]` コメントで
明示してある。

| 追加                                                 | 理由                                                                                                                                                                                           |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Tile.designation`                                   | 6章の「伐採指定された木」「採掘指定タイル」を保持する先が必要                                                                                                                                  |
| `Building.buildProgress` / `growth` / `sown`         | 建築進捗と畑の3段階（12章のスプライト仕様）に対応                                                                                                                                              |
| `Colonist.carrying`                                  | 運搬ジョブが荷を持つ状態を表す                                                                                                                                                                 |
| `Colonist.activity`                                  | ニーズ由来の食事・睡眠・移動命令。ジョブシステムの外側に置く（プレイヤーが優先度を付ける仕事ではないため）                                                                                     |
| `Colonist.workPriorities`                            | `setJobPriority(colonistId, jobType, priority)` が入植者ごとの優先度を前提にしている                                                                                                           |
| `Colonist.color`                                     | 12章「個体差は色替えで対応し、共通の歩行スプライトシートを使い回す」                                                                                                                           |
| `Job.workType`                                       | 実行内容（`type`）と、どの仕事列で優先度を引くか（`workType`）の分離。ブループリントへの資材運搬は「建築」の仕事として扱う（そうしないと運搬を最低優先度にした植民地で建物が永久に完成しない） |
| `Job.payloadType` / `destinationId` / `workProgress` | 運搬先と運ぶ資源、作業進捗                                                                                                                                                                     |
| `GameState.nextIds` / `log`                          | ID 採番をセーブ間で安定させるため／失敗ジョブのログ（6章）                                                                                                                                     |

その他の実装上の判断:

- **扉は MVP では常に通行可能**とし、開閉はスプライトの見た目のみ（`BLOCKS_MOVEMENT`）。
- **貯蔵ゾーンは資材コストゼロ**なので、ブループリントを経ずに完成状態で設置される。
- 1 タイルの貯蔵スタックは 1 資源種類・最大 `STACK_MAX`。


## フェーズの進め方

魔力インフラ・物語生成・防衛は、当初 MVP から明示的に外されていた（9章・11章）。あとから足せるよう、
資源と建築のテーブルは `src/core/constants.ts` に集約してある —— `ResourceType` に1行足せば貯蔵・運搬・
食事・UI の全経路が追随する形にしてあり、マナ結晶の追加が実際にその形で済んだ。

**何がどこまで進んでいるかの表は [design.md](design.md) の 11 章**にある（仕様側の役割）。ここには
順序についての判断だけ残す。

- **生物レイヤーは本編ロードマップに無い追加**なので、フェーズ2と独立に着手できる「フェーズ2.5」として
  位置づけた。捕食者を入れるために HP と死亡を最小構成で導入する点だけが 9 章「含まないもの」からの
  意図的な逸脱で、その範囲と限界は [design-phase2.5-animals.md](design-phase2.5-animals.md) の 1 章と 11 章にある。
- **フェーズ3のうち特性・気分・思考だけを先に取った。** 入植者を「二本のゲージを持つ機械」から個人に
  するのに、関係性やメンタルブレイクの一式は要らなかった。依存順（フェーズ4のタレットはフェーズ2が
  前提）は崩していない —— 依存の無い部分を先に取っただけ。
- **フェーズ2は段階に割った。** A=結晶を掘れる、B=炉と送電と最初の消費建築、C=生産チェーンを変える
  消費建築。段階Bで照明まで入れたのは、結晶→炉→送電→効果が繋がって初めて「魔力インフラ」と言えるため。
  炉と導管だけ入れて「Bは完了」と言うことはできた——が、プレイヤーから見れば何も起きていない。

# 魔力インフラ（11章 フェーズ2）

## マナ結晶（フェーズ2 段階A）

設計書 11 章のフェーズ2は「既存の生産チェーンに電力に相当する制約を足す」段階で、その入力になるのが
マナ結晶。設計書は新規ジョブについて「既存の `mine` ジョブの対象拡張で対応可能か検討」と書いていて、
その答えを地形の側で出した ——**マナ結晶は建築ではなく地形**（`crystal`）であり、採掘指定も
ジョブも運搬も既存のものがそのまま動く。増えたのは「岩の面から何が出るか」の1分岐だけ。

鉱脈は岩盤の**奥**にしか湧かない（`s > 0.86` かつ結晶ノイズ）。8世界を実測すると1世界あたり 4〜57 本、
開けた地面まで岩を 2〜4 タイル（最悪 8）掘り進める必要がある。

（この 4〜57 は標本8世界のもので、**分布の尾を捉えていない**。段階Bで結晶が燃料になったあと
200 シードで数え直したところ 0〜194 本・中央値 40 で、鉱脈が1本も無い世界が 3/200 あった。
供給量として何を意味するかは [design-next.md](design-next.md) の 1 章。）初日に拾えるマナがあるとフェーズ2の
パズルが無料になるので、**掘って取りに行くもの**であることを地形で担保している。

1本あたりの産出は 6（岩1タイルの石 20 より少ない）。マナは全体の制約になる資源なので、
石より稀であることが出発点。

| 規則 | 値 |
| --- | --- |
| 鉱脈の湧く条件 | 岩盤のうち特に厚い部分（`s > 0.86`）＋結晶ノイズ |
| 1本あたりの産出 | 6 マナ結晶 |
| 採掘時間 | 岩と同じ（60 tick） |
| 到達性 | 岩の中なので、掘り進めない限り到達不能な仕事になる |

`isRock()` を1つ置いて、地形生成・採掘ツール・ジョブ生成・有効性判定の4箇所がすべてそれを通るように
した。新しい岩を1箇所に教えて別の箇所で忘れる、という壊し方を型と述語の側で塞いである。

この変更でセーブを `schemaVersion` 10 に上げた。v9 以前のセーブには鉱脈が存在しないので、移行時に世界シードから決めた
位置に埋め込む（同じ世界なら何度読み込んでも同じ場所）。既存の貯蔵ゾーンの受け入れ資源にも
`manaCrystal` を足す —— プレイヤーが除外していないものが除外された状態で現れてはいけない。


## 魔力ネットワーク（フェーズ2 段階B）

設計書 11 章が求めるのは「材料が足りるか」ではなく **「供給し続けられるか」** という第二の制約。
その形が魔導炉・導管・照明の3つ。

- **魔導炉**（石25＋木10）はマナ結晶を燃やしてネットワークに 10 供給する。1個の結晶で 2/3 日燃える。
- **導管**（石2）は隣接する魔力建築を1つのグリッドに繋ぐ。**歩ける** —— 送電線が回り道を強いる壁に
  なってはいけない。
- **魔力灯**（石4＋木4）は 3 消費し、半径6タイル以内の入植者の気分を +5 する。

### ネットワークは導出であって保存しない

`ManaNetwork` / `ManaGrid` は連結成分ラベリングで、変わるのは建物が増減したときだけ ——
つまり既存の**領域ラベルとまったく同じ形**なので、同じ場所（`SimContext`）に同じ作りで置いた。
セーブには入らない。保存されたネットワークは、それが繋いでいると主張する建物と食い違いうる。

ダーティフラグだけに頼るのはやめた。フラグは**最後にセットし忘れた人の分だけ嘘をつき**、しかも
その嘘は静かだ（地図上にあるのにどのグリッドにも属さない灯）。tick ごとに state オブジェクトが
作り直されるので、それと突き合わせることで、セットし忘れの代償が「永続」から「1 tick」になる。

### 供給不足はグリッド全体を落とす

部分的なブラウンアウトにすると「誰から切るか」の規則が要り、プレイヤーは何が起きたかを知るために
建物ごとの状態を読む羽目になる。**落ちたヒューズ**なら見て分かる事実が1つで、打つ手も2つに絞られる
（炉を増やす／負荷を減らす）。

### 燃料補給は新しい仕組みではない

炉への結晶運搬は**ブループリントへの資材運搬とまったく同じ haul ジョブ**で、行き先が完成済みの建物
なだけ。マナを維持する仕事が他の運搬と同じ優先度列で競合する —— これがフェーズ2の狙いそのもの。

実装中に見つかった落とし穴を2つ記録しておく。`isJobStillValid` は運搬先が**ブループリントであること**を
条件にしていたので、生成された燃料ジョブは毎回その場で無効化されていた（テストが無ければ、機能全体が
静かに何もしないまま出荷されていた）。もう1つ、満杯の炉に運び込んだ余りの結晶が消滅していた ——
地図上で最も希少な資源を、プレイヤーに見えない失敗のために黙って削るのは論外なので、地面に戻す。

| 建築 | コスト | 供給 | 消費 | 通行 |
| --- | --- | --- | --- | --- |
| 魔導炉 | 石25・木10 | 10 | — | 塞ぐ |
| 導管 | 石2 | — | — | 通れる |
| 魔力灯 | 石4・木4 | — | 3 | 通れる |


# 生態と環境

## 自動採掘機（フェーズ2 段階C）

照明は気分に効くが、**生産チェーンそのものは変えない**。設計書 11 章がフェーズ2に期待しているのは
「最適化パズルの発展」なので、段階Cで入れたのは労働を置き換える機械。

魔力 8 を消費し、**半径3タイル以内の岩を 500 tick に1タイル**、入植者なしで削る。出た石（結晶なら結晶）は
機械の足元に落ち、あとは既存の運搬チェーンが拾う。

プレイヤーが買っているのは**速さではなく労働**。入植者は1タイル 60 tick で掘るので、機械は8倍以上遅い。
その代わり歩かず、食事も睡眠も取らず、指示も要らない。対価は炉の出力ほぼ全部（供給10に対し消費8）と、
その炉を燃やし続ける結晶。**炉1台で採掘機1台**——2台は乗らない。これがこの段階の判断そのもの。

### 半径3にした理由（隣接のみから変更）

最初は隣接1マスのみにした。「地図の向こうまで届く機械では、どこに置くかという唯一の判断が消える」という
理屈だったが、隣接だと**最大4タイル＝石80**しか掘れない。石30・木15・炉1台・結晶の継続消費に対して
4タイルで用済みになり、あとは解体するしかない置物になる。誰も2台目を建てない。

半径3なら最大で二十数面あるので、機械として金を払う価値があり、「どの岩壁に寄せて置くか」は依然として
実際の判断として残る。**近い面から順に**削るので、外側へ食い進む。

### 停電は取り返せない

電力が落ちると進捗はその場で止まり、復旧後はそこから再開する（`Building.manaProgress` に保存）。
tick から導出すると停電が無コストになり、炉を燃やし続ける意味が消える。

### 実装中に見つかった不具合

`isManaBuilding()` が建築3種を**手書きで列挙**していたので、追加した採掘機はどのグリッドにも属さないまま
地図上に立っていた。何も消費せず、何も掘らず、エラーも出さない。修正はテーブル側からの導出:

```ts
type === 'manaConduit' || type in MANA_OUTPUT || type in MANA_DRAW
```

供給か消費を持つものは自動的にネットワークの一員になる。**describe するものと別に更新が必要な規則は、
いつか必ず忘れられる**（`isRock()` を1つ置いた理由と同じ）。

テスト側にも1つ。採掘機の周りを掃除せずに岩を並べていたので、地図が生成した別の岩が同距離にあるシードでは
そちらを削り、機能のバグに見えた。実測で分かる類のものではないので、**リグは自分が使う範囲を明示的に
作る**ようにした。

## 森の再生

木材だけが「使い切れる」資源だった。草は生え直し、ベリーは実り直し、野生動物は端から歩いて戻ってくるのに、
伐った木だけは永久に戻らず、地図を丸裸にすると木材が二度と手に入らない。

規則は最小限にした ——「木の隣の裸地は木になりうる」（日1回・4%・冬は停止）。これだと伐採跡は外側から
ゆっくり塞がるので、目の前の最後の木を伐ることには依然として代償がある。

ただしこの規則には**不動点が無い**。5年分を実測したところ森 1033 → 2253、草原 1892 → 672 で、放っておくと
放牧地が消える。そこで地図の**森林容量**（生成時の森タイル数）を `GameState.forestCapacity` に持たせ、
再生はそこまでで止まるようにした。森は戻るが、草原を侵食はしない。


## 出来事（インシデント）

世界はこれまで「毎日の規則」しか実行していなかった —— 作物は育ち、狼は狩り、余裕があれば移住者が来る。
だが**何も起きない**ので、どの年も記憶に残らず、食料を解決した植民地はゲームを解き終えてしまう。
設計書のフェーズ3（物語生成）の最小版として、季節重み付きの出来事を6種入れた（`src/core/events.ts`）。

| 出来事 | 内容 | 起きやすい季節 |
| --- | --- | --- |
| 陽気 | 実りかけの畑が一斉に収穫可能になる | 秋 |
| 立ち枯れ | 畑の一部が全損（**最大でも半分まで**） | 夏 |
| ベリーの当たり年 | 森のベリーが一斉に熟す | 春〜秋 |
| 狼の群れ | 通常の上限とは別に2頭が現れる | 冬 |
| 渡りの群れ | 鹿か兎が4頭通りかかる | 春・秋 |
| 落とし物 | camp 近くに木材か食料が落ちている | 冬 |

判定は1日1回・確率0.3で、**全て即時効果**にしてある。これは手抜きではなく制約 —— 「3日間成長が落ちる」
ような持続効果は `GameState` のフィールドとマイグレーションと毎 tick の失効処理を要求するのに対し、
即時効果はどれも不要で、それでいてプレイヤーが対応を迫られる部分は変わらない。

**ログのノイズ削減**: 10倍速で5日走らせた実測では、ログの4/5が「野生動物が狼に食われた」で埋まっていた。
狼が森で兎を食べるのは天気であってニュースではないので、**野生かつ未指定の動物の死は記録しない**ように
した（100行のバッファから、移住者の到着・家畜の損失・柵の破損といった**プレイヤーが行動する情報**を
押し出してしまうため）。自分の家畜と、狩猟・屠殺を指定した動物は従来どおり記録する。実測では 1年あたり **43行**（うち25行が
スキルのレベルアップ）まで減り、読めるだけの量になった。

なお `state.log` は100件のリングバッファなので、長時間の実行結果をログから測ると**バッファを測ってしまう**。
毎 tick 末尾を数えるのはさらに悪く、同じ1行を数千回数える（実際にこれで「1年で25,154回レベルアップ」
という測定結果を出してしまった。上限は約400回）。`recordLog`（`testUtils`）が正しい記録方法を1箇所に
まとめてある。

出来事はログ上で色分けされる（`LogEntry.kind`）。狼の群れの到来が「Hauling がレベル2になった」と
同じ見た目では気づけないため。`kind` は任意フィールドなので、これ以前のログ行は「印なし＝通常行」として
そのまま読め、マイグレーションを要さない。

新しい植民地が最初の出来事に出会うまでの日数を120ワールドで実測: **中央値4日目・90パーセンタイル8日目・
出会わないワールドは0**。6種すべてが「最初の出来事」として現れる。

乱数は tick と**世界シード**の両方から導く。tick だけだと再現性はあるが、**これまでに始まった全ての植民地が
同じ暦を共有する**ことになり、序盤の静かな2週間まで含めて毎回同じになってしまう。実測（400日）では
発生率はどちらでも設計通り（0.3/日に対し 122/400）で、世界シードが買っているのは**別の植民地が別の年を
過ごすこと**の方。セーブを読み直せば同じ年が再生される点は変わらない（両方テストで固定）。


## シナリオ（開始条件）

これまでどの地図も「ノイズ違いの同じ地図」だった。シードが変えるのは木の位置であって、それは
風景の多様性であってゲームの多様性ではない。開始1週間で実際に効く3つの数値だけを動かす3種を用意した
（`src/core/scenario.ts`）。

| シナリオ | 入植者 | 畑 | 初期資源 | 獲物 | 狼の上限 |
| --- | --- | --- | --- | --- | --- |
| Sheltered valley（穏やかな谷） | 4 | 8 | 食料240・木材120・石30 | 1.5倍 | 1 |
| Open country（標準） | 3 | 5 | 食料120・木材60 | 等倍 | 2 |
| Hard frontier（過酷な辺境） | 2 | 2 | 食料60・木材40 | 0.6倍 | 4 |

季節・スキル・特性・移住・森の再生はどれも共通なので、シナリオが変えるのは**規則ではなく立ち上がり**。
狼の上限は生成時の一度きりの決定ではなく毎日走る規則なので、シナリオ名は `GameState.scenario` に保存する。
標準は従来の値そのままで、既存の計測結果を静かに壊さないことをテストで固定してある。

**初版は初期資源だけを動かしていて、実質的に見た目だけの違いだった。**1年計測したところ gentle も harsh も
人口6・食料1400前後で終着していた ——「倉庫の中身は2日で使い切られ、その後は畑がすべてを決める」ため。
入植者数と畑数を動かすようにして再計測した結果:

| 時点 | Sheltered valley | Open country | Hard frontier |
| --- | --- | --- | --- |
| 5日目 | 人口4・食料1084 | 人口3・食料692 | 人口2・食料383 |
| 10日目 | 人口6・食料2185 | 人口5・食料1403 | 人口3・食料812 |
| 15日目 | 人口7・食料2457 | 人口6・食料1440 | 人口4・食料815 |

差が最初の数日で消えず1年続き、なおかつ Hard frontier でも餓死者は出ない（遅れているだけで詰んではいない）。
テストも「5日目の食料比較」から「10日目＝立ち上がりを過ぎた時点」に変えてある。


## 家畜の一連の流れ

牧場・繁殖・産卵はそれぞれテスト済みだったが、**どれも「手で置いた家畜」から始まっていた**。
プレイヤーが実際に通る道（牧場を描く → 野生動物に手懐けを指定する → あとは植民地がやる）は
どのテストも通っていなかった。実ビルドで先に遊んで確認した（牧場を描き、全体に手懐け指定、
4日目に山羊を含む5頭が家畜化）うえで、同じ流れを `livestock.test.ts` に落としてある。


## 山羊

牧場タイルは種によらず1頭ぶんなので（`PASTURE_TILES_PER_ANIMAL`）、**囲いの価値は頭あたりの産出で決まる**。
ところが手懐けられる動物は全て小型で、最良でも鶏（1500 tick ごとに卵6）だった。山羊はその倍を短い周期で出し、
屠殺時の肉も鶏より多い。代わりに手懐け成功率は低い —— **手に入れにくく、飼う価値が高い**。

万能にはしていない。**猪の方が大きな肉**（45 対 30）で、その代わり生きている間は何も産まない。
「狩るか、飼うか」が選択のまま残るようにしてある。

（実装時、コメントに「鶏は山羊の1/4の牧草地で済む」と書いたが**これは誤り**で、牧場の収容数は種を見ない。
テストが「山羊は全ての項目で最良」という過大な主張も落とし、猪の肉が上回ることを明示的に固定した。）


## 動物を見つける・追う

動物は33頭生成され、うち8〜9頭は初期カメラ内にいるが、緑の地形に対して小さく、森の中では特に紛れる。
動物パネルの種名をクリックすると、その種の最寄りの個体へカメラが飛ぶようにした（入植者一覧と同じ操作）。

最初の実装はクリック時点の**タイル**を選択していたが、実ビルドで測ると**5種すべてがパネル描画までにその
タイルを離れて**いて、選択パネルは「ここに動物はいない」と表示していた。動くものはタイルではなく
**個体そのもの**を選ぶ必要がある（入植者には既に `selectedColonistId` があった）。`selectedAnimalId` を
追加し、`AnimalDetail` パネルが対象に追従するようにした —— 名前・種別・現在地・行動・健康・空腹・
産出量・屠殺時の肉。再測定で5種とも追従を確認（28,44 → 29,44 など）。


## ファンタジー層の4種（フェーズ5 F-A〜F-D）

設計案（[design-phase5-trade.md](design-phase5-trade.md) 3 章）が置いた選定基準は
「**実測で分かっている穴を塞ぐこと。飾りとして足したものは1つも無い**」だった。
4種とも新しい機構ではなく、**既存の数値を曲げるか、既存の表に1行足すか**で成立している。

| 追加 | 塞ぐ穴 | 実装の中身 |
| --- | --- | --- |
| 霜花 | 冬に食料が落ちる一方で、冬にできる仕事が無い | 建築型1つ＋季節表1枚（`FROSTBLOOM_GROWTH_BY_SEASON`） |
| 光苔 | 冬に草が戻らず、囲った群れが打つ手なく餓える | `Tile.forage` が回復する条件をもう1つ |
| 晶角鹿 | マナが唯一再生しない資源 | `SPECIES` に1行と `produceType` の1フィールド |
| 岩喰い | 鉱脈が岩の奥で到達不能／外圧が狼1種だけ | 3つ目の食性 `lithovore` |

`ResourceType`・`JobType`・`GameState` のフィールドはどれも増えていない。**セーブの移行は不要**で、
`schemaVersion` は交易の 16 のまま。

### 霜花 —— 冬の落ち込みが半分になった（実測）

同じ3シードを、霜花だけを 0 株にした対照と突き合わせた（1年＝20日、無操作、標準シナリオ）。

| シード | 秋末の食料 | 冬末（霜花あり） | 冬末（霜花なし） | 差 |
| --- | --- | --- | --- | --- |
| 1201 | 1691 | **1418** | 1140 | +278 |
| 1301 | 1621 | **1260** | 1038 | +222 |
| 1409 | 1636 | **1437** | 1176 | +261 |

秋の山からの落ち込みは −551/−583/−460 が −273/−361/−199 になる。**冬の減りがおよそ半分**になり、
それでもまだ減る —— 越冬の緊張は残っている、というのがここで欲しかった形。
シード 1409 では余った食料で移住者が1人多く定着した（4人 → 5人）。

収穫量は `food` 7 とベリーの 9 より**低く**してある。冬が「別のことをする季節」になればよいのであって、
「良い季節」になってはいけない。

### 光苔 —— 灯りが装飾から設備になった（実測）

[design-phase2.5-animals.md](design-phase2.5-animals.md) 12 章が記録している穴 ——
冬に草が戻らないせいで「囲った群れがプレイヤーの打つ手なく餓死していた」——
を、実際に再現できる形にして測った。5×5 の牧場に8頭、**牧草を食べ尽くした状態で冬に入る**。

| 条件 | 冬明けの頭数（4シード） |
| --- | --- |
| 灯り無し | 0 / 0 / 0 / 0 |
| 灯り有り（供給の通った魔力灯1基） | 8 / 8 / 8 / 7 |

**全滅か、ほぼ全頭生存か**というくらい効く。ここで初めて、魔力灯が「気分 +5 の装飾」から
**冬を越すための設備**になった —— フェーズ2が生産チェーンに触れた最初の場所である。

回復率は夏草の 0.6 倍（冬草の 0.15 倍に対して4倍）。灯りの下が最良の牧草地になっては困るので、
夏草より**遅い**ままにしてある。灯りが消えると回復は止まるが、既に生えた分は消えない。

実装で1つ効いたのは、**草かどうかを見るのをやめた**こと。放牧の判定は
「そのタイルに `forage` があるか」だけを見るようになった（草地は最初から持っており、それ以外は
灯りの下でしか増えないので、結果は以前と同じ）。地形で分岐したままだと、石床の上の苔を
食べられない、という「プレイヤーに見えない失敗」がそこに1つ残ったはずだった。

### 晶角鹿 —— 1頭では炉を賄えない、を数字で固定した

設計案 6.3 の出発点は「2400 tick に**2個**」だったが、それだと 1日 2.5 個で、
魔導炉の消費（1980 tick に1個 ＝ 1日 1.52 個）を**上回ってしまう**。
受け入れ条件は「**晶角鹿1頭では魔導炉1基を賄えない**」なので、案の側が条件と矛盾していた。

産出を 2400 tick に **1個**（1日 1.25 個）へ下げた。結果:

- 1頭 … 1.25 < 1.52。炉は少しずつ燃料を減らす。**足りない**
- 2頭 … 2.50 > 1.52。炉1基が回り、少し余る

鉱脈は「掘って取りに行くもの」のまま（1本6個）で、群れは**掘り尽くした地図を死んだ地図にしない**
ためのもの、という役割分担になった。体力・肉・手懐けやすさはすべて鹿より下にしてある。

### 岩喰い —— 脅威ではなく、動く地形

入植者も家畜も襲わない。狼の獲物にもならない（肉が0で逃げないので、狼が岩に噛みついたまま
餓死する）。できるのは岩を食うことだけで、900 tick（実時間で3分）に1タイル開ける。

**鉱脈は食わない。** 食うのはただの岩と石壁だけで、鉱脈は「その手前の岩が開いた結果**露出する**」。
マナを食う生き物は地図で最も希少なものを植民地と奪い合うことになるが、道を開けるだけの生き物は
**プレイヤーが仕組まなかった幸運**になる。

実測（3シード・1年）: 2頭で岩 **94タイル**が開く。地図の岩は 419〜643 タイルなので、
1年で 15〜22%。5年放置すれば岩は目に見えて減るが、20日の1年で地形が別物になることはない。

ログについては一度失敗している。開けたタイルごとに1行書いたところ、1年で 94 行になり、
**「狼が兎を食べた」で埋まっていた頃のログ**に逆戻りした（`logging.test.ts` が落ちて気づいた）。
いま書くのは**鉱脈が露出したときと、石壁が破られたとき**だけ。丘で岩が1つ開くのは天気であって、
知らせる必要があるのは「**これで採掘を指示できる**」という変化の方である。

構造物の撤去は捕食者が扉を齧る経路と共有した（`breakStructure`）。予約の解放・魔力ネットワークの
無効化・リージョンの再構築は**どれか1つ忘れると静かに壊れる**種類の後始末で、
齧る主体が増えるたびに書き写すのは、忘れる場所を増やすのと同じ。

# 入植者

## 交易（フェーズ5 T-A・T-B）

植民地が資源を得る道は、これまで**地図から取ってくる1本だけ**だった。交易は2本目で、しかも
**地図に無いものを余剰から作れる**唯一の道 —— 鉱脈がゼロの世界で最も効く。

設計案（[design-phase5-trade.md](design-phase5-trade.md)）の3つの判断はそのまま実装した。

- **物々交換。通貨を作らない。** 通貨は「今売って後で買う」を可能にし、決断を先送りにできてしまう
- **商人は歩かない。** 柱の隣に現れて立ち、消える。経路探索を一切しないので A* 予算に影響しない
- **取引は既存の haul ジョブ。** 行き先が完成済みの建物なだけで、魔導炉の燃料補給とまったく同じ形。
  仕事優先度表は7列のまま。運搬を最低優先度にした植民地では**取引が流れる** —— バグではなく、
  炉が冷えるのと同じ設計意図

### 灯りは条件ではなく格上げ、を実装で守る

設計案が「一度間違えかけた」と記録している点 —— 灯りを来訪の条件にすると、鉱脈ゼロの世界は
**灯すためのマナを買うために灯りが要る**閉じた輪に入る。行商人は食料だけで来て、灯りは
晶商への格上げにだけ効く。テストで固定してある。

実装中にこの輪が**別の形で閉じかけた**。品揃えを毎回ランダムに間引いていたので、
**晶商がマナ結晶を持たずに来ることがあった**（実測: シード 8043 の晶商は木材と石だけ）。
灯りが「上がるかもしれない」ものになり、格上げの約束が壊れる。看板になっている品目だけは
間引かないようにした。

### 拾い上げ量の分岐が1つ足りなかった

運搬ジョブは「行き先が何をいくつ欲しがっているか」で拾う量を決める。ブループリントは資材表、
魔導炉は燃料規則、貯蔵タイルは全部。交易柱は**そのどれでもない**ので資材表を見に行き、
交易柱に資材表は無いので **0 を返し、荷を持ち上げた瞬間に取引がキャンセル**されていた。
行き先の種類ごとに答えが違う分岐は、種類が増えるたびに**答えないものが1つ増える**。

### 価格

| 資源 | 基準価値 |
| --- | --- |
| 木材・石 | 1 |
| 食料 | 2 |
| マナ結晶 | 12 |

商人は基準価値の 0.7 倍で買い、1.4 倍で売る。木材120でマナ結晶がおよそ3〜8個（実測レンジ、
商人ごとの幅を含む）。1本の鉱脈が6個なので、**交易は鉱脈の代わりにはならず足りない分を埋める**。
価格は tick と世界シードの両方から引くので、同じセーブを読み直せば同じ商人が同じ品を同じ値で持ってくる
（テストで固定）。

## 襲撃・戦闘・タレット（フェーズ4）

これまで危険なものはすべて**歩いて離れられた**。狼は捕れるものを捕って興味を失うので、入植者の答えは
逃げること、プレイヤーの答えは狩人を送ること。襲撃者は初めて**植民地そのものを目指して来る** ──
地図を横切り、邪魔なものを壊し、満足するまで諦めない。

だからこの段階で2つが必然になる。誰かが立って戦わなければならない（入植者が逃げる以外のことをする初）、
そして魔力ネットワークにようやく守るものができる（タレットがフェーズ2の後にしか来られない理由）。

### 民兵に専用画面を作らなかった

戦うのは**狩猟列が有効な入植者**。危険な動物を任せている人がそのまま襲撃にも出る。徴兵UIを足すと、
プレイヤーが管理する表が2つになる。

戦闘状態も `Colonist` の新フィールドではなく `activity: fighting` にした。仕事・気分・ニーズはすでに
`activity` を見て動いており、新フィールドは「見落とす場所」を作る。

### 実測で3つ直した

**1. 「諦めて引き返す」が1年に1,891回ログに出た。** ローカル変数を更新前に読んだまま分岐に使っていたので、
毎 tick「引き返す」と宣言しながら攻撃を続けていた。更新後に読み直して修正。

**2. 3世界のうち2つで、1年間まったく襲撃が来なかった。** 他の災厄と同じ重みだったため。
**誰も必要としない防衛層は、誰も建てない建物**でしかない。重みを 3〜4 に上げて再測定 → 2回 / 0回 / 1回。
8日目までのゲートがあるので、上げても序盤が理不尽にはならない。

**3. 引き上げる襲撃者が地図に居座った。** 端に到達しないと消えない実装で、実測では1回の襲撃の残党が
5,000 tick 近く歩き回っていた。壁や岩で出口を見つけられない個体のために、猶予 600 tick 後の強制退去を
足した。

### 現状のバランス（3世界×1年の実測）

| シード | 襲撃 | 倒した襲撃者 | 入植者の死 | 最少人口 |
| --- | --- | --- | --- | --- |
| 9719 | 2 | 2 | 0 | 3 |
| 9723 | 0 | 0 | 0 | 3 |
| 9727 | 1 | 2 | 0 | 3 |

**いまのところ植民地が勝つ。** 初期設定では全員の狩猟列が有効なので、3〜6人全員が民兵になるため。
壁を壊されたケースも無かった。危機として物足りない可能性はあるが、これは測った事実であって
「ちょうどいい」という主張ではない。強くするなら襲撃者の数か体力を上げるのが次の一手。

### recordLog が1 tick 2行を落としていた

襲撃者が倒れる行と「襲撃は終わった」の行が同じ tick に出る。`recordLog` は**末尾だけ**を見ていたので、
死亡の行が記録から消えていた。前回見た行以降を全部拾うように直してある（バッファから溢れていた場合は
残り全部が新しい行）。これは共有ヘルパーの改善なので、他のテストにも効く。

## 娯楽とメンタルブレイク（フェーズ3）

この2つは別々の機能ではない。**人によって満たされるニーズ**を入れると炉端が建てる価値のあるものになり、
それが尽きることが「立ち尽くす」以外のブレイクの引き金になる。だからまとめて1つとして実装した。

### 娯楽は他人が満たす唯一のニーズ

2日で満杯（空腹の 0.8 日、睡眠の 16 時間より遅い）。閾値を越えると炉端へ向かい、150 tick 座る。
回復量は **炉端 1.0 / 地べた 0.45 / 仲間が近くにいると ×1.5**。関係性の後に実装したのはこのため ——
「誰かと過ごす」が効く土台が先に要る。

空腹と睡眠には常に譲る。飢えたまま火に当たる者はいないし、これは植民地が**後回しにできる**唯一のニーズ。
眠っても抜けない ——「睡眠は休息ではない」。ここを同じ扱いにすると、ベッドのある植民地は炉端を
建てる理由が消える。

**快適・美しさはニーズにしなかった。** 床・寝床・灯・冬はすでに気分の思考として載っている。
バーを2本増やしても同じことを二重に言うだけで、プレイヤーの操作は増えない。

### ブレイクは賽ではなく引き金で決まる

| 引き金になった思考 | 見た目 |
| --- | --- |
| 餓死しかけ・空腹 | **binge** ── 倉を漁って食べる |
| 眠い・立ったまま寝そう・孤独・喪 | **wandering** ── ふらふら歩き去る |
| それ以外 | **brooding** ── 立ち尽くして仕事を拒む |

無作為に選ぶと、**1つの出来事に対する3種類のアニメーション**にしかならない。引き金で決めれば、
プレイヤーは入植者の様子を見て理由を逆算できる。3種とも仕事は止まり、違うのは植民地が何を
見せられるかだけ。

### テストのリグが3回嘘をついた

この機能のテストで、リグ側の間違いを3つ踏んだ。記録しておく価値がある種類のもの:

1. **体力35を3ケース共通で設定していた** → 「重傷」(-19) が常に最悪の思考になり、何を並べても
   brooding になった。選択規則は正しく、リグが嘘をついていた。
2. **空腹10・睡眠20 にしていた** → 「満腹」+6 と「よく眠れた」+6 が入り、mood が 31〜32 で
   限界(20)を割らない。中間帯（40）にして思考を消す必要があった。
3. **ランダムウォークの終点を見ていた** → シード 6037 は 400 tick 後に**出発点へ戻ってきた**。
   「ふらつく」の意味は終点ではなく「立ち止まらない」なので、走行中の最大距離を見るように直した。

どれも機能ではなくテストの設計の問題で、機能の側を直していたら壊していた。

## 関係性（フェーズ3）

入植者6人の植民地は、これまで**独立した生存機械が6台**だった。1人失うのは手が1組減ることでしかなく、
1年間となりで働いた相手と、昨日歩いてきた他人が同じ扱いだった。

絆はペアごとの数値1つ。近く（4タイル以内）で起きて過ごすと育ち、離れていると緩やかに薄れる。
買えるものは2つ ——**仲間の存在**と**喪**。どちらも新しい仕組みではなく、既存の気分システムに載る
（特性が守った規則と同じで、これが十数個の追加を十数個の特殊ケースにしない理由）。

### 速度は測って2回変えた

最初のレート（1インターバルあたり1.0、離れても減らない）で1年（20日）回した実測:

| 日 | ペアの affinity（最小〜最大） | 友人ペア数 |
| --- | --- | --- |
| 1 | 16〜31 | 0 |
| 5 | 47〜100 | 2/3 |
| 18〜20 | **全ペア 100** | 15/15 |

10日目には全員が上限に張り付く。**飽和した数値は何も言わなくなる**し、喪も道連れになる ——
affinity が全員100なら、誰が死んでも全員に同じ重さで刺さる。

レートを 0.15 に落とし、離れている間の減衰 0.05 を足して再測定:

| 日 | affinity（最小〜最大） | 友人ペア数 |
| --- | --- | --- |
| 1 | 1.5〜3.4 | 0 |
| 5 | 3.9〜10.2 | 0 |
| 12 | 0〜21.7（移住者が来て最小が0に） | 0 |
| 16 | 9.3〜41.5 | 1/15 |
| 20 | 25.8〜69.3 | **7/15** |

友情が育つのが年の後半になり、ペアごとに差が出て（25 対 69）、移住者はよそ者として始まる。
「仲間が近くにいる」割合も 82% → 16% に落ち、常時点灯のボーナスから**時々の救い**になった。

### 「親しい人がいない」の閾値を友情とは分けた

減速後、友情の閾値（40）を孤独の判定に使うと、**1年のほとんどが孤独**になる。3人が毎日一緒に
働いている植民地に1年間ペナルティを課すのは、その思考が言いたいことではない。
「知り合い」の閾値（12）を別に置き、**誰ともまだ知り合っていない状態**だけを孤独とした。

### 喪は最も重い1件だけ

死者は直近10人まで覚え、affinity に比例した重さで3日かけて消える。**複数の死を積み上げない** ——
1週間に3人失った入植者が、手の打ちようがない理由で1週間ぶっ続けで限界を割るのは、パズルではない。

### 巻き添えで見つかったテストの嘘

特性を2つ足したことで `rollTraits` の抽選プールが 12→14 になり、同じシードでも配られる特性が変わって
世界の展開がずれた。それでセーブ移行テストが1件落ちた ——「v3セーブを移行して400 tick 回すと誰かが
経験を得る」。

調べると、**旧コードでもその400 tickで得ていた経験は合計5ポイント**だった。植民地にたまたま残っていた
仕事の切れ端に乗っていただけで、世界が少しずれれば0になる。梯子を登れることを確かめたいなら、
**目の前に段を1つ置く**必要がある ── 移行後に伐採を指定してから回すように直した。

## 特性（トレイト）

スキルが「その人が何をしてきたか」なのに対し、特性は「その人がどういう人か」で、生涯変わらない
（`src/core/traits.ts`）。12 種を6つの排他グループに分けてあり、早熟と晩成が同時に付くことはない。
だいたい2つ、1割は無特性で、全員が特別な植民地は誰も特別でないため。

特性はすべて **既存の数値への乗数** として実装してある。新しい仕組みを一切増やさないので、組み合わせが
特殊ケースの山にならず、特性ゼロの入植者は特性導入前とまったく同じ挙動になる（乗数の積が 1）。

| 特性 | 曲げる数値 |
| --- | --- |
| 早熟 / 晩成 | 経験値の入り |
| 勤勉 / 悠長 | 作業速度（スキルとは別に乗る） |
| 大食い / 小食 | 空腹の進み |
| 眠り上手 / 落ち着かない | 睡眠の回復・消耗 |
| 頑健 / 虚弱 | 休息中の治癒 |
| 楽天家 / 悲観家 | 気分の振れ幅（良い出来事も悪い出来事も） |


## スキル

入植者は仕事の列ごとに熟練度を持つ（`src/core/skills.ts`）。実際に手を動かした tick だけが経験になり、
レベルが上がるほど同じ仕事が速く終わる（レベル10で1.8倍、`WORK_TICKS` 自体は変えない）。
`deconstruct` は建設の列で扱うため、解体も建設の熟練度を伸ばす。

開拓者と移住者は世界シードから決まる得意分野を2つ持って現れるので、「この人は狩人」「この人は大工」が
最初から成り立つ。レベルが上がるとイベントログに残り、入植者パネルに上位3つが並ぶ。


## 気分（ムード）

入植者は「二本のゲージを満たせば同じ速度で働く機械」ではなくなった。ベッドがあるか、倉に食料が
どれだけあるか、床が張ってあるか、いま冬か——植民地の状態がそのまま **気分** になる
（`src/core/mood.ts`）。

気分は **保存しない**。毎回その場の state から導出するので、セーブの移行が要らず、実態とずれることが
なく、そして何より **常に内訳を説明できる**。入植者パネルのバーにカーソルを置くと、その数値を作った
思考が符号つきで並ぶ。プレイヤーが直せるのはバーではなく思考の側だからである。

| 思考 | 点 |
| --- | --- |
| 餓死しかけ / 空腹 | -30 / -10 |
| 立ったまま寝そう / 眠い | -18 / -8 |
| 重傷 / 痛む | 体力に比例して最大 -25 |
| 追われている | -20 |
| 地べたで寝た / 自分のベッドがない | -8 / -5 |
| 倉が空 / 倉が満杯（5日分以上） | -12 / +8 |
| 満腹 / よく眠れた | +6 / +6 |
| 床が張ってある | +4 |
| 冬が長い | -6 |

気分の使い道は2つある。**作業速度**は 40〜70 のあいだ完全に平坦（＝気分導入前とまったく同じ挙動）で、
下回ると最大 0.6 倍まで落ち、70 を超えると最大 1.1 倍まで上がる。そして 20 を切ると入植者は
**仕事を放り出す**（`activity: brooding`、400 tick）。この放棄状態だけは保存する。食事を一口与えた瞬間に
復帰してしまっては、プレイヤーは何が起きたのか一度も見ないまま終わるからである。

放棄中でも空腹と睡眠は優先される（拗ねて餓死はしない）。ラベル（安定／不安定／…）の境目は
仕組みの境目とぴったり一致させてあり、表示が変わったときには必ず挙動も変わっている。


## スキルで仕事を割り当てる

スキルは作業速度を変えるだけで、**誰がやるかには一切影響していなかった**。全員が全列で同じ優先度2から
始まり、プレイヤーが1セルずつ手で埋めない限りそのままなので、最高の木こりが運搬をしていてもおかしくない。
仕事表に「スキルで割り当て」ボタンを追加した（得意な上位2列を最優先にする）。

**これは無料の改善ではない**。当初「仕事が速く終わる」とテストに書いたが、実測すると逆だった —— 4シードで
40本の木を指定し700 tick 走らせたところ、ボタンありでは8本・22本が残り、なしでは0本だった。誰かの得意列を
最優先にすることは、**それ以外の列（プレイヤーが今出した指示を含む）を相対的に格下げする**ことに等しい。
これは優先度表という仕組みに内在するもので、バグではない。テストとボタンの説明文の両方に、この取引を
そのまま書いてある。


## 入植者シート

一覧は「ざっと見る」ためのものなのでスキル上位3つしか出さない。スキルと特性が入った以上、
「この人は結局何が得意で、なぜ遅いのか」という別の問いが生まれるので、入植者をクリックすると
専用パネルが開くようにした（`src/ui/ColonistDetail.tsx`）。

7スキル全部をレベルと**次レベルまでの進捗%**付きで表示し、特性は効果の説明文ごと出す。さらにスキルと
特性を掛け合わせた実効速度（例: `1.61x at construction`）を1行にまとめる — プレイヤーが実際に感じるのは
その積であって、内訳ではないため。`describeTile` と同じくフラットな文字列配列を返す純粋関数なので、
毎 tick 走るセレクタでも `useShallow` が効く。


# 建築と物流

## 壁の建設位置

ブループリントのタイルは壁が立つ瞬間まで通行可能なので、**建てた本人がその上に立ったまま壁を完成させて
自分を封じ込めていた**。通行不可タイルの上にいるエンティティはリージョンラベルを持たず、`isReachable` は
まず「自分の居るリージョン」を問うので、その瞬間から地図上のあらゆる仕事が到達不能に見える。
6枚の壁のうち3枚が建ったところで3人全員が閉じ込められ、仕事が queued のまま植民地が停止していた。

修正は2段構え。完成後に通行を塞ぐ建築（`BLOCKS_MOVEMENT`）は**隣接タイルから建てる**ようにし、
それでも完成の瞬間にタイル上に居合わせた者（別の入植者や動物）は隣の通行可能タイルへ押し出す。
床のように塞がない建築は従来どおり足元に敷ける。


## 損傷と修理

これまで `BUILDING_HP` は誰も減らせない飾りだった。獲物に手が届かない捕食者が、間に立つ建築を齧るように
した（`gnawStructure`）。齧りは通常の噛みつきより弱く遅く、しかも他の追跡と同じ `PREDATOR_PURSUIT_TICKS`
で打ち切られる。1回の襲来で入る傷はせいぜい十数回分なので、**木の扉は3回ほどの襲来に耐え、石壁はまず落ちない**。
柵は「無敵の壁」でも「形だけ」でもなく、維持する対象になる。

損傷は**地図上でも**分かる。建築スプライトを4段階で赤側に着色する（`src/render/damage.ts`）。
段階を4つに量子化しているのは、レンダラがキーの変化でのみスプライトを作り直すため —— HP 1点ごとに
キーが動くと、見て分からない差のために毎回の噛みつきで再構築が走る。ブループリントは自前の色を持つので
対象外（1HP で生成されるため、そのまま適用すると計画が全部真っ赤になる）。

損傷した建築には `repair` ジョブが自動生成される。解体と同じく独立した列は持たず **建設列** で走るので、
建設を切れば修理も止まる。資材は不要（修理は作り直しではなく手当てで、資材搬入を挟むと2つ目の
ブループリント機構になってしまうため）。損傷はアラートにも出る（40%未満で critical）。


## 貯蔵ゾーンのフィルタ

貯蔵ゾーンは資源ごとに受け入れの可否を持つ（選択パネルのチップで切り替え）。ゾーンは牧場と同じく
**場所**になり、隣接しないゾーンは別々の在庫になる（壁際の薪置き場と寝床脇の食料庫を別に運用できる）。
牧場は `food` だけを受け入れる＝飼い葉置き場であり、以前のように薪や石が家畜の間に積まれることはない。

フィルタを絞っても既存の在庫はその場から消えない。「そこに置いてはいけない荷物」になるだけで、
次の tick から通常の運搬ジョブとして運び出される。


# UI

## 次にやること（目標パネル）

囲い・手懐け・貯蔵フィルタ・修理・スキルと仕組みは増えたが、**ゲーム内にそれらの存在を伝えるものが
何も無かった**。ツールバーはボタンを並べるだけで、なぜ押すのかは言わない。

`src/core/goals.ts` は「植民地が欲しがるもの」を8項目、およそ欲しがる順に返す。全て**現在の状態から
導出**していて、プレイヤーの操作履歴は使わない —— 履歴で消し込むと、ベッドが無くなった後も達成済みの
ままになる。状態から導けば未達に戻り、パネルは「で、今なにを？」に答え続けられる。

各項目には**実際の道具名を含むヒント**を付けてある（`Build > Pasture`、`Animals > Tame`、
`Accepts チップ` など）。パネルは達成が進めば1行に畳める（`3/8 — spring · next: Quarry some stone`）。


## ミニマップ

60×60 の地図は画面に収まらないため、右サイドバー上部に 1 タイル = 1 ピクセルの全体図を置いた
（`src/ui/Minimap.tsx`）。地形・建築・牧場・指定に加えて、入植者（白）・捕食者（赤）・家畜（黄）・
野生動物（茶）が点として乗る。クリックでカメラがそこへ飛び、白枠が現在の表示範囲を示す。損傷した建築は赤で描かれるので、
齧られている柵をアラートだけでなく地図上でも見つけられる。

描画は 60×60 の `ImageData` に直接書き込んで CSS で拡大する（`image-rendering: pixelated`）。
カメラ位置はレンダラからストアへ報告するが、タイル単位に丸めた上で変化が無ければ更新を捨てるので、
静止中のカメラが毎フレームの再描画になることはない。


## 空間 —— マップ4倍と画面の再配置（フェーズ6）

設計案（[design-phase6-space.md](design-phase6-space.md)）が「別々の要望に見えて同じ一つの事実の裏表」
と書いたとおりに実装した —— 植民地が最初の枠に収まらなくなった、という一つの事実である。

### 寸法を定数から `GameState` へ移したのが作業の中心

`MAP_WIDTH` / `MAP_HEIGHT` は12ファイルから参照されるモジュール定数だった。値を 120 に書き換えるだけなら
1行だが、それだと**既存のセーブが全部読めなくなる** —— 保存された 60×60 のタイル集合に対して、
領域ラベルの `Int32Array` も A\* の添字計算も 120 幅で走る。8 章の規則に照らせば拒否するしかなく、
拒否とはプレイヤーに植民地を捨てさせることである。

そこで `state.width` / `state.height` を持たせ、定数の方を **`DEFAULT_MAP_WIDTH` / `DEFAULT_MAP_HEIGHT`
に改名した**。改名は意図的で、これがあると**全参照箇所がコンパイルエラーになる** ——
「1箇所だけ直し忘れて、そこだけ古い寸法で走る」という、静かに間違う壊れ方を型の側で塞げる。
これは 4 章の「導出できるものは保存しない」に反しない。地図の寸法は導出値ではなく、
`worldSeed` と同じ**その世界を定義する事実**である。

`SimContext` にも `width` / `height` を持たせた。領域ラベルは寸法で添字を作るので、
**別の寸法の state を渡された context は静かに間違う**（落ちない）。同一プロセスで2つの寸法の
セーブを開くのは普通の操作なので、`roundtrip.test.ts` に「60 と 120 を入れ替えて読み直す」検査を足した。

### 密度化がこの拡張の実質的な中身

| 項目 | 60×60 | 120×120（密度化の前） | 120×120（後） |
| --- | --- | --- | --- |
| ベリー / 1000タイル | 7.2 | 1.8 | **7.2** |
| 霜花 / 1000タイル | 3.9 | 1.0 | **3.9** |
| 動物 / 1000タイル | 10.6 | 2.7 | **10.6** |

定数のままだと「広い世界」ではなく「同じ植民地が置かれた、4倍がらんとした世界」になる ——
歩く距離だけ伸びて手に入るものは変わらない。`perArea`（面積比）と `perSpan`（短辺比）の2つを置いて、
ベリー・霜花・野生動物の頭数と、捕食者／野生動物／インシデントの湧き出し距離をそこに通した。

**狼の上限だけは通していない。** シナリオごとの上限（1 / 2 / 4）は面積ではなく**難易度**の表明で、
機械的に4倍にすると `Hard frontier` が狼16頭になる。密度で置くか難易度で置くかは種別ごとの判断で、
捕食者は難易度側に置いた。

### 性能（実測）

| | 60×60 | 120×120 |
| --- | --- | --- |
| 1 tick | 1.0 ms | **6.4 ms** |
| セーブ（JSON） | 0.48 MB | **1.95 MB** |

設計案 2 章の見積もり（0.732 → 2.791 ms）より両方とも高い。理由は2つあって、
**設計案を書いた時点よりコードが増えている**（マナ層・襲撃・交易・幻想層がその後に入った）ことと、
測定がテストランナー内であること。予算 200 ms に対して 3.2% なので受け入れ条件（5% 以内）は満たすが、
10倍速では 1 コアの約 32% になる（60×60 では 5%）。**設計案が「性能は制約にならない」と言った結論は
変わらないが、余裕は見積もりほど大きくない。** 4倍のタイルに対して 6.4 倍なので、
タイル数に線形でない項がどこかにある —— 詰まったら最初に見るのは、毎 tick 全タイルを走査する
`runJobGenerator` と、`updateTile` が最初の書き込みでタイル表全体を複製する copy-on-write である。

### テストは 60×60 のまま回す

これは判断であって手抜きではない。理由は2つで、**2つ目のほうが重い**。

1. 4倍の地図は4倍の実行時間。全件は現在 **11 分**（57ファイル・412件）で、
   ハーネスごと 120×120 にすれば数十分になる。走らなくなったテストは無いのと同じ
2. **この notes の実測値はすべて 60×60 で取ったもの**である。ハーネスが黙って広がると、
   1年放置の食料も、霜花の +278 も、越冬した頭数も、**一行も書き換えないまま全部が無効になる**。
   「過去の測定を消さない」という規則は、消さないだけでなく**意味を変えない**ことでもある

出荷される寸法は3つのテストが受け持つ —— `longrun` が 120×120 で1年、`chaos` が 120×120 で不変条件、
`roundtrip` が2つの寸法を同一プロセスで往復させる。

**この判断は、一度これを外して壊してから固めた。** 既定を 120×120 にした直後の全件実行で7件落ちた。
原因は全部同じで、**ハーネスを通さず `generateWorld({ seed })` を直接呼んでいたテスト**が
黙って 120×120 になっていた —— 拠点の中心が (30,30) から (60,60) へ動くので、
「拠点の周り14タイル以内に森が10タイル以上ある」といった地形の主張は、
**別の地図の別の場所**を見て落ちる。1年回すテストは4倍の時間で時間切れになった。
`testWorld`（`testUtils`）を置いて、世界を自前で作るテストもすべてそこを通るようにした。

ついでに1つ直した。`season.test.ts` の越冬テストは食料の合計を**毎 tick** 数えていて
（1年＝60,000 回、毎回すべてのスタックを走査）、それがこのテストの実行時間のほとんどだった。
`longrun` と同じく 200 tick ごとの標本に変えた —— 秋の山と冬の谷は、1日の15分の1では動かない。

### 画面 —— 3つの行き先に振り分けた

11個のパネルが幅 300px の1列に積まれ、どれも畳めなかった。設計案の規則
「**常に見たいが小さいものは隅へ、見たいときだけのものはサイドバーで畳む**」をそのまま実装した。

- **左上オーバーレイ**: 資源とアラート。アラートは元から0件で `null` を返していたので、
  隅に移した結果「危機が無いときは何も描かれない」が自然に満たされた
- **右上オーバーレイ**: ミニマップ
- **サイドバー**: 目標・入植者・仕事・動物・ログ。それぞれ畳める

**選択詳細の3パネルは1枠にした。** `ColonistDetail` と `AnimalDetail` は store 上で**排他**
（`selectColonist` は選択中の動物を消し、`selectAnimal` は逆をする）なのに、独立した2枠として
縦に並んでいた。同時には決して埋まらない箱が2つ、というのは1つ分の場所を無駄にしている。

**折り畳みの状態は `localStorage` に置き、`GameState` には入れない。** 入れるとセーブに載り、
`schemaVersion` の移行対象になり、他人のセーブを読むとパネルの開閉まで付いてくる。
これは見落とすと後から直しにくいので、**テストで機械的に固定した** ——
`JSON.stringify(state)` に UI の語が1つも出てこないこと。

既定の開閉は「全部開く」ではなく**状態から決める**（目標パネルと同じ考え方）——
入植者が3人以下なら仕事優先度表は畳んでおく、家畜が0頭なら動物パネルは畳んでおく。
一度プレイヤーが触ったパネルは、以後その選択が勝つ。


# 測ってわかったこと

## 1年放置の実測

個々の機能は数百 tick の単位で検証しているが、それらが噛み合った状態で長期に成立するかは別問題なので、
`src/core/longrun.test.ts` が無操作のまま1年（20日 = 60,000 tick）を回す。実測値（seed 8101）:

| 時点 | 人口 | 食料 | 動物 | 最高スキル |
| --- | --- | --- | --- | --- |
| 5日目（夏） | 3 | 718 | 28 | 5 |
| 10日目（秋） | 5 | 1448 | 30 | 6 |
| 15日目（冬） | 6 | 1506 | 30 | 7 |
| 20日目（春） | 6 | 934 | 28 | 7 |

入植者の死亡ゼロ、餓死ゼロ、失敗ジョブの滞留なし、1 tick あたり 0.59〜0.62 ms（予算 200 ms）。
冬に食料が 1506 → 934 まで落ちて春に回復するので、越冬の緊張は残しつつ詰まないバランスになっている。

この計測で分かったのは、既定の植民地が **1年で開始時の貯蔵庫をほぼ埋め切る**（20タイル × 75 = 1500 に対し
最大 1497）ということ。貯蔵が満杯になると運搬係は置き場所を見つけられなくなり、荷物は落ちた場所に
留まるが、これまでその理由はどこにも表示されなかった。満杯・行き場なしをアラートに追加した。


## ランダム操作による不変条件テスト

上記の壁のバグは「スクリーンショットを眺めていて3人が idle なのに queue があるのに気づいた」ことで
見つかった。それは運であって再現性のある方法ではないので、一般形を用意した（`src/core/chaos.test.ts`）。

シード付き乱数で任意のプレイヤー操作（指定・建築・キャンセル・ゾーン・動物指定・優先度・フィルタ）を
流し込み、各ラウンドの後に**どんな状態でも成り立つべきこと**を検証する:

- 入植者は必ず通行可能なタイルの上にいる
- 予約・ジョブ・入植者の3つの記録が常に一致する
- 建築とタイルが相互に指し合っている／アイテムは自分が載っているタイルの一覧に入っている
- ゾーンは実在するタイルだけを覆い、実在する資源型だけを受け入れる

主張は「植民地がうまくやっている」ではなく「**状態が破綻していない**」に限定してある。好みを主張する
fuzzer は自分の意見しか見つけないため。

**この網が実際に機能することは、壁の修正を一時的に戻して確認した** —— 戻すと2つのシードで
`expect(tile.walkable).toBe(true)` が落ち、戻し直すと通る。

加えて「エンジン自身が『取れる』と言っている仕事の隣で入植者が遊んでいないか」という**停滞の検査**も
入れてある。判定には `candidatesFor`（割り当て段階そのもの）を呼ぶので、テスト側に書き写した規則が
本体からずれて検出しなくなる、という事故が起きない。

ただし**この停滞検査は壁のバグを捕まえない**。同じ手順（修正を戻して実行）で確認したところ通ってしまう。
壁に封じられた入植者はリージョンを持たないので `isReachable` が全ジョブを弾き、エンジンは正直に
「あなたに出来る仕事はありません」と答える —— 壊れていたのはキューではなく視点の方だった。
あれを捕まえるのは上の「通行可能タイルの上に居ること」の方で、停滞検査が拾うのは別種の詰まり
（取れるはずの仕事が誰にも取られない）である。


## テストヘルパーの「黙って短い配列を返す」問題

2イテレーション続けて「何も検査していないテスト」が見つかった。原因はどちらも同じ形で、
**ヘルパーが要求より短い（あるいは空の）タイル配列を黙って返す**こと —— 使えないタイルを渡された
アクションは受け取った state をそのまま返すので、「何も変わらない」という主張が、検査対象とは
無関係な理由で真になる。

`tilesWithTerrain` / `nearestTilesWithTerrain` は要求数に足りなければ**例外を投げる**ようにした
（短い配列はテストの破損であって、静かに進んでよい状況ではない）。

牧場を置くヘルパーは5ファイルに同じ実装が写されていて、どれも「camp の隣の固定矩形」だった。
矩形に木やベッドが1つ入るとそのタイルが落ち、残りは連続しなくなり、ドラッグは牧場を2〜3個作る。
その後「その牧場」を取るテストは、最初に見つかった方を掴んで、無関係な理由で通ったり落ちたりする。
`placePastureNear`（`testUtils`）に集約し、**本当に空いているブロックを探索し、1回のドラッグが
1つの囲いになったことを検査**するようにした。


## 言語（フェーズ9）

UI を英語直書きから2言語辞書（en / ja）に移した。設計案は
[design-phase9-language.md](design-phase9-language.md)、現況は [design.md](design.md) 11 章。

**ライブラリを入れなかった。** i18next 等が解く問題（複数形規則・遅延読み込み・翻訳ワークフロー）は
2言語・184キー・全文字列同梱のこの規模では発生しない。代わりに `Strings` インターフェースが
全キーを列挙し、en と ja の両方がそれを実装する —— 訳し漏れは実行時ではなく
コンパイルエラーで捕まる。パラメータ付き文言は関数にし、英語の単複（`plural()`）は
en 辞書の実装詳細に閉じた。

**コアは文章を作らない形にした。** アラート・目標・状態メッセージは `{key, params}` を返し、
文章は表示の瞬間に辞書から導出する。導出値なので、**既に出ている警告も言語切替で即座に翻訳される**。
ログだけはセーブに入る文章だったので、`LogEntry` を `{tick, kind?, key, params}` に構造化した
（LogKey 48種）。これは翻訳の都合ではなく「導出できるものは保存しない」の適用 ——
保存すべきは出来事で、文章はそこから導出できる。

**過去のログは翻訳しない。** v15→v16 の移行は旧エントリを `{key: 'legacy', params: {text}}` に
包んで原文のまま表示する。保存済みの英文を構文解析して出来事に逆変換する処理は書けるが必ず漏れる。
リングバッファ100件なので、legacy 行は数日のプレイで自然に押し出される。

**言語設定は `GameState` に入れない。** 言語を変えてもシミュレーションは 1 tick も変わらないので、
`localStorage`（`simworld.language`）に置いた。セーブは言語に依存せず、同じセーブを両言語で開ける。

**実測**（`npm run build:single`、各1回）:

| | バイト |
| --- | --- |
| 導入前（HEAD） | 839,617 |
| 導入後 | 872,887 |
| 増分 | **+33,270（+4.0%）** |

2言語ぶんの辞書・キー化・移行を全部足して +33 kB。フォントは同梱していない
（システムフォントで日本語が出ない環境は現実的にほぼ無く、単一 HTML に日本語フォントを
埋め込むとサブセット化しても数百 KB 増えるため。実ビルドを両言語で目視して問題が
出てから判断する、が設計案 5 章の結論だった）。


## 鉱石と建築メニュー（フェーズ10 段階A・C）

設計案は [design-phase10-ores.md](design-phase10-ores.md)、現況は [design.md](design.md) 11 章。
採掘産出の分岐2箇所（`mine` ジョブと自動採掘機）を `VEIN_YIELD` の1枚の表にし、鉄はその表への
1行として入った。素の岩は表の行ではなくフォールバック（stone 20）——表が知らない地形でも
「黙って何も出ない」を作らないため。

**鉄の分布（60×60・200シード、実装時）**: 設計案の出発点しきい値 0.55 は結晶の 3.1 倍で目標帯
（2〜3倍）を超えたため **0.57** に調整。調整後は中央値 114 タイル＝結晶（40）の **2.85 倍**、
鉄ゼロの世界 0/200。結晶判定が先に走るので、結晶の分布は鉄の導入前後で完全一致（200シード照合）。

**フェーズ6（120×120 既定）統合後の再計測（200シード）**: しきい値 0.57 のまま比率は帯の中に
収まったので、**再調整はしていない**。結晶の分布はフェーズ6 実装時点（main）の生成結果と
200シードで完全一致（鉄の判定は結晶判定の後にしか走らないため）。

| | min | p10 | 中央値 | 平均 | p90 | max | ゼロ世界 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 鉄 | 138 | 343 | **528** | 550.2 | 823 | 1,144 | 0/200 |
| 結晶 | 21 | 102 | **191** | 208.2 | 336 | 642 | 0/200 |

中央値の比は **2.76 倍**。面積4倍で本数もほぼ4倍になっており、ノイズしきい値方式は
密度換算（フェーズ6 3.2）を書かずに地図の拡大へ自然に追従した。

**年単位テストの種の振り直し。** 鉄鉱脈は岩の約2割の地形ラベルを変えるため、同じ種でも
1年放置の成り行き（狼の当たり外れ）が変わる。統合前の main でも無操作の1年は種によっては
開拓者を失う（例: 種 743 は main 単体でも狼に1人取られる）——「無操作でも必ず全員生き残る」は
元々どの側の主張でもなく、テストは代表の種を固定しているだけ。地形が変わって外れを引いた
2本（season 727 → 733、longrun の出荷寸法）だけ、成立する種に固定し直した。

**移行番号の統合。** フェーズ5・6（main 側）とフェーズ9・10 段階A（作業ブランチ側）が
それぞれ v15 から移行を積んでいたため、統合時に main の番号を正とし、ログ構造化を
**17→18**、鉄の後付けを **18→19** に振り直した（`SCHEMA_VERSION = 19`）。main 系列の実セーブは
どの版でも全段を正しく通る（v15 以前の文章ログは 17→18 が包む）。壊れるのは統合前の
作業ブランチだけが書けた開発用 v16〜v17 セーブのみで、これは出荷されていないので受け入れた。


## 鉱石と家具（フェーズ10）

段階B（家具5種）を実装し、フェーズ10 が完結した。設計案は
[design-phase10-ores.md](design-phase10-ores.md)、現況は [design.md](design.md) 11 章。
鉱脈の一元表・鉄の分布（60×60 実装時と 120×120 統合後の 200 シード表）・移行番号の統合と
開発用 v16〜v17 セーブの割り切りは、直前の節「鉱石と建築メニュー（フェーズ10 段階A・C）」に
記録済みで、ここでは繰り返さない。

**鉄の分布の再確認（120×120・200シード、段階B実装後のコードで再計測）**: 上の節の表と
**完全一致**した（鉄 min 138 / p10 343 / 中央値 528 / 平均 550.2 / p90 823 / max 1,144、
ゼロ世界 0/200。結晶 min 21 / p10 102 / 中央値 191 / 平均 208.2 / p90 336 / max 642、
ゼロ世界 0/200。中央値比 **2.76 倍**）。段階Bは生成に一切触れていないので当然だが、
「触れていないはず」を測って確かめた。

**家具は新しい機構を1つも増やさなかった。** 5種とも既存の数値への接続で済み、
`GameState` のフィールド・ニーズ・ジョブ・`ResourceType` の追加はゼロ:

- 食卓・腰掛け・石像は**魔力灯の +5 と同じ走査**に相乗り。`factsFor`（mood.ts）の建物ループは
  1本のままで、半径判定のループを別に増やしていない（設計案 8 章の性能条件）。
  食卓・腰掛けの収集は食事中の入植者に対してだけ走る
- 戸棚は**特性 `heavySleeper` と同じ乗算スロット**。×1.15 は特性の ×1.35 より弱く、
  「家具は資質を超えない」という 7.2 の序列を守る。複数の戸棚は重ねない（最初の1つで打ち切り）
- 安楽椅子は**既存 `relaxing` 活動の対象拡張**。activity のフィールド名は `hearthId` のまま
  （改名するとセーブ移行が要る。逃走の `fromId` と同じ、名前が実態より狭くなった例として
  型定義にコメントを残した）

**実測の効果差**（`furniture.test.ts`。条件は各テストに固定してある）:

| 家具 | 測り方 | 実測 |
| --- | --- | --- |
| 戸棚 | ベッドで 300 tick 睡眠、特性なし1人 | 睡眠回復 33.3 → 38.3（**×1.150**、ちょうど乗数どおり） |
| 安楽椅子 | 60 tick の休息を炉端と比較、友人なし | 娯楽回復 40.0 → 52.0（**×1.30**） |
| 食卓 | 半径2（チェビシェフ）内で食事中の思考 | +3。隣接（チェビシェフ1）に腰掛けがあると +4 |
| 石像 | 半径4内の入植者の思考 | +3。半径5では付かない |

半径は**すべてチェビシェフ距離**（正方形）にした。魔力灯はマンハッタン距離だが、
「食卓を囲む」「像が見える部屋」はプレイヤーが盤面から読む正方形の方が説明しやすく、
腰掛けの「隣接」（チェビシェフ1）と同じ距離関数で全部が書けるため。

**思考はプラスのみ**（設計案 4.3 のとおり）。導出値なので、家具を解体した瞬間に次の導出から
思考が消え、掃除するべき保存状態が存在しない —— これもテストで固定した（tick を1つも回さずに
建物を消して思考が消えることを確認）。設計図は5種とも無効果。

**メニューの最終形**: 構造 6 / **家具 7**（ベッド・炉端 + 新5種）/ 魔力 5 / 区域 3。
表示ボタン数の上限は家具の 7 で、設計案 5.2 の想定どおりカテゴリ切替の頭打ちがそのまま成立。

## 研究と職業（フェーズ12）

設計案は [design-phase12-research.md](design-phase12-research.md)、現況は
[design.md](design.md) 11 章。**新しい機構は実質ゼロ**——研究台は建築の並列テーブルに1行、
`research` ジョブは `farm` と同じ形（対象の建物へ行き `WORK_TICKS` を積む）、資源要求テック
（晶学）は魔導炉の燃料補給と全く同じ形で成立させた。建物の `requiredResources` はブループリント
の材料を数える場所だったが、finished な研究台に同じ場を再利用し、`isJobStillValid` の haul 分岐に
`researchDesk` の1ケースを足しただけで「届くまで進捗が始まらない」が書けた。新しい「届いた量」を
数えるフィールドは増えていない。

### 肩書きを保存フィールドにしなかった理由

`Colonist.profession` のような保存フィールドは採らなかった。理由は設計案 4.2 に書いたとおり2つ:
保存された導出値は実態と食い違いうる（優先度表とスキルという実態がすでにあるのに、農夫と自称する
入植者が実際には建築ばかりしている、という状態を作れてしまう）、そしてスキルの速度ボーナス
（レベル×8%）と職業ボーナスを両方持たせると同じことを二重に言うことになる。代わりに
`titleSkillOf`（`src/core/skills.ts`）という純粋な導出関数1つと、優先度表を一括で書き換える
UI ボタン（`applyProfession`）1つに分けた。前者はシミュレーションから一切読まれない
表示専用の値で、後者が保存するのは適用結果の `workPriorities` だけ。研究を続けた入植者の
肩書きが自動で「研究者」に変わることは、この分離の直接の帰結としてテストで固定してある
（`research.test.ts`「follows a colonist who took up research」）。

### 研究の周期を実測して、コストを2.5倍に上げた

設計案 6 章の見積もりは「木工の心得（300進捗）は入植者1人・優先度1で約1日」だった。
ヘッドレスで測ると、これは大きく外れていた。

**測定条件**: 3人の標準シナリオの植民地。研究台は建てる時間を測定から除くため直接設置。
1人だけ `research` 列を優先度1に上げ、他の列は既定のまま（本人も含め通常どおり空腹・睡眠で
中断されうる）。木工の心得（当時のコスト300）が解禁されるまでの tick を5シード
（401, 403, 407, 409, 419）で測った。

| 元のコスト（300） | 実測 |
| --- | --- |
| 完了までの日数（5シード） | 0.28 〜 0.41 日、平均 **0.36 日** |

見積もりの1日の1/3ほどで終わっていた。理由は単純: novice（速度係数1）が
`TECH_PROGRESS_PER_CYCLE`（10）を `WORK_TICKS.research`（50 tick）ごとに積むと、
300進捗は 1,500 tick（0.5日）の連続作業で終わる計算になり、しかも空腹・睡眠のしきい値
（55・75、それぞれ概ね1,300〜1,500 tick 付近）に達する前に終わってしまうケースが多く、
中断による遅れがほぼ乗らなかった。

CLAUDE.md の「測った値と食い違ったら直すのは主張の側」に従い、**4テックとも見積もりの
2.5倍**に引き上げた（木工・石彫 300→**750**、鉄工 600→**1500**、晶学 500→**1250**。
比率は元のまま保持）。同じ条件で再測定:

| 新しいコスト（750） | 実測 |
| --- | --- |
| 完了までの日数（5シード、同シード） | 0.83 〜 1.11 日、平均 **0.98 日** |

見積もりの「約1日」に実測が合った。テック間の比率（木工:鉄工 = 1:2、晶学はその中間）は
変えていないので、鉄工が木工よりおおむね2倍かかるという設計案6章の意図もそのまま成立している。
5シードは小標本であり、これ以上の精度を主張しない。

### セーブ移行

`schemaVersion` 19 → 20。追加は設計案5章のとおり `research` の1フィールドのみ
（`current: null`・`progress` は4テックすべて0・`unlocked: []`）。全入植者に
`workPriorities.research = 3`・`skills.research = 0` を補う。3.1（既存の建築15種＋食卓・腰掛けは
ロックしない）により、旧セーブを解禁済みにする救済は不要——実際、`research.test.ts` の移行テストは
「何も再ロックしない」ことだけを確認し、`unlocked` は空のまま検証している。

## バイオーム（フェーズ11 段階A）

設計案は [design-phase11-worldmap.md](design-phase11-worldmap.md) 3章、現況は
[design.md](design.md) 11章。実装したのは段階Aのみ（4バイオームの生成レバー・結晶下限・毎日の

### 実装の形

design-next.md 提案1(a) をそのまま実装した——`enforceCrystalFloor`（`worldgen.ts`）は生成の
最後に一度だけ走り、既存の `stone` タイルから「岩に囲まれた深さ」→「石ノイズの値」→「座標」の
順で決定的に候補を並べ、必要数だけ `crystal` に変える。乱数は使わない：ノイズ値そのものが種から
決まっているので、候補の並びと選択がすでに種依存である。マイグレーション v9→v10（結晶の後付け）
と同じ「既存の地形から種で埋める」という形の3例目（v18→v19 の鉄が2例目）。

`ResourceType` / `JobType` / `BuildingType` は増えていない。`GameState` への追加は `biome`
1フィールドのみ（`schemaVersion` 20 → 21、旧セーブは `meadow` を補う1段）。毎日効くレバー
（`forage` 回復・森再生・野生動物補充・灯の気分）はすべて既存の数値への乗数で、新しいループは
増えていない——`biomeOf(state)` は `scenarioOf(state)` と同じ形の1関数で、既存の走査（`spawnWildlife`
の種ループ、`regrowForage` の1回のステップ計算、`regrowForest` の1回のロール閾値）が読む値を
差し替えるだけ。

## 世界地図と部族（フェーズ11 段階B・C）

設計案 [design-phase11-worldmap.md](design-phase11-worldmap.md) の2章・4章・7章を実装した。
実装との差分（生成レバーの詳細な形など）は同ファイル末尾の実装メモにある。ここには
測ったものだけを書く。

### ワールドマップの導出（`src/core/worldmap.ts`）

16×16セル。世界レベルの値ノイズ2枚（湿り気 `moisture` ・険しさ `ruggedness`、スケール4セル）の
閾値からバイオームを決める4分岐——`manaheath`（湿り気>0.7 かつ 険しさ>0.55）→ `crag`
（険しさ>0.6）→ `deepwood`（湿り気>0.55）→ `meadow`。ローカル地形生成（森・岩ノイズ）と
同じ`valueNoise2D`を1段上のスケールで使うだけで、新しいアルゴリズムは無い。

**隣接セルの一貫性**（design-phase11-worldmap.md 2.3「隣のセルは似たバイオームになる」）:
5世界シード・横方向の隣接ペア計1,200組で測定。**同じバイオームである割合は実測79.0%**
（同じバイオーム分布をセル位置にランダムシャッフルしたときの基準値34.1%に対して）。
ノイズがハッシュではなく実際に空間相関を持っていることの直接の裏付け（`worldmap.test.ts`
に閾値付きの回帰として残している——シャッフル基準の1.15倍を下回らないことを検証）。

**200世界シードのバイオーム分布**（`worldMapGrid(seed)`、種1〜200、`seed*7919+13`の形で分散）:
平均 草原101.5・深森61.0・岩尾根73.0・晶土20.5セル（256セル中）。**晶土が1セルも無い世界が
2/200**（岩尾根・深森はどちらも0/200）——ローカル地形の結晶ゼロ問題（design-next.md 1.1、
60×60で3/200）と同じ形の薄い裾が世界地図の側にも残っている。この段階では下限保証を
足していない（部族に実体は無く、`tribalInfluence` は「灯持ちがどこにもいない世界」を
「距離Infinity、全乗数1.0」として素通りするだけで破綻しない——4.2章「どの圏からも遠い」の
延長として扱った、design-next.md への新規追記はしていない）。

`cellSeed(worldSeed, x, y)` は256セット中250個以上が異なる値になることをテストで確認
（31bit空間へのハッシュなので、ごく少数の衝突は許容している）。

### `worldSeed` と `cellSeed` の使い分け

Stage A は `seed` 引数をそのまま地形ノイズに渡していた。Stage B は `worldCell` が渡されたとき、
地形ノイズ・コロニストの背景・ベリー/霜花の散布・初期野生動物の乱数源を
`cellSeed(worldSeed, x, y)` に切り替え、`state.worldSeed` 自体（インシデント・交易の乱数源）は
変えない。結果、同じ世界の異なるセルは地形もコロニストも違うが、インシデントと交易の
「毎日の運」の乱数系列自体は世界シード単位で共有される——これは意図的な単純化で、
仕様が要求するのは「同じセルの再選択で同じ地図になる」ことだけであり、
「同じ世界の異なるセルで異なる災害暦になる」ことまでは要求していない（8章に記載なし）。

### 部族の勢力圏とマルチプライヤ（`src/core/tribes.ts`）

勢力圏は**その部族が好むバイオームのセル集合そのもの**（灯持ち＝晶土、森歩き＝深森、
渇き衆＝岩尾根）。別のノイズ層は持たない——設計案4.2の「同じ世界ノイズから導出される」を
そのまま満たす最も単純な実装で、勢力圏を描くための第2のノイズを足す必要が無い。

距離はチェビシェフ距離（セル単位）。「近い」の閾値は部族ごとに変えた——渇き衆は
design-phase11-worldmap.md 4.2 の文言「圏内・隣接」どおり距離≦1、灯持ち・森歩きは
「近い」という緩い表現に合わせて距離≦3（見積もり、未調整）。

**距離乗数は毎tickではなく、呼び出し側の関数が実際に使う瞬間に読む純粋関数**
`tribalInfluence(state)` で計算し、`(worldSeed, worldCell)` をキーにしたモジュール内メモ化
1件キャッシュを持つ（`SimContext` には置いていない——`runIncidents` / `runArrivals` /
`runTrade` は `SimContext` を受け取らない関数のままにしたかったため、既存のシグネチャを
変えずに済む形を選んだ）。`worldCell` は生成後は不変なので、キャッシュは実質「開始時に
一度計算」を満たす。

### 測定: 森歩き（移住間隔 3日→2日）

worldSeed=2、`nearAndFarCells` で見つけた最近接セル (6,0) と最遠セル (0,0)。食料を
上限まで積んだ状態で `runArrivals` を1tickずつ回し、最初の到着tickを比較。

| セル | 最初の到着tick | 相当する日数 |
| --- | --- | --- |
| 近接（森歩き圏内） | 6,000 | 2日 |
| 最遠 | 9,000 | 3日 |

設計の狙いどおり、近接セルは3日ではなく2日で最初の移住者が来た。最遠セルは
従来の `ARRIVAL_INTERVAL_TICKS`（3日）と完全一致——遠いセルは乗数1.0のまま。

### 測定: 灯持ち（行商間隔 5日→3日）

worldSeed=3、最近接セル (9,0)・最遠セル (0,0)。交易柱を建て、食料を満たした状態で
`runTrade` を1tickずつ回し、最初の来訪tickを比較。

| セル | 最初の来訪tick | 相当する日数 |
| --- | --- | --- |
| 近接（灯持ち圏内） | 9,000 | 3日 |
| 最遠 | 15,000 | 5日 |

こちらも設計どおり5日→3日、最遠セルは従来の `TRADE_INTERVAL_TICKS`（5日）と一致。

### 測定: 渇き衆（襲撃規模×1.5・重み×1.5）

`runIncidents` のみを1日ずつ回す方式（`createHarness().run()` によるフル tick シミュレーション
は使っていない——後述のとおり実測1tickあたり約0.6msかかるフルシミュレーションで
600,000tick規模を回すと1テストで数分かかり、日次判定だけを見たいこの測定には過剰）。
各日の判定前に `state.raiders = {}` をリセットして、前日の襲撃が居座って翌日の判定を
ブロックする効果（`isUnderAttack` ガード）を切り離し、人口（`raidSize` のもう1つの入力）も
一定に保っている——見ているのは「その日の役（イベント）が襲撃かどうか」と「規模」という
2つのレバーだけ。

8世界シード（1〜8）×1,500日ロールを両側（渇き衆の圏内・最遠セル）で実施、
片側12,000日ロール・合計24,000日ロール:

| | 襲撃回数（合計） | 襲撃者数（合計） | 平均規模 |
| --- | --- | --- | --- |
| 近接（渇き衆圏内、距離≦1） | 386 | 1,284 | 3.33 |
| 最遠 | 323 | 754 | 2.33 |

頻度は約+19.5%（重み×1.5が季節ごとの他イベントとの相対配分を押し上げる分、期待どおり
「1.5倍」より小さい――他のインシデントの重みは変わらないため）。**平均規模は2.33→3.33で
ほぼ設計の×1.5どおり**（`raidSize` の乗数と上限が population/2 の項・乱数のジッターを
均した後に効いてくるため、十分な標本数で初めて×1.5に近づく）。8シードすべてで
「近接 > 最遠」の方向が一度も逆転しなかった。

### 導出物は何も保存していない

`worldMapGrid` ・`worldBiomeAt` ・`tribalInfluence` の3つはいずれも `worldSeed` と（必要なら）
`worldCell` だけから毎回計算し直せる純粋関数で、`GameState` に足したフィールドは
`worldCell: {x, y} | null` の1つだけ（`schemaVersion` 21→22）。旧セーブは `worldCell: null` を
補うだけの1段で移行し、`tribalInfluence` は `null` を「距離Infinity・全乗数1.0」として扱う
——4.2章の「どの圏からも遠い」を、旧セーブがそのまま体現する形になっている。

## 提示（フェーズ13）

設計案は [design-phase13-presentation.md](design-phase13-presentation.md)。実装は設計案から
ほぼ変えていない。変えた点・決めた点・実測値だけを書く。

### 実装で決めた点（設計案からの差分）

- **建築完了のログ行は増やさなかった。** 設計案 5.3 は完成音の引き金を「建築完了」と
  書いたが、完了を知らせる `LogKey` が存在せず、音のためにコアへログを足すのは
  「コアは音を知らない」（7章）に反する。代わりに `SfxDirector` が**完成建物の数の増分**
  （ブループリント以外・ゾーンマーカー除く）から鳴らす。配置音も同じ形（ブループリント＋
  ゾーンマーカーの数の増分）。ログ差分から鳴るのは角笛（`incidentRaid`）・研究
  （`researchUnlocked`）・取引（`tradeSettled`）の3つだけ
- **ロードで鳴らさない仕組みは tick の連続性で判定。** 2回の観測の間に tick が50超
  跳んでいたら（ロード・新規開始・長い停止からの復帰）、差分を語らず基準を取り直す。
  50 は `MAX_CATCHUP_TICKS`(30)×10倍速=300 より小さいが、そこまで跳ぶフレームは
  停止明けであり音を捨てるのが正しい、という判断
- **critical アラートの同一性は `game/loop.ts` の一時停止判定と同じ** `key + params` の
  文字列。同じ危機で「一時停止はするが音は二重に鳴る/鳴らない」という食い違いを作らない
- **選択タイルの見出しは「タイル x, y」に変更。** 盤面の Fold が「選択中」を名乗るので、
  内側のパネルが同じ語を繰り返していた（実ビルドのスクリーンショットで発見）。
  `rowTile` の行は見出しに昇格して廃止
- **ミュート中も `SfxDirector` は差分を見続ける。** 再生だけを省く。ミュート解除の瞬間に
  溜まった差分が一斉に鳴る「音の未払い」を作らないため

### 測定: 受け入れ条件（実ビルド、Chromium ヘッドレス）

単一HTMLビルド（906KB。音のコードを足す前は902KB——**効果音6種の増分は約4KB**で、
設計案 5.1 の「アセット0バイト・コード数KB」の見積もりどおり）に対し Playwright で
21項目を自動測定、全項目合格（1280×700、一部760px幅でも確認）:

- 段階A: セーブ実行でメッセージが出ても `app__body` の位置・寸法が変わらない
  （en/ja 両方、幅760pxでも同じ）。`text-overflow: ellipsis` が効き、全文が `title` に載る
- 段階B: 資源・ミニマップ・選択枠が個別に畳める／畳んでもキャンバスの位置が動かない／
  折り畳み状態がリロード後も残る／未選択時は左下オーバーレイ自体が無い／選択枠は
  ビューポート左下から 8px・サイドバーからは消えている
- 段階C: 既定ミュート（`aria-pressed=false`）／トグルで `localStorage`（`simworld.sound`）に
  残りリロード後も有効

### 測定: 発火の規律（ヘッドレス、`src/ui/sfx.test.ts` 7件）

- 初回観測は危機の真っ最中でも無音（基準取り）
- 10倍速相当（200ms/フレーム×300フレーム=1日、毎フレーム配置を試行）で同種の音の
  発火間隔が一度も 500ms を割らない
- critical アラートは出現の瞬間に1回だけ。出続けている間は再発火しない
- tick が10,000跳ぶロード相当の遷移では、新規ログ行・建物増があっても無音

### 保留の再確認

## 時間と動き（フェーズ7）

設計案は [design-phase7-time.md](design-phase7-time.md)（末尾に実装メモ）。現況は design.md 11章。

### 測定: しきい値乗数だけでは睡眠は夜に寄らない

設計案 3.4 の (b)（`SLEEP_THRESHOLD` に夜0.7・昼1.3 の乗数）を数値モデルで先に確認した:
睡眠サイクル（ゲージ充填16時間＋睡眠4〜7時間 ≒ 21時間）が24時間の時計とずれ続けるため、
乗数の組をどう振っても（0.5〜0.8 × 1.2〜1.3 を走査）夜間開始は最大50%（一様分布で42%）。
実シミュレーション（シード15101、8日）でも夜間睡眠 tick 比率 0.43 と一致した。

**「夜の眠りは夜明けまで続く」を錨として追加**（覚醒判定に1行、空腹85超なら夜中でも起きる）。
さらに就寝側の傾斜を画面の日暮れ（17〜19時）と同じ位置に置くと、就寝が17時台に固定されて
夜明けまでの拘束で労働が1日約4時間消え、**季節テスト（蓄えた植民地が冬を越す）が餓死で落ちた**。
傾斜を20〜22時へ移すと就寝は約20:40・睡眠約8時間に収まり、季節テストは復帰。

| 条件 | 夜間（19〜05時）の睡眠tick比率 |
| --- | --- |
| 一様（無策） | 0.417 |
| 乗数のみ（0.7/1.3、実測） | 0.43 |
| 乗数＋夜明けまで持続＋傾斜17-19時 | 0.648（ただし季節テスト餓死） |
| **採用: 乗数＋夜明けまで持続＋傾斜20-22時** | **0.638〜0.671（3シード×8日、過渡3日除外）** |

### 測定: 歩調の端数

`stepProgress` をステップで0にリセットすると端数が切り上がり、荷の1.15倍が実質1.5倍になる
（20歩=46tickのはずが60tickになる。テストで発見）。端数は次の歩へ持ち越す。

### 灯りは「穴」ではなく加算の光

全面オーバーレイに減算の穴を開けるにはレンダーテクスチャ（オフスクリーン合成）が要る。
放射グラデーションのスプライト（コード生成、アセット0バイト）を加算合成で重ねれば
1枚も増やさず済み、柔らかい。給電が切れた灯は `litLamps` が返さないので勝手に消える。

### 1年計測 —— 最初の全スイートで4件破綻し、数値3つを曲げて戻した

歩速の乗数と夜間睡眠の導入は生産チェーン全体に効く。傾斜を20〜22時に移した状態で
全スイートを回すと、**それでも4件が落ちた**（longrun の1年で植民地が死滅・冬越しで餓死・
霜花の冬収支が赤字・作業割当の応答性テスト）。原因は2系統:

1. **覚醒可能時間の上限**。睡眠ゲージは16時間で満ちる（`SLEEP_PER_TICK` = 100/2000）ので、
   昼しきい値97.5に達するまでの覚醒は最長15.6時間。起床が夜明け（05:00）に固定された結果、
   1日は「覚醒15.6h＋就床8.4h」となり、導入前の就床約5.8hから**労働が1日約2.6時間減った**。
   これが年間走行の死滅と冬の赤字の正体。**`SLEEP_PER_TICK` を 100/2400（19.2時間で満ちる）に
   変更**し、24時間周期（覚醒約15.7h＋就床約8.3h）として整合させた。あわせて
   **就床時の空腹が睡眠中に100へ達する競合**（就寝間際の高い空腹＋長い夜）を、
   「睡眠中でも空腹85（`NIGHT_WAKE_HUNGER`）で目を覚ます」で塞いだ
2. **冬の労働のさらなる目減り**。森の歩速1.25倍と夜の就床は冬の霜花収穫に一番効く。
   **`FOOD_PER_FROSTBLOOM_HARVEST` 7→8**（ベリー9未満は維持——冬が最良の季節にはならない）で
   冬の収支を黒字に戻した

作業割当のテストは別因で、**craft スキルが初期スキル抽選のプールに入ったことで同じシードの
出目が全部ずれた**（提案3の副作用）。テストを乱数の出目依存から明示的なスキル設定に直した
（検証したい「ボタンは応答性を代償にする」という形は変えていない）。建築メニューは作業台で
家具カテゴリが8個になり、上限を7→8へ（上限の意味は「画面に収まる」で、8でも収まる）。

## プレイテスト由来の修正5件（#8・#9・#11・#13・#14）

フェーズ番号を持たない、実プレイテストの指摘5件。現況は design.md 11章末尾。

### #11 サイドバーのスクロールバーのちらつき

`.sidebar` と `.log--scroll` に `scrollbar-gutter: stable` を追加した（`src/styles.css`）。
コンテンツ高がビューポート高（`.log--scroll` は自身の `max-height: 190px`）を跨ぐたびに
スクロールバー幅が出入りし、内容幅が横に揺れていたのが原因。

`.modal`（ワールドマップ）には**適用しなかった**：開いている間に高さが変わらず
（可変部分 `.worldmap__summary` は `min-height` で吸収済み）、かつ固定幅を持たず
`max-width` までコンテンツに合わせて縮む箱なので、gutter を常時確保すると逆に幅が変わる。
「スクロールバーの出入りで幅が動く」問題への対処が、別の箱では「gutter 自体が幅を動かす」
原因になる――同じ CSS プロパティでも当てはめる箱の性質を見てから決める必要があった。

### #14 ミニマップのドラッグ

`onClick` を `pointerdown`/`pointermove`/`pointerup`/`pointercancel` に置き換えた
（`src/ui/Minimap.tsx`）。座標変換を純粋関数 `tileAtMinimapPoint` として切り出し
（範囲外はクランプ）、`setPointerCapture` でミニマップ矩形の外へポインタが出てもドラッグが
続くようにした。

`focusOnTile` は毎 `pointermove`、`selectTile` は `pointerup` の1回だけに分けた――ドラッグ中
に毎回選択すると検査パネルが通過タイルを次々表示してちらつくため。カメラ追従（見る）と
選択（決める）は同じドラッグの中でも別のタイミングで確定してよい。ドラッグ状態は `useRef`
に置き、`GameState` には入れていない。

### #13 動物のクリック選択

純粋関数 `pickAt(state, x, y)`（`src/render/pick.ts` 新規）を新設し `handleSelectClick` から
使う。優先順は 入植者 → 動物 → 移動命令 → 選択解除。入植者と動物が同じタイルにいれば
入植者が勝つ。同じタイルに動物が複数いても id 順で決定的に1体を返す（`src/render/pick.test.ts`
で固定）。

**判断**: 入植者を選択中に動物をクリックしたら、移動命令ではなく動物の選択にした。逆にすると、
その場から動かない動物（膠着した狩猟対象・追い詰められた捕食者）が永久にクリックで選べなく
なるため。代償は「動物のいるタイルへ直接クリックで歩かせられない」（1マス隣のクリックで済む）。

### #8 開始直後の高速移動

**報告された症状の原因はフェーズ7で既に解消済み**だった。フェーズ7以前の補間は全エンティティ
一律 `0.007 タイル/ms`（≒143ms/タイル）で、実際の歩調（1倍速で 入植者 400ms・シカ 600ms・
ニワトリ 800ms）に対し2.8〜5.6倍速だった。0.007 は3倍速の入植者（133ms/タイル）にほぼ一致する。
起動直後の tick まとめ処理で論理位置が先行し、表示がその差を最大5.6倍速で追いかけ、追いついた
瞬間に通常速度へ落ちていた。

現在の `interpolationSpeed` では表示速度が論理歩調を超えられないことを、起動時のストールを
含む合成フレーム列で速度{1, 3, 10}×`ticksPerStep`{2, 3, 4}について固定した（`src/render/pace.test.ts`）。
そのうえで、調べる過程で以下の2つの残存欠陥が見つかった――当初の仮説（catch-up バーストが
主因）は外れており、より重い原因が別にあった。

**残っていた欠陥1**: 「3マス超離れたらスナップ」のガードが `updateColonistView` にしか無く、
`syncAnimals` と `syncRaiders` に無かった。退避（`evictFromTile`）やセーブのロードで、歩いても
いない地面をスプライトが横断していた。判定を `isTeleport`/`TELEPORT_DISTANCE_TILES`
（`src/render/pace.ts`）に1箇所へ出して3種で共有。併せて入植者側の既存の取りこぼしも修正
――スナップ直後に古い大きな `dx`/`dy` をそのまま加算していて、合わせたはずの位置を1フレーム
ぶん行き過ぎていた。

**残っていた欠陥2（本命）**: catch-up の上限で打ち切ったぶんの時間を `accumulator` に残して
いたため、ストールが明けて通常フレームに戻っても毎フレーム上限に張り付き続けた。

測定条件: 速度10、1000msフレームを2000回（バックグラウンドタブでの `requestAnimationFrame`
抑制を模した最大長のストールを連続させた状態）流し込んだあと、通常の16.7msフレームへ切り替えて
何フレーム目で上限（30 tick/フレーム）を下回るかを数えた（`src/game/loop.test.ts`）。

| | 修正前 | 修正後 |
| --- | --- | --- |
| 上限に張り付いたフレーム数 | 1,372 | 0 |
| 実時間換算（60fps） | 約22.9秒 | 0秒（最初の通常フレームから正常） |
| その間の実効 tick レート | 1,800 tick/秒 | 50 tick/秒（正常） |
| 正常速度（速度10）に対する倍率 | 36倍 | 1倍 |

catch-up の計算は `advanceTicks`（`src/game/loop.ts`）として切り出してテスト可能にした。
ガードは「交差回数」ではなく「tick 数」（速度10では1回の交差で10tick増えるので上限は
3交差で効く）。上限に掛かったフレームでは1tick未満の端数を除いて積み残しを捨てる――上限を
設けた時点でゲーム内時計が実時間から遅れることは受け入れている以上、負債として持ち越すのは
一貫しない。定数（`MAX_CATCHUP_TICKS = 30`・`MAX_FRAME_MS = 1000`）は変えていない。

### #9 狩猟時に入植者がうろうろする

**測定条件**: `createHarness(seed)`（60×60）、狩猟指定した動物1体を拠点から12タイル離して
配置、空腹/睡眠/娯楽は測定中フリーズ（ニーズに引っ張られて途中でジョブを離れないように）、
30シード。

**原因は2つあり、当初の仮説より重いものが主因だった。**

- **(1) 地形に張り付いて永久に回り込めない（主因）**: `chase` の貪欲移動は「大きいほうの軸→
  だめならもう一方の軸」を試し、**両方が塞がったときだけ**実経路（A*）に落ちていた。1タイル
  より幅のある岩場では「もう一方の軸」が壁沿いに開いているため実経路に落ちず、壁面を往復し
  続けた。**30シード中2件（15007・18007）が1,500 tick 経っても狩猟を完了せず**、対象との
  距離が縮まらないままだった。
- **(2) 射程の境界での往復（当初の仮説、実在した）**: 距離が `HUNT_RANGE` 以内になった瞬間
  `chase` が `'arrived'` を返して入植者が止まるため、獲物が1歩さまようたびに射程外へ出て
  入植者が1歩詰め直す。境界上に湧かせた条件でウサギは狩猟中に平均5.37回射程外へ逃げ、
  約12tickごとに詰め直していた。

**修正1**: 貪欲移動は大きいほうの軸だけを試し、そこが塞がっていれば直ちに実経路へ落ちる。
求めた経路は既存の `path`/`pathTargetTileId` に載せて**最後まで歩き切る**（次のタイルが
通行可能かだけ毎tick再確認）。毎tick 引き直すと、獲物が動くたびに障害物のどちら回りが近いか
が入れ替わり、前のtickの一歩を打ち消していた。回り込み中は貪欲判定より優先する――壁面に
立っていると「壁沿いの1歩」が生の距離を縮めるので、貪欲がすぐ回り込みを取り消して行き止まり
へ戻してしまう。**新しいフィールドは増やしていない**（既存の `path`/`pathTargetTileId` を使う。
`indexColonistPath`/`clearColonistPath` で PathIndex との整合も保つ）。

**修正2**: `HUNT_APPROACH_MARGIN = 2` を追加。最初の作業tickが入るまで（`job.workProgress === 0`）
は `huntRangeOf() - 2` まで詰め、作業に入ったあとは従来どおり `huntRangeOf()` を使う。
**弓の存在理由を壊さないよう下限をクランプ**: 弓（射程8）は `BOAR_CHARGE_RANGE + 1 = 7` より
内側へ入らないので、イノシシの突進圏の外から撃つという性質（フェーズ8 E-3）は保たれる。
近接（射程5）は元から突進圏の内側なので性質は変わらない。手懐け（射程1）と `chaseRaider` は
不変。

**修正後の実測（同じシード・同じ条件）**:

| 指標 | 修正前 | 修正後 |
| --- | --- | --- |
| 狩猟の完了 | 28〜30/30（2シードが1,500tickで未完） | 30/30 |
| 未完だった2シードの所要 | 1,499 tick（打ち切り） | 約165 tick |
| 到達後の歩数（シカ・イノシシ、距離12） | 59 | 2.8 |
| 向きを変えた回数（同上） | 51 | 0.2 |
| 射程外へ逃げられた回数（同上） | 2.6 | 0.7 |
| 同（ウサギ） | 1.2 | 0.17 |
| 作業tickの割合（シカ・イノシシ） | 0.63 | 0.69 |
| 同（ウサギ） | 0.58 | 0.63 |

狩猟全体の所要 tick の中央値はほぼ変わらない（+2〜3 tick、少し深く詰めるぶん）。**変わったのは
最悪ケースで、最大 1,499 → 約160 tick**。

新しい回帰テスト `src/core/hunt-chase.test.ts`（永続）。上の2シードの地形張り付きと、境界の
往復の減少（射程外へ逃げられた回数・作業tick割合）を、**測った値から決めた閾値**で固定して

**その修正が `longrun` を壊した ―― `chase` は狩猟だけのものではなかった。**

上の修正を入れて全スイートを回したところ、`longrun.test.ts` の「1年を通してセーブ往復しても
植民地が生き残る」（seed 8117、60×60）が**入植者0人＝全滅**で落ちた。ベースコミットでは同じ
テストが5/5通る。

原因を測るため、7シード（8101・8111・8117・8123・8130・8140・8150）×1年を60×60で回し、
`recordLogEntries`（100件のリングバッファを迂回する）で死因を集計した。

| seed | 生存 修正前→後 | 死者 前/後 |
| --- | --- | --- |
| 8101 | 5 → 5 | 1 / 1 |
| 8111 | 4 → 4 | 2 / 2 |
| **8117** | **2 → 0** | **4 / 6** |
| 8123 | 2 → 4 | 4 / 2 |
| 8130 | 5 → 3 | 1 / 3 |
| 8140 | 5 → 5 | 1 / 1 |
| 8150 | 6 → 6 | 0 / 0 |
| 合計 | | **13 / 15** |

決め手は3つあった。**死因は前後とも `colonistKilledByRaider` だけ**（餓死ゼロ・動物による死ゼロ）。
**食料は一度も枯れていない**（最低在庫100〜127、年末1,100〜1,500）。そして**狩猟イベントは
全シードで0件** ―― 狩猟はプレイヤーが指定する仕事なので、無操作の `longrun` では一度も発生しない。
つまり `HUNT_APPROACH_MARGIN` はこの回帰に一切関与しておらず、効いていたのは
**`raid.ts` の守備側が呼ぶ `chase`（射程1）**だけだった。襲撃者は `chaseRaider` で毎tick再照準して
動くため、数tick前の位置に向けて計算した回り道を最後まで歩き切ると、その間に襲撃者は壁を壊し、
別の入植者を殴れる。接敵の遅れがそのまま被害になっていた。

**対処**: `chase` に `ChaseOptions.persistDetour`（既定 `true`）を足し、`raid.ts` の戦闘呼び出しだけ
`false` を渡して**#9以前の挙動へ完全に戻した**（両軸の貪欲→両方塞がったときだけ A*、しかも1歩で
使い捨て）。狩猟・手懐け側は既定のまま #9 の修正が効く。同じ関数でも、追う相手の性質が違えば
正しい戦略は違う ―― さまよう動物は障害物ごしに回り込む価値があり、正面から来る襲撃者は
毎tick照準を引き直す価値がある。

採らなかった案：経路キャッシュに「一定歩数で見直す」上限を設ける（狩猟と戦闘で最適値が違い、
根拠のない定数を1つ増やすことになる）。譲歩ステップだけを条件付きで戻す（変更が半端に混ざり、
「途中で貪欲が回り込みを取り消す」問題が再発しうる）。

**戻したことの確認**: 同じ7シードの診断が**ベースと完全一致**（合計13死、8117 は2人生存、
襲撃回数・建物の破壊数・食料の推移・失敗ジョブ数もシードごとに一致）。襲撃側の軌跡が
#9 以前に戻ったことを、生存数だけでなく内訳で確かめている。`longrun` 5/5・`hunt-chase` 4/4。

## 水（フェーズ14 段階 W-1）

`docs/design-phase14-water-medicine.md` の 2 章を実装した。測定条件はすべて
**シード 1〜20 を `testWorld` 経由・60×60**。

### 見積もりは高すぎた

設計案 7 章は「草原の水タイルは全体の 4〜6%」としたが、実測は **3.04%**。
閾値を下げて合わせることは**しなかった** —— 段階 W-2 が同じ地図に川を足すので、
いま上げると川が乗ったときに超過する。合計は川が入ってから測り直す。
**測った値と食い違ったら直すのは主張の側**なので、`biome.ts` のコメントと
この節に実測値を書き、設計案の見積もりは提案時のまま残した。

| バイオーム | 浅瀬 | 深水 | 合計 |
| --- | --- | --- | --- |
| 草原 meadow | 2.47% | 0.57% | 3.04% |
| 深森 deepwood | 2.00% | 0.33% | 2.33% |
| 岩尾根 crag | 0.27% | 0.00% | 0.27% |
| マナ荒野 manaheath | 1.31% | 0.12% | 1.44% |

深水:浅瀬の比も見積もり（1:2）から外れて 1:4〜1:9 になった。値ノイズの分布が中央に寄るため、
閾値を 0.08 離すと上側の裾が薄くなる。「岸が必ずできる」という狙いは満たしているので比は追わない。
岩尾根には20シードを通して深水が1タイルも出なかった —— 湖の無い世界がありうる、
という意図どおりの結果。

### 断片化は水のせいではなかった —— 岩尾根が元から持っていた

設計案 3.2 は「湖が地峡を塞いで地図が割れる」ことを主なリスクに挙げていた。
20シード × 4バイオームで、拠点の region が歩ける陸地に占める割合を測った。

| バイオーム | 最小 | 中央値 | 90% を下回ったシード |
| --- | --- | --- | --- |
| 草原 | 97.89% | 100.00% | 0 / 20 |
| 深森 | 99.26% | 100.00% | 0 / 20 |
| 岩尾根 | **62.92%** | 99.26% | **7 / 20** |
| マナ荒野 | 95.93% | 100.00% | 0 / 20 |

岩尾根の7シードが下限を割った。**しかし水が原因ではない。** 全バイオームの `waterThreshold` を
実行時に 0.99 へ差し替え（＝水を1タイルも生成しない状態）て岩尾根を測り直すと、
結果は**完全に一致した**（最小 62.92%・中央値 99.26%・90%未満7シード）。

つまりこれは水が持ち込んだ欠陥ではなく、**岩尾根が `stoneThreshold: 0.62` で元から持っていた
性質**である。フェーズ11 でバイオームを入れたときには測られていなかった。
拠点から遠い森や鉱脈が「幾何的には近いのに到達不能」になる形なので、
CLAUDE.md の「プレイヤーに見えない失敗」に当たる。段階 W-2 の連結性保証は、
水のためだけでなく**この既存の断片化にも効かせる**。

*仮説が外れた3例目*（#8・#9 に続く）。今回は「新機能が壊した」という当然に見えた説明が
実測で否定され、原因が**既存の、測られていなかった性質**にあった。
アブレーション（新機能を無効化して同じ測定を繰り返す）を回さなければ、
水のせいにして誤った修正を入れていた。

### 再較正は不要だった

`worldgen.test.ts` の地形構成の下限（拠点から14以内に森10超・20以内に岩0超）は、
既存6シードのまま**成立した**。鉄鉱脈を入れたとき（`season.test.ts` / `longrun.test.ts` の
コメントに残る総入れ替え）のようなことは起きていない。水が岩・森より先に決まる分だけ
両者が減るが、下限には元から余裕があった。

### テスト

`src/core/water.test.ts`（7件）。浅瀬は歩け深水は歩けない／水の上にブループリントが置けない／
水を `mine` に指定できない／拠点から森と岩へ **region で**到達できる（幾何距離ではなく `isReachable`）／
3日回して誰も深水に立っていない／バイオームごとの水の割合が想定の範囲に入る。

## 川と連結性（フェーズ14 段階 W-2）

測定条件は W-1 と同じ **シード 1〜20 を `testWorld` 経由・60×60**、4バイオーム。
連結性は「拠点タイルを含む歩ける連結成分が、歩けるタイル全体に占める割合」。

### 既存の断片化が消えた

| バイオーム | 水（W-1、湖のみ） | 水（W-2、川込み） | 拠点 region 最小 | 中央値 | 90%未満 |
| --- | --- | --- | --- | --- | --- |
| 草原 meadow | 3.04% | **5.65%** | 97.98% | 100.00% | 0 / 20 |
| 深森 deepwood | 2.33% | 5.11% | 96.82% | 100.00% | 0 / 20 |
| 岩尾根 crag | 0.27% | 1.77% | **92.06%** | 99.74% | **0 / 20** |
| マナ荒野 manaheath | 1.44% | 4.38% | 98.13% | 100.00% | 0 / 20 |

**岩尾根は 7/20 → 0/20、最小 62.92% → 92.06%。** W-1 のアブレーションで「水ではなく
`stoneThreshold: 0.62` 由来の既存の欠陥」と分かっていたものが、水のために入れた連結性保証で
一緒に直った。フェーズ11 から存在していた「幾何的には近い森や鉱脈が到達不能」がこれで無くなる。

### 川の本数は測って1本減らした

草原の `riverCount` は設計の出発点どおり 3 で実装したが、実測 **6.99%** で 7章の目安
（4〜6%）を超えた。2 に下げて **5.65%**。連結性は変わらず（最小 97.98%・0/20）。
W-1 で「湖だけでは目安を下回るが閾値は上げない、川が乗ってから測り直す」と決めておいた
判断が、結果として二重調整を避けた。

### 実装の形

- 川は `shallowWater` で引く（深水は湖の芯だけ）。**川が地図を割ることが構造的に起きない。**
- `enforceConnectivity` は `derived.ts` の `RegionIndex` を使えない —— `createSimContext` は
  `generateWorld` の**後**に走る。`worldgen.ts` 内に自前の flood fill を書いた。
- 貫通させる経路は **0-1 BFS**（辺のコストが0か1しかないので Dial's algorithm）で、
  拠点側の全タイルを同時に根にして最小の貫通タイル数を求める。
- **マナ結晶と鉄鉱脈は探索グラフから除外**する。有限で `minCrystalTiles` が下限を保証している
  資源なので、連結性のために潰してよい対象ではない。深水は浅瀬へ、岩は草地へ落とす。
- 貫通したタイルには `walkable: true` を必ず書く（`terrain` だけ変えると `walkable` が古いまま
  残り、経路探索と見た目が食い違う。既存の採掘 `execute.ts` が同じ形で書いている）。
- 反復には上限（40）を置く。繋がらない地図で回り続けない。
- `state.forestCapacity` の計算を川と連結性保証の**後**へ動かした。両方が森を水や草地に
  変えうるので、再生の天井は「地図に実際に残っている森」でなければならない。

## 薬草（フェーズ14 段階 H-1）

### 3種目を足す前に表へ抽出した

`building.type === 'berryBush' || building.type === 'frostbloom'` という2種前提の or が
4箇所（`generator.ts` 2箇所・`execute.ts`・`simulation.ts`）にあった。薬草を足す前に
`WILD_PLANTS`（産出資源・産出量・再生速度・季節表）1枚に畳み、4箇所がそれを引くようにした。
フェーズ10 が `VEIN_YIELD` でやったのと同じ形で、**新しい機構ではなく分岐の置き場所の変更**。

季節表だけは表に直接持たせず `'crop' | 'frostbloomInverse'` の判別子にした ——
`season.ts` が `constants.ts` を import しているので、逆向きの import は読み込み順で循環する。

### `food` の variant にしなかった

`Item.variant`（調理済みの食事の前例）に乗せると、**腹を空かせた入植者が薬を食べる**。
`variant` は「されたこと」であって「それが何か」ではない、と型のコメント自身が書いており、
`food` の variant はあらゆるジョブ・フィルタ・交易にとって依然として食料である。
`ResourceType` に `herb` を1つ増やした（鉄が同じ形の前例）。

テストは餓死を**実際に起こしてから**（体力低下と `colonistStarving` ログを確認してから）
薬草の残量が減っていないことを見る。空腹でなければ食べないのは当たり前なので、
先に飢えさせないと主張が空になる。

## 水と川が既存テストをずらした（フェーズ14 段階 W-1・W-2 の後始末）

段階W-1・W-2 は `worldgen.test.ts` の地形構成の下限を再較正なしで通したので、地図のずれは
吸収されたと判断して先へ進んだ。**これが早合点だった。** 別のテスト2件が落ちていた。
どちらも製品の欠陥ではなく、**テストの側が地形の形に寄りかかっていた**もの。

### `fantasy.test.ts`「霜花の収穫が倉へ届く」

冬の初めと終わりで**食料の総量**を比べていた。これは「植民地は冬を経て豊かになったか」という
食料経済全体の問いで、この植物についての問いではない —— 収穫した先から食べられるので、
収穫が完璧に動いていても総量は動かない。水で地図がずれ、seed 5107 では収穫量と消費量が
ちょうど釣り合って 120 対 120 になり、落ちた。

**名前が約束していること（倉へ届く）を測る形に直した**: 総量の*増加分だけ*を積算し、
かつ `countStoredResource`（貯蔵ゾーンの中身）が一度でも増えることを見る。
元のテストは名前に反して**貯蔵を一度も見ていなかった**。

### `testUtils.ts` の `placePastureNear`

拠点から4方向のスポーク上だけを半径ごとに試していた。これは探索ではなく4回の当てずっぽうで、
牧場を置ける場所がスポークに乗っているときだけ見つかる。水で地形が少し動き、seed 4201 が
どのスポークにも乗らなくなって helper が例外を投げ、**貯蔵フィルタとは何の関係もない理由で**
`storageFilters.test.ts` が落ちた。

箱の中の全オフセットを拠点に近い順（同距離は座標順で決定的）に走査する形に直した。
これで「地図に本当に置き場所が無い」ときだけ失敗する。

*教訓*: 地形生成を触ったら、地形の**構成比**を見るテストだけでなく、
**地形の形に依存しているテスト**（拠点の周りに何かを置く、特定シードの収支を見る）も走らせる。
前者が通ることは後者の保証にならない。

## 病気と治療（フェーズ14 段階 M-1）

### `illnessTicks` は必須フィールドではなく `mealUntilTick` と同じ任意フィールドにした

設計案 6章は `Colonist.illnessTicks: number`（必須）としていたが、実装の依頼文が
`src/core/worldgen.ts` を「触ってはいけない範囲」に明記しており、新しい入植者を作る
`addColonist`（と、その既定優先度を組む `defaultPriorities`）はその中にある。必須フィールドに
すると `addColonist` の `Colonist` リテラルに値を足す必要があり、範囲を破ることになる。

`mealUntilTick` / `stepProgress` が既にこの形（型では `?`、未設定は「まだ効果なし」と読む）を
採っていたので、`illnessTicks?: number` にして同じ規約に乗せた。読む側は全箇所
`colonist.illnessTicks ?? 0` を通す（`> 0` 判定は `undefined > 0` が `false` になるので実は
素通りするが、`<= 0` 判定は `undefined <= 0` が `false` になり**逆に壊れる**ので、
`generator.ts`・`needs.ts`・`events.ts` の「無効化して次へ」系の分岐は明示的に `?? 0` を挟んだ）。

**依頼文の範囲指定が生んだ食い違いを1つ、親側で直した。** 段階M-1 の依頼は `worldgen.ts` を
「触ってはいけない範囲」に入れていたため、新規生成された入植者の `workPriorities.treat` は
`defaultPriorities()` の一般則に乗って **2** になっていた（研究・加工と同じ最低の3ではない）。
一方 26 → 27 の移行（`saveFile.ts`）は既存セーブに **3** を補うので、
**既存の植民地と新規の植民地で既定値が食い違う**状態だった。

5.3章が「既定優先度は research / craft と同じ最低」と明記している以上、これは設計との不一致で、
かつ「誰も勝手に医者にならない」という意図そのものが新規植民地でだけ緩む形になる。
`defaultPriorities()` に `t === 'treat'` を足して揃えた（1行）。

*教訓*: サブエージェントへの「触ってはいけない範囲」は、**同じ段階の中で必ず一緒に変わる
ものを含めてはいけない**。ここでは `JobType` を1つ増やすことと、その既定優先度を決める
`defaultPriorities()` は不可分だった。範囲を狭く切りすぎると、エージェントは指示に忠実に従い、
その結果として設計と食い違う実装が正しく報告されて返ってくる。範囲の誤りは親の責任であって、
報告してきたエージェントの側の誤りではない。

### 病気の進行が速すぎた —— 警告が「死亡の告知」になっていた

最初の実装は `ILLNESS_HEALTH_DECAY_PER_TICK = 100/8000` だった。設計案7章は
「治療なしで約5日で**危険域**」としているが、治療列を切って3シード測ると
**day 3.7 / 4.1 / 4.6 で患者が死んだ**。危険域どころではなく、プレイヤーが気付いて
動く窓が存在しない。この状態では 5.4章 のアラートは「病人がいます」ではなく
「病人が死にました」を出すだけの飾りになる。

`100/11000` に緩めて測り直した（同3シード・治療列オフ／既定優先度の両方）。

| | 健康50を割る | 危険域（20）を割る | 死亡 | 最低体力 |
| --- | --- | --- | --- | --- |
| 治療なし seed 3401 | day 3.2 | day 4.5 | day 5.5 | 0 |
| 治療なし seed 3402 | day 3.7 | day 5.9 | **死なず** | 20 |
| 治療なし seed 3403 | day 4.5 | day 4.5 | day 5.6 | 0 |
| 治療あり seed 3401 | — | — | — | 66 |
| 治療あり seed 3402 | — | — | — | 67 |
| 治療あり seed 3403 | — | — | — | 64 |

危険域に入るのが day 4.5〜5.9 で、死ぬのはその後。**放置すれば墓に行き着くのは変わらないが、
行き着く先が警告の「後」になった。** 治療が回っていれば体力は64を下回らない。

`healColonists`（`animals.ts`）が睡眠中に体力を回復させるので、正味の進行速度は
「1日のうちどれだけ寝たか」に依存する。紙の上で割り算しても出ない値で、測るしかなかった。

*仮説が外れた4例目。* 「死ぬまで放置される病気」と「危険域で気付ける病気」は
定数1つの違いで、しかもその定数は睡眠時間と相殺し合うので**実行して測らないと判別できない**。

`createHarness(seed)` で1年（`TICKS_PER_SEASON * 4` = 60,000 tick）を無操作で回した。
入植者は3人で始まり、到着で6人（`ARRIVAL_MAX_COLONISTS`）まで増える。

| seed | 発症（延べ） | 治療（延べ） | 年末人口 | 病気による死亡 |
| --- | --- | --- | --- | --- |
| 3401 | 1 | 1 | 6 | 0 |
| 3402 | 2 | 2 | 6 | 0 |
| 3403 | 4 | 3 | 6 | 0 |
| 3404 | 1 | 1 | 6 | 0 |
| 3405 | 3 | 3 | 6 | 0 |

5シードとも病気を理由にした死亡はゼロ（`colonistKilled` / `colonistKilledByAnimal` /
`colonistKilledByRaider` / `colonistStarvedToDeath` のいずれも記録なし）。治療1回が
`herb` を`TREAT_HERB_COST`（1）個消費するので、消費した`herb`の延べ数は治療回数と同じ
（1・2・3・1・3 = 計10個）。発症が0のシードは無かった —— 機構は繋がっている。

**発症頻度は7章の出発点（1人あたり20日に1回程度）より低い。** 平均人口4〜5人・20日で
4〜5回程度が出発点の見積もりだが、実測の平均は2.2回。`illnessWeightMultiplier`
（`events.ts`）が気分・空腹・頭数で重みを引き上げる形にしたが、この5シードは大きな飢えや
不満を経験しなかったため乗数がほぼ1のまま推移し、季節重み（春1・夏0.6・秋1・冬1.6）と
他の6つのインシデントとの取り合いの分だけに抑えられた。数値を追って引き上げることはせず
**そのままにした** —— 7章自身が「多すぎると作業台と同じ『常時対応』になる」と釘を刺しており、
実測が下振れした方向は安全側にある。治療が確実に追いついている（発症数と治療数がほぼ一致、
死亡ゼロ）ことのほうを優先した。

**`ILLNESS_HEALTH_DECAY_PER_TICK`（100/8000）は「危険域」より重い。** 治療が一切ないまま
だと、`healColonists`（睡眠中のみ回復）を差し引いても1日あたりおよそ20の体力を失う計算になり、
5日で0を割る—— 7章の見積もり「治療なしで約5日で危険域」は本来「危険域止まり」を意図していたが、
この数値では5日で致命的域まで進む。実測で誰も死ななかったのは、既定優先度（前節、新規植民地は
2）でも治療が5日以内に間に合っているためで、値そのものは危険側に振れている。据え置いた理由は
2つ: (1) 5シードとも死亡がゼロだった実測が「治療という安全弁込みで見て致死的すぎない」ことを
示している、(2) 治療が本当に届かない状況（`illness.test.ts`「薬草がなければ治らない」）を
弱めずに保つには、体力が測定可能なほど落ちる必要がある。値を緩めるなら、まず「治療が遅れた
コロニー」（`treat` の列を意図的に落とした状態など）を実測してから調整するのが筋が良い。


## 野生動物の密度（#10）

野生動物の頭数が多すぎるという報告（issue #10）。初期配置（`worldgen.ts` の
`spawnInitialWildlife`）と毎日の補充（`animals.ts` の `spawnWildlife`）は、どちらも
`SPECIES[species].initialCount` を `perArea(state, scaledCount(initialCount, scenario.wildlife
* biome.wildlifeMultiplier))` の形で読んでいる **1箇所の値**なので、その1箇所を動かせば
初期配置と補充の両方に効く。別の乗数は新設しなかった —— 新設すると knob が2ファイルに
分かれるし、`fantasy.test.ts` の `expect(elk.length).toBe(SPECIES.crystalElk.initialCount)`
のような自己参照テストが `SPECIES` を直しても追随しなくなる。

捕食者を除く7種すべての `initialCount` を約半分にした: deer 6→3, boar 4→2, rabbit 10→5,
chicken 8→4, goat 5→3, crystalElk 3→2, rockeater 2→1（合計 38→20、60×60基準）。
crystalElk と rockeater も含めて半減した理由は測定の節で述べる。`wolf.initialCount` は
既存の死にデータのままで、これは触っていない（狼の頭数は `scenario.predators` が決めており、
面積スケールもしない設計）。

### 測定条件

- **個体数**: 4バイオーム（meadow / deepwood / crag / manaheath）× 10シード（60×60、
  `testWorld`）と、出荷寸法 120×120 × 3シード（`createHarness(seed, 120)`）。
- **狩猟由来の食料**: standard シナリオ・60×60・3シード。1年（`TICKS_PER_SEASON * 4` =
  60,000 tick）を通じて、毎日（`TICKS_PER_DAY` ごと）その時点で野生・未指定の動物を
  すべて `designateAnimals(state, tileIds, 'hunt')` で狩猟指定し直す（`chaos.test.ts` と
  同じ呼び出し方）。ログの `animalHunted` を `recordLogEntries` で取りこぼしなく数え、
  各エントリの `species` から `SPECIES[species].foodYield` を積算した。**狩人の処理能力が
  ボトルネックになるよう常に「狩れるだけ狩猟指定してある」状態**で測っているので、この数字は
  「その気になれば1年でどれだけ狩れるか」の上限に近い。
- **捕食者の獲物不足**: harsh シナリオ（狼上限4、面積スケールなしなので60×60でも120×120でも
  同じ4）・60×60・3シード、**最悪ケース**として `placePastureNear` で牧場を1つ確保し、
  山羊4頭を手飼い（`tame: true`）で置いた状態で1年放置。(a) 狼の頭数を日次でサンプルした
  min/max/平均、(b) `animalKilledByPredator` のログ行数（**飼い畜の損失のみがログに残る**
  —— `killAnimal` は「野生かつ未指定」の死を記録しないので、このログは山羊の損失そのもの）、
  (c) 入植者が捕食者に襲われて `fleeing` 状態に入った回数（狩猟指定なし・レイダーは
  `state.animals` に存在しないので `fromId` の存在チェックで自然に除外される）、
  (d) 捕食者による入植者の死亡数（`colonistKilledByAnimal`）を数えた。
- **越冬**: 無操作1年、(1) standard シナリオ・60×60・seed 8101（`longrun.test.ts` と同じ種）、
  (2) harsh シナリオ・60×60・seed 9313（`scenario.test.ts` と同じ種、牧場なし）。

### crystalElk と rockeater は半減した

据え置く選択肢も検討したが、測って半減のままにした。理由:

- **crystalElk の毎日の補充は `initialCount` に依存しない。** `spawnWildlife` は
  `WILDLIFE_RESPAWN_INTERVAL_TICKS`（1日）ごとに種あたり最大1頭を補充する規則で、
  `initialCount` はその補充が止まる**上限**にすぎない。1頭を手懐けて野生の頭数が上限を
  割れば、翌日にはまた1頭補充される —— つまり「2頭手懐けるのにかかる日数」は
  `initialCount` を2から3に変えても変わらない。半減で変わるのは**同時に野生でいる頭数**
  （見つけやすさ・狼に狩られたときの一時的な谷の深さ）であって、手懐けの総量ではない。
- `fantasy.test.ts` の「一頭では炉を賄えない・二頭ならほぼ賄える」という炉の経済性は
  `produceAmount` / `produceIntervalTicks`（頭数あたりの生産速度）で決まっていて
  `initialCount` は無関係 —— 半減してもこの経済性そのものは変わらない。
- rockeater は捕食者の獲物にならない（`findPrey` が `diet === 'lithovore'` を除外している）
  ので、半減しても「捕食者の獲物不足」の測定には効かない。半減する理由は個体数の目標
  （合計52.6%）に単純に揃えるためで、据え置いても半減しても実害・実益のどちらも小さい
  ——今回は他の5種と同じ扱いに揃える方を選んだ。

`src/core/fantasy.test.ts` の `elk.length === SPECIES.crystalElk.initialCount`（自己参照）、

`src/core/longrun.test.ts` も無変更で緑（`lowestWildlife > 5` を含む）。

## 風が渡る明度の帯（#23）

issue が挙げた3案は (a) スプライトへのアニメフレーム追加、(b) 描画時の変形、(c) 明度の帯を流す、の3つ。
**(c) を採った。**

### (a)・(b) を採らなかった理由

- (a) はスプライトシートにフレームを足すことになる。フェーズ7の設計案（design-phase7-time.md 5章）が
  「草木の揺れ（アニメフレーム追加）」を明示的に非目標としており（雲の影 #15 のときにも同じ理由で
  見送っている——design.md 11章「雲の影（#15）」）、ここだけ蒸し返す理由が無かった。
- (b) は描画のたびに頂点を歪めるような変形になり、`renderer.ts` に新しい描画経路を作ることになる。

### (c) を選んだ決め手 —— 雲の影の機構がそのまま使える

雲の影（`src/render/clouds.ts`、design.md 11章「雲の影（#15）」）は既に「動く帯を1枚重ねる」機構を
純関数 + `syncClouds` の形で持っている。風はこれと同じ形（純関数 `windAt` + `syncWind`）で、
風向き・速度・帯の大きさを変えるだけで成立した——CLAUDE.md「新しい機構より、既存の数値を曲げる」に
沿う選択で、`renderer.ts` に新しい描画経路を増やしていない（`blendMode: 'add'` で明るくする点だけが
雲の影の「暗くする」との違い）。

### 乱数を使わない設計

`GUSTS` は4つの固定表（`x0`/`y0`/`speed`/`length`/`width`/`strengthScale`）。雲の影の `CLOUDS` 表と
同じく「表自体がアセット」という扱いで、`Math.random` は使っていない。各ガストの位相オフセットは
`variantAt`（`tileVariant.ts`、フェーズ地形バリエーション #19 で作った関数）をガスト自身の
`(x0, y0)` に当てて導出する——座標から決定論的に導き、手で選んだ「それらしい」定数を使わない、という
`variantAt` 自体の設計意図をそのまま踏襲した形。

### 強さの上限は雲の影の半分以下

`WIND_STRENGTH_MAX = 0.08`。雲の影の `CLOUD_ALPHA_MAX`（0.18）の半分以下に置いた。理由は「2つの層が
注意を奪い合わないため」——雲の影は建物・動物・入植者まで暗くする比較的目立つ層である一方、風は
地面がわずかに明るくなる程度に留め、雲の影の下（描画順で terrain の直後・building の手前）に置く。

### コストの性質

タイル数に依らない一定コスト（スプライト4枚）。雲の影（5枚）と同じ性質で、120×120でも60×60でも
描画するスプライト数は変わらない。`GameState` に増えたフィールドはゼロ（経過時間はレンダラー内部の
`windElapsedMs` が持つ、雲の影の `cloudElapsedMs` と同じ扱い）、`schemaVersion` は不変。
ポーズ中（`state.speed === 0`）は経過時間が進まず、ガストは停止する。

### 未実施の検証

**測っていない。** 当初の計画は「120×120 実ビルドでのフレーム時間測定」と「10倍速での目視確認」
だったが、どちらも実施できなかった。原因はブラウザのペインを非表示にすると `requestAnimationFrame`
が進まなくなること——実測では **5.5秒で1フレーム**しか進まず、フレーム時間もアニメーションの
見た目も測定にならない状態だった。雲の影と同じ性質のレイヤーであることから性能上の懸念は小さいと
見ているが、これは**測っていない見積もり**であり、実測値ではない。

## 音声ファイルの生成とBGM（フェーズ15 段階S-2 実データ・段階S-3、#22）

### 前提の訂正 —— issue #22 の想定は外れていた

issue #22 は「この開発環境では音声を生成できない（GPUなし・PyTorchなし）」を前提に書かれていた。
これは**リポジトリのコンテナ側**の事実としては正しく、design-phase15-audio.md 1.1章の
「開発環境（コンテナ）にGPUが無く、生成モデルの実行・検証ができない」という記述もいまも変わらず正しい
（`nvidia-smi` 無し・PyTorch 無し・`ffmpeg`/`sox` 無し、はコンテナの中の話）。

しかし issue が前提にしていた「だから生成できない」という結論は、**開発者の手元に別の環境がある**
ことを見落としていた。実際には Stable Audio 3 Medium を動かせる環境が別に用意されていた
（`C:\Dev\StableAudio3`、RTX 5070 12GB、44.1kHz stereo WAV 出力）。生成そのものはこの手元環境で行い、
成果物のファイルをリポジトリに置く形にした（`tools/generate-audio.ps1` のコメントに同じ経緯を記す）。

**主張する前に測る、の裏返しとして**——「できない」という前提も検証してから受け入れる必要がある、
という記録として残す。

### 生成パイプライン

- `tools/generate-audio.ps1`: 19音（効果音13種のうち `build`・`animal` は3バリエーションずつ、
  BGM2本）の**プロンプト・seed・長さ**の表。音はスプライト（`npm run sprites`）と違い、このリポジトリの
  中だけでは再現できない——モデルの重み・同じランチャー・同じGPUが要る。スクリプトが保存するのは
  「発注内容」までで、これは design-phase15-audio.md 9.1章が受け入れると明記していたトレードオフに沿う。
- `tools/process-audio.mjs`: 後処理。依存パッケージの追加はゼロ——WAVは手でパース・書き出しできる
  程度に単純なコンテナなので、`Float32Array` に対する純粋関数の並びとして実装し、
  `src/assets/processAudio.test.ts` でユニットテストしている。処理順は
  モノラル化 → 先頭無音の除去（振幅がしきい値を超える最初のサンプルまで切る）→ 目標長へ切り詰め
  ＋末尾10msフェード → ピーク -3 dBFS へ正規化 → 16bit PCM 書き出し。

### BGM だけ切り詰めない

`TARGET_DURATIONS` で `bgm_day` / `bgm_night` だけ目標長を `Infinity` にしている。理由は
ループする音に末尾フェードを掛けると**1周ごとの音量の落ち込みそのものが継ぎ目になる**ため——
他の17音は末尾10msフェードを受けるが、BGMの2本だけは無傷のまま16bit化・正規化のみを受ける。

### 実測: 生成時間

短い効果音は1本あたり約51秒。ただし他プロセス（同じマシン上の別ジョブ）と競合すると
約5分まで悪化した。シード・本数を変えた比較測定ではなく、実行ログからの単純な実測値。

### 実測: 後処理の結果

全19本ともピーク **0.7079**（`TARGET_PEAK = 10 ** (-3/20)`、-3 dBFS ちょうど）。

| | サイズ |
| --- | --- |
| 効果音17ファイル合計 | **918 kB**（実測 940,078 バイト） |
| BGM 1本あたり | **5.29 MB**（実測 `bgm_day.wav` 5,292,044 バイト・`bgm_night.wav` 5,291,386 バイト） |

BGMが大きいのは60秒・モノラル16bit・44.1kHzの非圧縮WAVだからで、`.ogg`/`.mp3`のようなエンコーダは
このツールチェーンに無い（`process-audio.mjs` のコメントに同じ理由の記載がある）。

### 容量の実測とデプロイ先の変更

design-phase15-audio.md 7章は「単一HTMLのままでよい」と結論していたが、その実測は
「1.5MBの偽BGMを1本」という条件（940kB → 2,898kB）に基づくものだった。issue #22 は
「容量は問題にならない」という同じ結論を引き継いでいたが、**今回の条件（BGM2本・非圧縮WAV）は
その条件の外**だった。

| | 実測 |
| --- | --- |
| `dist/simworld-embed.html`（BGM2本同梱後） | **16,339,023 バイト（15.58 MiB）** |
| Claude アーティファクトの上限 | 16 MB |

解釈次第で上限を超えうる境界上の値になった。**7章の判断は外れた**——判断を消さずに残すのは、
design-next.md の他の「外れた判断」の記録と同じ扱いである。

対応として、音質を落とさず **GitHub Pages を公開経路として追加**した（`.github/workflows/pages.yml`）。
通常ビルド（`npm run build`）の `assetsInlineLimit` は 200000 のままなので、BGM は data URI 化されず
別ファイルとして出力され、キャッシュが効く。実測 **12.8 MB**（GitHub Pages のサイト上限1GBに対して
十分すぎるほど余裕がある）。`vite.config.ts` の `base` は既に `'./'` だったので変更は不要だった。
**単一HTMLのビルド（`npm run build:single`）は残す**——issue #22 の受け入れ条件が求める
「data URI で同梱・外部リクエストゼロ」を満たす経路として引き続き有効なので、Pages は置き換えではなく
追加の配布経路である。

**試聴していない。** 効果音とBGMのどちらも、長さ・ピーク・非無音・形式という機械的な条件は

とある通り、試聴での確認が要る。

### 追記: 実ビルドで見たら、風は一度も現れなかった（#23）

上の節は「未測定」として閉じていたが、実ビルドを 120×120 で目視したところ**風の帯が一度も
画面に出なかった**。原因の切り分けとして、巨大な静止ガスト（60×60タイル・強度 0.6）を一時的に
置いて再読み込みしたところ、地面がはっきり明るくなった —— **描画機構は正しく、原因はパラメータ**
だった。

（この切り分けの途中で1つ手間取った。Vite の HMR が反映されず、数値を変えても画面が変わらない
時間があった。強制リロードを挟むまで「実装が壊れている」と読み違えかけたので、目視で何かを
否定するときは**まず変更が本当に届いているかを確かめる**こと。）

外していた見立ては2つある。

| | 初回 | 調整後 |
| --- | --- | --- |
| 本数 | 4 | 10 |
| 大きさ | 18×4 タイル | 26〜36 × 7〜9 タイル |
| 速さ | 4.8〜6.5 タイル/秒 | 1.8〜2.6 タイル/秒 |
| 明度上限 | 0.08 | 0.22 |

- **本数と速さ**: 120×120 の地図に 18×4 の帯が4本では、視界（約16タイル）を横切るのが1本あたり
  約3秒で、ほとんどの時間はどこにも無い。雲（0.8〜1.5タイル/秒）より遅くはしていない ——
  雲のように動くものは突風に見えないため、速さは中間に置いた
- **明度上限**: 0.08 は単純に見えない濃さだった。0.22 で「地面が光を受けた」に見え、
  「そこが光っている」には見えない

**`WIND_STRENGTH_MAX < CLOUD_ALPHA_MAX` という当初の根拠は撤回する。** 二重に外れていた ——
0.08 は見えなかったし、そもそも2つの数は比較可能ではない。雲は**暗い**テクスチャを重ね、
風は**白**を加算するので、同じ数値が同じ明るさを意味しない。テストの主張は
「それぞれが 0.5 を下回る（光源ではなく波紋のままである）」へ置き換えた。

**フレーム時間の実測**（120×120 実ビルド、119フレーム連続）: 平均 16.67ms、中央値 16.70ms、
p95 16.80ms、最大 16.90ms。60fps に張り付いており、風によるフレーム落ちは無い。ただし
vsync 上限なので、**余裕がどれだけあるかまでは測れていない**。スプライト10枚でタイル数に
依らない性質は雲の影と同じなので、120×120 で問題にならないなら他の寸法でも問題にならない。

**まだ残っていること**: 10倍速での見え方と、調整後の濃さが「わずか」の範囲に収まっているかの
最終判断。どちらも人間の目で見るしかない。

### 追記2: 「もや」は風に見えなかった、線状の筋へ差し替えた（#23）

上の「まだ残っていること」への回答として、実ビルドを目視した感想は「光のもや・霧が移動しているように
見える」で、依然として風には見えなかった。

原因は形そのものだった。放射グラデーションを楕円に引き伸ばしたテクスチャには方向が入っていない。
方向の無い形は、速度や配置をどう変えても移動する光の塊にしか見えない——(1) の調整（本数・大きさ・
速さ・濃さ）はどれも正しい方向だったが、形の問題を数値では解決できなかった、ということでもある。

6本の細い筋を描くテクスチャに差し替えた。各筋は両端だけがすぼまる横グラデーション（途中は均一。
線形ランプにすると両端がすぼまらずレンズのように見える）で、太さ3〜6px・長さと濃さを不揃いにして
方向を形そのものに持たせた。`STREAKS` は `GUSTS` と同じく固定表——表そのものがアセットで、乱数は
使わない。

この時点では**見た目は未確認**だった（ブラウザのペインが非表示で目視できない状態が続いていた）。
濃さ（0.22）が線に対して適切かも未判断で、線は面積が小さいぶん上げる必要があるかもしれない、と
持ち越した。

### 追記3: 筋を2本に絞り、速度を10.8〜15.6タイル/秒、上限0.18へ最終調整（#23）

目視での指摘3点を反映した。

- **本数**: 6本から2本へ。6本は「風」ではなく網掛けの帯に見えていた。長く強い筋1本と、横にずらした
  短く淡い筋1本だけでも方向は伝わる
- **速度**: 5.4〜7.8 → 10.8〜15.6 タイル/秒へ。2段階の目視調整の結果で、1.8〜2.6 は漂流、5.4〜7.8 でも
  まだ遅い、という判断だった。雲（0.8〜1.5 タイル/秒）とは一桁違う——2つは同じ機構なので動きだけで
  区別されるほかなく、雲のように動くものは突風に見えない
- **明度上限**: `WIND_STRENGTH_MAX` を 0.22 → 0.18。筋のテクスチャは同じ alpha をもやより狭い面積へ
  集めるので、同じ数値でも濃く出る

連続性テストの1ステップ上限を 0.6 → 1.2 タイルへ広げた。速度を倍にしたことで実移動量が0.78タイルに
なり、0.6では正常な移動を誤検知する。折り返しの跳びは24タイル幅なので、「最速の正常な移動」と
「跳び」の間には依然として二桁の開きがある。

最終形: **10本、26〜36×7〜9タイル、10.8〜15.6タイル/秒、明度上限0.18、筋は2本**。design.md 11章を
この最終形へ更新した。

## 雲の影の追加調整（#15 の積み残し）

風（#23）の目視調整と同じ流れで、雲の影も実ビルドで見たら少なすぎ・薄すぎた。原因はフェーズ6で
地図が60×60→120×120へ4倍になったときに「5個」という表が追随しなかったこと——出荷寸法（120×120）
では初期実装は密度不足で、報告どおり「見えない」のが実態だった。

### 密度が足りなかった（個数を5→13→18→26→36へ）

測り方は3回とも同じ：120×120で20分ぶんの経過時間を一定間隔でサンプルし、視界サイズ（約16×14タイル）
の窓を多数の位置に置いて「画面に影がある割合」を数える。`WRAP_MARGIN_TILES` を大きさの追加に合わせて
広げるたびに測り直しているので、同じ個数でも回によって数値が動く。

| 個数 | 測定時の `WRAP_MARGIN_TILES` | 割合 |
| --- | --- | --- |
| 5（初期実装） | 14 | 16.0% |
| 13 | 14 | 40.5% |
| 5 | 18 | 17.2% |
| 13 | 18 | 38.9% |
| 18 | 18 | 59.1% |
| 5 | 28 | 14.3% |
| 18 | 28 | 51.0% |
| 26 | 28 | 82.4% |
| 36 | 28 | **90.3%** |

最終的に36個で**90.3%**。90%は意図して100%にしていない——買っているのは「常時曇天」ではなく
「たいてい何かが起きている空」で、この指標は視界の隅に触れているだけの影も1としてカウントするため、
実際に地面が暗く見える体感より数値のほうが高めに出る。

既存の先頭5個のパラメータは終始不変。変えたのは個数の追加だけなので、これまで流れていた雲は
これまでどおり流れる。コストの性質も不変（1個1スプライト、タイル数に依らない）。

### 濃さも足りなかった（`CLOUD_ALPHA_MAX` 0.18→0.28）

13個へ増やしても「見えない」という指摘は残った。原因は個数ではなく濃さだった——テクスチャの
グラデーションは中心から60%地点で既に半分、外周でゼロなので、影の面積の大半は地面を1割未満しか
暗くしていなかった。草地の上ではそれは何も無いのと同じ。

0.3ではなく0.28にしたのは、`clouds.test.ts` が既に「0.3未満」を固定しており、その制約を残す価値が
あるため——`NIGHT_ALPHA`（0.45）に近づいた影は天候ではなく「暗さの上の暗さ」に見える。テストは
変えていない。風の `WIND_STRENGTH_MAX < CLOUD_ALPHA_MAX` を実測で撤回したのとは事情が違う——あちらは
実測が二重に否定した思い込みだったが、こちらは意図が明示された不変条件で、0.28で両立できた。

### 大きさにも幅がなかった（半径5〜10→5〜16→5〜26）

数と濃さを直しても「まだ小さい・少ない」という指摘が残った。初期の半径幅（5〜10）は狭く、どの影も
「同じものが少し違う大きさで出ている」ようにしか見えなかった。空にスケール感を出すには大きくて
遅いものが要る。半径5〜16へ広げた段階で、大きいものほど遅くする関係を導入した——26タイルの影が
10タイルのものと同じ速さで横切ると、天候ではなくカメラが動いたか壁が通り過ぎたように見える。
その後さらに半径5〜26まで広げ、26タイルの影は集落を丸ごと覆う大きさになった。`WRAP_MARGIN_TILES`
は最大半径を下回らないという元の意図（コメントに明記）を保つため、半径を広げるたびに 14→18→28 と
追随させた。

### 色を紺から青みへ寄せた（合成方法を変えるまでの中間段階）

初期の色は near-black の紺 `rgba(20, 26, 45)`。実際に影が受け取る alpha ではほぼ黒で、明るさを
引くだけだった——地面が灰緑になり、陰ではなく「汚れ」に見えていた。晴天下の影は光の不在ではなく、
日が当たらない場所に空の色が降りてきたものなので、まず青みのスレート `rgba(46, 74, 132)` へ寄せた。
この段階ではまだアルファ合成のままで、次の「合成方法」の変更で置き換わっている。

### 合成方法がくすみの正体だった（アルファ→乗算）

色をスレートへ寄せても「色みはいいがくすんで見える」という指摘は残った。原因は色ではなく
**合成方法**だった——アルファ合成は覆った画素を1つの平坦な色へ引き寄せるので、その色が何であれ
地面自身の変化（草のテクスチャの明暗）も一緒に潰れる。潰れた色が「くすみ」の正体だった。

乗算はチャンネルを掛けるだけなので、草は自分のテクスチャを保ったまま、この層が遮った光ぶんだけ
暗くなる。そのためテクスチャの色を暗い側から**明るい青**へ反転させた——乗算では「影が何色か」では
なく「光が何になるか」を指定するため、白に近いチャンネルは残り、暗いチャンネルは消える。最初は
`rgba(128, 168, 248)`（赤を約0.5・緑を約0.65まで落とし青をほぼ残す）で試したが、これは薄すぎた。
乗算下では地面のテクスチャが残るぶんコントラストが削られるため、最終的に `rgba(36, 84, 196)` まで
暗い側へ寄せ直している。**テクスチャの色と `blendMode` は必ず一緒に変える必要がある**（片方だけ
変えると影が明るい斑点に反転する）。

グラデーションの芯も広げた（60%地点で半分だったのを55%までほぼ全力）。従来は明るい芯と長く薄い
裾で、画面に映るのはほとんど裾だった。芯を広げるほうが、色を暗くするより効いた。

`CLOUD_ALPHA_MAX` は 0.28 のまま触っていない（`clouds.test.ts` の「0.3未満」は依然として機能している）。

### 形も単一の真円のままだと反復が見えた（真円→複合シルエット3種）

個数を増やすほど「同じ判子」であることが分かってしまう。大きな塊1つに小さな塊を偏らせて重ねた
複合シルエットを3種用意し、重なりを素直に濃くした（輪郭だけでなく密度にもムラが出る）。雲ごとに
index固定で割り当てているので、プールが増えても同じ雲は同じ形のまま変わらない。

3種にとどめたのは、反復が直したい対象だから0では困るが、雲は数分おきに・移動しながら・別の縮尺で・
昼夜のティント越しに見えるものなので、数種を超えるとシルエットを見比べる人がいないため。

**この過程で自分が入れた不具合を1つ直した記録**：複合形状の初版は塊の半径をテクスチャの正規化座標
（0..1）で最大0.28に収めており、テクスチャの中央にしか広がっていなかった。`syncClouds` は
「256px = radius×2タイル」としてスプライトを拡大するので、`CLOUDS` 表の `radius` はそのままなのに
実際に描かれる影は半分以下に縮み、画面からほぼ消えていた——**指定した値と実際に見えるものが食い違う、
プレイヤーに見えない失敗**の一種（`CLAUDE.md` が名指ししている失敗パターンそのもの）。塊が0.95付近
まで届くよう作り直して直した。

design.md 11章「雲の影（#15）」をこの最終形へ更新した。

## 風と雲で同じ失敗を2回出した（→ issue #30）

風（#23）と雲の影（#15の積み残し）は、どちらも同じ形の失敗をたどった：コードは正しく、`npm test`
は緑で、既存テストは値域・純粋性・折り返しの連続性・乱数の不使用をすべて固定していたが、
**「プレイヤーの目に実際に入るか」だけを誰も測っていなかった**。風は初版が一度も画面に出ず、
雲の影はフェーズ6の地図拡大（60×60→120×120）に個数の表が追随せず、6回に5回何も見えていなかった。
どちらも直したのはロジックではなく数値（個数・大きさ・速さ・濃さ・合成方法・形）だけだった。

この教訓（「機能として存在するかは機械的なテストだけでは検証できない」）への対応そのものは本チケットの
範囲外とし、**GitHub issue #30 として起票済み**。ここには経緯のみを記録し、対応は #30 に委ねる。

## 描画層の画面占有率（#30）

### 測っていなかったのは1つだけだった

`clouds.test.ts` は値域・純粋性・折り返しの連続性・乱数の不使用をすべて固定していた。
固定していなかったのは「**プレイヤーの目に入るか**」だけで、そこが抜けている限り
「コードは正しく、テストは緑で、数値のせいで存在していない」が通ってしまう。

`src/render/screenCoverage.ts` がその欠けていた測定。時間変化する円の集合を視界窓
（16×14タイル）で走査し、閾値を超える要素が窓に触れている時間の割合を返す純関数。
**雲にも風にも依存しない**。風の帯（有向の長方形）は「幅/2 を半径とする円を長軸に
沿って並べたカプセル」として渡す —— 外接円で近似すると短軸方向を大きく過大評価する。

### 途中で main と衝突し、こちらの実装を捨てた

この作業の途中で main 側に #15 の積み残し（雲を5→36個、乗算合成、複合シルエット）と
#23（風）が入った。こちらは「枚数を面積から導く」実装を先に書いていたが、**main 側を
全面採用してこちらを捨てた** —— main の変更は実ビルドを見ながら色・濃さ・大きさ・
シルエットを詰めたもので、机上の構造改善で潰してよいものではない。

そのうえで、構造の側だけを入れ直した。**基準面積（120×120）ちょうどでは表をそのまま
返す分岐**を持たせてあるので、`frontier` の出力はこの変更の前後で1ビットも変わらない。
変わるのは 120×120 **以外**の寸法だけ。これはテストで固定してある（マージ前のコードの
出力と deep-equal で比較して確認した）。

### 指標が入った初日に、指標が問題を見つけた

`MAP_SIZES` は `vale: 60` と `frontier: 120` の**2つとも出荷されている**（プレイヤーが
TopBar で選べる）。main の36個の表は 120×120 に手で合わせてあり、`vale` に追随していない。
測ると **60×60 の雲は 99.6%** —— つまり**常時曇天**で、main 自身が `clouds.ts` の
コメントに書いている意図（"90% is deliberately not 100%: ... not permanent overcast"）に
反していた。**#30 が問題にしているのと同じ構造の不具合が、逆向きに出ていた**。

| 地図 | 雲（前→後） | 雲の枚数 | 風（前→後） | 風の本数 |
| --- | --- | --- | --- | --- |
| 60×60（`vale`） | 99.6% → **66.4%** | 36 → 9 | 85.2% → **41.6%** | 10 → 3 |
| 120×120（`frontier`） | 88.0% → 88.0%（不変） | 36 → 36 | 45.8% → 45.8%（不変） | 10 → 10 |
| 180×180（非出荷） | 65.2% → **86.8%** | 36 → 81 | 26.1% → **50.8%** | 10 → 23 |

測定条件: 視界窓 16×14 タイル、閾値 0.02、20分ぶんを5秒間隔、窓位置を8タイル刻み。

表より少ない枚数を採るときは**等間隔に間引く**。先頭 N 個ではない —— 表は
「小さいもの → 大きいもの → 巨大な塊 → 埋め」の順に並んでいるので、先頭を取ると
**大きい雲が全部消えて小さいものばかりになる**。多いときは表を巡回し、周回ごとに
決定論的なオフセットを足す（乱数は使わない）。

### 上限をテストにした

「常時曇天にはしない」は main のコメントには書かれていたが、**どこにも測られていなかった**。
下限だけでは 99.6% を捕まえられない。雲は下限 0.55・上限 0.95、風は下限 0.38・上限 0.75。

テストは寸法を直書きせず **`MAP_SIZES` から駆動する**。これが issue の
「将来また地図サイズが変わったとき気づかせる」への答えで、寸法が足された瞬間に
その寸法も自動で測られる。180×180 を直書きしていたら、出荷されない寸法の面倒を
見続けることになっていた。

### 合成のモデルが間違っていた（自分で作った誤り）

枚数が増えると重なりが普通に起きるので、合成後の暗さに上限を置いた。最初これを
**アルファ合成のモデル**（`1 - Π(1 - alphaᵢ)`）で書いたが、main は雲を
`blendMode: 'multiply'` ＋ 色 `rgba(36, 84, 196)` で描いている。乗算では channel ごとの
透過率が `1 - (1 - c/255)·a` で、Rec.709 の輝度重みで畳むと **1層あたり `1 - 0.679a`**。

誤ったモデルでは最悪値が 0.44〜0.46 と出て「夜（`NIGHT_ALPHA` = 0.45）に届いている」と
読めたが、正しいモデルでは **0.21〜0.39**（120×120 で 0.319）で、**main の濃さの調整は妥当**
だった。テストが赤いとき、疑うべきが実装とは限らない。係数 0.679 はコード内で色から
計算していて、`renderer.ts` の色を変えれば追随する。

### 修正前のパラメータは、条件ごとテストの中に残した

「修正前を通すと下限を割る」テストは、当時の `WRAP_MARGIN_TILES`（雲は14、風は12）と
当時の強度をリテラルで持って**自己完結**させてある。最初は現在の `clouds.ts` から
定数を import していたが、main が 14 → 28 に変えた瞬間に測定値がずれて落ちた
（18.1% → 13.95%）。**測定記録は、それを測ったときの条件ごと持っていなければ記録にならない。**

## 狭い幅で盤面が潰れる（#26）

### 制約は「盤面の面積」だと決めた

幅だけを見ていると、ツールバーが2行3行に折り返して**高さ**を食っている分を取りこぼす。
実測すると 640×480 では折り返しが4行（134px）まで伸びていて、そちらの寄与の方が大きかった。
なので判定は一貫して**面積比**（`.app__viewport` の面積 ÷ ビューポートの面積）で行う。

実ブラウザ実測（Chromium、Playwright）:

| ビューポート | 修正前 ツールバー / 盤面 | 修正後 ツールバー / 盤面 | サイドバー |
| --- | --- | --- | --- |
| 1024×768 | 88px・3行 / **40.1%** | 44px・1行 / **70.3%** | 左は常設、右はドロワー |
| 800×600 | 134px・4行 / **23.3%** | 44px・1行 / **62.5%** | 左は常設、右はドロワー |
| 640×480 | 134px・4行 / **9.0%** | 44px・1行 / **90.8%** | 両方ドロワー |
| 1440×900 | —— | 44px・1行 / 58.1% | 両方常設 |
| 1920×1080 | —— | 45px・1行 / 67.9% | 両方常設 |

**1024 の時点で既に過半を割っていた**（40.1%）。issue の「800px を下回るあたりから顕著」は
体感の話で、数字の上ではもっと手前から負けている。

### 外すのではなく、重ねる

常設をやめたサイドバーを**消す**と、狭い画面ではツールバーに二度と手が届かない。
`position: absolute` のドロワーにして盤面の上に重ねると、閉じている間は盤面の幅を1pxも
取らず、開けば全幅で使える。つまり `layoutFor` の判定は**盤面の面積を増やす方向にしか
動かない**ので、「畳んだせいで別のところが狭くなる」が構造的に起きない。

右から先に外すのは、右が「開いて読む」パネル群（入植者・仕事・研究・動物・ログ）で、
左の建築ツールバーより手放す損が小さいから。フェーズ6の「目は地図、答えは右端」の分類が
そのまま優先順位になる。

### 純関数のテストでは足りなかった —— 実ブラウザが2件捕まえた

`layoutFor` の単体テストは全部緑のまま、実ブラウザで**2件の実害**が出た。
どちらも「モデルの中では正しいが、ページの上では壊れている」種類のもの。

1. **「…」メニューの閾値が低すぎた。** 当初 900px にしていたが、実測すると畳まない
   ツールバーは **1811px** ないと収まらず、畳んでもなお ~983px 要る。つまり 1024 でも
   800 でも溢れていて、**「…」ボタン自体が画面の外にいた**。閾値を 1850 に上げ、
   `.topbar__jobs` を省略記号で詰まるようにして解いた
2. **ドロワーに位置の基準が無かった。** `position: absolute` の祖先に `position` が
   無く、`top: 0` がページ全体を基準に解決されて、ドロワーが `.topbar` の下に潜り込んで
   いた。`.app__body { position: relative }` で解いた

### 閉じたドロワーがページの幅を300px伸ばしていた

親のレビューで見つけた3件目。閉じたドロワーは `translateX(100%)` で画面の外に停めてあるが、
これは**ページの `scrollWidth` を右サイドバーの幅ぶん（300px）伸ばす** ——
右がドロワーになるすべての幅で `body.scrollWidth - innerWidth === 300` を実測した。

今は `body { overflow: hidden }` がたまたま隠しているので実害は出ていない。ただ
「たまたま隠れている」は保証ではなく、body の overflow を将来触った瞬間に 300px の
死んだ帯が現れる。停めてあるドロワーは、そもそもページの幅の一部であってはいけない。
ドロワーの基準ブロック側（`.app__body`）に `overflow-x: clip` を置いて解いた
——`hidden` ではなく `clip` なのは、`hidden` だとここがスクロールコンテナになり、
サイドバー自身の `overflow-y: auto` の効き方が変わるため。修正後は5つの幅すべてで
`body.scrollWidth - innerWidth === 0`、開いたドロワーは従来どおり全幅で画面内に収まる
（800×600 の右ドロワー x=500..800、640×480 の左ドロワー x=0..260 を実測）。
