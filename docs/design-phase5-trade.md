## 1. 位置づけ — なぜ交易が本編の土台を壊さないか

**[design-next.md](design-next.md) の 9 章は「複数マップ・キャラバン・貿易・研究ツリー」を提案しないものとして挙げている。**
理由は「どれも『1枚の地図の上の最適化パズル』という土台を変える」だった。この判断を全部は撤回しない ——
**壊すのは「こちらから出ていく」ほうだけ**である、というのが本設計案の出発点。

| 形 | 何が要るか | 判断 |
| --- | --- | --- |
| キャラバン（入植者が地図の外へ出て交易する） | 世界地図・地図間の時間・不在中の植民地・帰還の解決 | **採らない**（土台を変える） |
| 行商（商人が地図の端から来て、去る） | **来訪の規則ひとつ**。既存の移住者とまったく同じ形 | **採る** |

`runArrivals` は「スケジュールは tick の関数、条件は在庫の関数、保存する状態は無し」で成立していて、
地図は1枚のまま、外の世界は**在庫から導かれる圧力**としてしか存在しない。行商はその2つ目になる ——
移住者が「食べていける植民地には人が来る」なら、行商は「**灯りのついた植民地には物が来る**」。
どちらも外の世界を実体として持たない。

**本編の設計原則との整合**:

- 原則1（データとロジックの分離）: 追加する型はプレーンデータ・ID 参照のみ。`Trader` は座標と期限と品揃えだけを持つ
- 原則2（シミュレーションと描画の分離）: 商人は `GameState` に載るだけ
- 原則3（土台が回ってから積む）: 交易は既存の運搬・貯蔵・予約の**上に**載り、そのどれも改造しない
- 原則4（主張する前に測る）: 本書の数値は**すべて未実測の出発点**であり、段階ごとに測って直す

## 2. いまの世界が「ファンタジー」に見えない理由

[design.md](design.md) の 1 章はこう始まる ——「SimWorldは、**ファンタジー世界観**の入植地シミュレーションである」。
ところが実装されている世界の中身を並べると、そうは読めない。

| 層 | 中身 | 幻想的か |
| --- | --- | --- |
| 地形 | 草地・森・岩 | いいえ |
| 植生 | 草・木・ベリーの茂み | いいえ |
| 動物 | 鹿・猪・兎・鶏・山羊・狼 | いいえ |
| 資源 | 木材・石・食料 | いいえ |
| **マナ結晶と魔力インフラ** | 結晶・魔導炉・導管・魔力灯 | **はい** |

**幻想的なのは魔力インフラだけで、それ以外は中世の農場である。** マナ結晶は 1 本だけ立った柱で、
生態にも植生にも接していない —— 光る石を掘って燃やすと灯りがつく、というだけで、
世界の他の部分はそれを知らない。

そこで本設計案の方針は「**ファンタジー生物を賑やかしとして足す**」ではなく、
**既に世界にあるただ一つの幻想要素（マナ）を、生態と植生に接続する**こと。
追加する4種はどれも、マナか季節か岩という**既存の仕組みに噛み合う**形にしてある。

## 3. ファンタジー層: 追加する4種

選定の基準は「**実測で分かっている穴を塞ぐこと**」。飾りとして足したものは1つも無い。

| 追加 | 塞ぐ穴（出典） | 曲げる既存の数値 |
| --- | --- | --- |
| **霜花**（frostbloom） | 冬に食料が 1506 → 934 まで落ちる（notes「1年放置の実測」） | `CROP_GROWTH_BY_SEASON` |
| **光苔**（glowmoss） | 冬は草が戻らず、囲った群れが打つ手なく餓える（design-phase2.5-animals 12章） | `Tile.forage` |
| **晶角鹿**（crystal elk） | マナが唯一再生しない資源（design-next 1.2） | `SpeciesProfile` の1行 |
| **岩喰い**（rockeater） | 鉱脈は岩の奥で到達不能／外圧が狼1種しかない | `gnawStructure` |

### 3.1 霜花 — 冬にだけ咲く

**規則は1つ**: 他のすべての植物と成長の季節が逆。`CROP_GROWTH_BY_SEASON` は
`{ spring: 1, summer: 1.25, autumn: 0.7, winter: 0 }` なので、霜花はこの表を**反転して引く**
（冬 1.0、他 0）。新しい仕組みは要らず、参照する表を変えるだけ。

野生の茂みとしてベリーと同じ方式で地図に撒く（`scatterBerryBushes` と同型。岩の近くの草地に 14 株、
見積もり）。収穫は `food`。**新しい資源型は増やさない**（design-phase2.5-animals 2 章の判断をそのまま踏襲）。

これで冬は「何も起きず備蓄が減るだけの5日間」ではなくなる。**冬にしかできない仕事**が1つできる。

### 3.2 光苔 — 灯りの下に生える

**規則は1つ**: 供給の通った魔力灯の半径（`LAMP_RADIUS` = 6）内のタイルは、季節に関係なく
`Tile.forage` が回復する。草地でなくてもよい（石床の上にも生える）。

`forage` は既に存在するフィールドで、放牧・過放牧・飼い葉のパズルはすべてその1つの値で成立している。
光苔は**新しい資源でも新しいアイテムでもなく、既存の値が回復する条件をもう1つ足すだけ**。

効果は大きい。design-phase2.5-animals 12 章が記録しているとおり、冬に草が戻らないせいで
「囲った群れがプレイヤーの打つ手なく餓死していた」という穴があり、飼い葉はその応急手当だった。
光苔は**灯りの下でだけ冬に放牧できる**ようにする —— つまり魔力灯が、気分 +5 だけの装飾から
**冬を越すための設備**になる。フェーズ2が初めて生産チェーンに触れる。

### 3.3 晶角鹿 — 角がマナを結ぶ

`SPECIES` テーブルの**1行**。鹿より遅く、体力は低く、手懐けは難しく、肉は少ない。
その代わり、家畜化すると **`food` ではなく `manaCrystal` を産む**。

現在の産出は `addItem(state, 'food', profile.produceAmount, ...)` と資源型が固定されているので、
必要な差分は `SpeciesProfile.produceType: ResourceType` の**1フィールドだけ**（既存6種はすべて `'food'`）。

これは design-next.md 1.2 が挙げた「マナは唯一再生しない資源」への**部分的な**答えになる。
部分的、というのが重要で、意図的にそうしてある（→ 9 章）。

### 3.4 岩喰い — 岩を食う

草食でも肉食でもない3つ目の食性（`lithovore`）。岩を齧って進み、齧り終えたタイルは
採掘したときと同じく開けた地面になる。**捕食者が扉を齧る `gnawStructure` がそのまま使える** ——
対象が建築か地形かの1分岐だけが増える。

- 遅い。齧るのも遅い（岩1タイルに実時間で数分、見積もり）
- 入植者も家畜も襲わない。**脅威ではなく地形の変化**である
- 石壁も齧る。石壁を建てた側からすると害獣で、**柵の維持がもう1つ意味を持つ**
- 齧った先が鉱脈だった場合、**掘らずに鉱脈が露出する**

最後の1点が狙いで、design-notes.md がマナ結晶について書いた「掘って取りに行くもの」という性質は
維持したまま（岩喰いは制御できない）、**たまに向こうから開いてくれる**という物語が生まれる。
段階C（自動採掘）が「機械が掘る」なら、岩喰いは「**生き物が勝手に掘る**」で、
どちらが先でも互いを壊さない。

## 4. 交易層: 誰が来て、何をどう交換するか

### 4.1 来訪者は2層

移住者と同じく、**スケジュールは tick の関数、条件は状態の関数**で、保存するスケジュールは持たない。

| 訪問者 | 来る条件 | 品揃え |
| --- | --- | --- |
| **行商人**（pedlar） | 交易柱があり、食料に余剰がある（移住者と同じ形） | 木材・石・食料 |
| **晶商**（crystal factor） | 上記 **＋ 供給の通った魔力灯が1つ以上ある** | 上記＋マナ結晶・晶角鹿・霜花の苗 |

**灯りは条件ではなく格上げである。** ここは一度間違えかけた設計で、記録しておく ——
「灯りのある植民地にだけ商人が来る」にすると、鉱脈ゼロの世界（1.5%、design-next 1.1）は
**灯すためのマナを買うために灯りが要る**という閉じた輪に入る。基本の行商人は食料だけで来るようにし、
灯りは頻度と品揃えを上げるだけにすることで、輪が開く。

冬にも来る。移住者は冬に来ない（「凍った地図を渡って来る者はいない」）が、**商人は逆**にした ——
冬は畑も草も止まり、やることが最も少ない季節なので、そこに交易を置くと年の形が変わる。
霜花（3.1）と合わせて、**冬が「耐える季節」から「別のことをする季節」**になる。

### 4.2 交易柱と、既存の運搬の再利用

`tradingPost`（交易柱）を建てると、そこが商人の立ち位置になる。**商人は歩かない** ——
柱の隣に現れ、期限まで立ち、消える。経路探索を一切しないので、design-phase2.5-animals 7 章が定めた
A\* 予算の話に**一切影響しない**。

取引の物理は、design-notes.md が魔導炉の燃料補給について書いた形をそのまま使う ——
「**ブループリントへの資材運搬とまったく同じ haul ジョブで、行き先が完成済みの建物なだけ**」。

```
プレイヤーが取引を確定
  → 差し出す品に haul ジョブが立つ（行き先＝交易柱）
  → 運び込まれた時点で、対価が交易柱の足元に落ちる
  → 既存の haul ジョブが貯蔵まで運ぶ
```

新しいジョブ種別は**増えない**。仕事優先度表は 7 列のまま。そして取引を成立させる仕事は
**他のあらゆる運搬と同じ優先度列で競合する** —— 運搬を最低優先度にした植民地では、
商人が去るまでに荷が届かず取引が流れる。これはバグではなく、フェーズ2の燃料補給と同じ設計意図である。

### 4.3 物々交換にする（通貨を作らない）

`ResourceType` に通貨を足さない。理由は2つ。

1. **通貨は「今売って後で買う」を可能にし、決断を先送りにできてしまう。** 物々交換だと
   「いま何を手放せるか」が毎回の問いになり、これは既存の貯蔵・運搬パズルと同じ質の問い
2. 通貨を足すと価格・インフレ・残高表示が付いてくる。**得るものに対して機構が増えすぎる**

代わりに資源ごとの**基準価値表**を置き、商人ごとに幅を持たせる。買値と売値には差（スプレッド）を付ける ——
交易が損失を伴わないと、余った木材を無限にマナへ変換する機械になるため。

### 4.4 価格の決まり方

乱数は incidents と同じ規律に従う ——**tick と世界シードの両方**から導く。tick だけだと
これまでに始まった全ての植民地が同じ相場を共有し、世界シードだけだと相場が動かない。
セーブを読み直せば同じ商人が同じ品を同じ値で持ってくる（テストで固定する）。

## 5. データモデル

本編 4 章の原則（メソッドを持たない、参照は ID、`Record` と配列とプリミティブのみ）を踏襲する。

```typescript
type TraderId = string;

type TraderKind = 'pedlar' | 'crystalFactor';

/** 商人が今回の来訪で扱う1品目。数量は在庫、rate は資源1あたりの基準価値に対する倍率 */
interface TradeOffer {
  resource: ResourceType;
  quantity: number;
  rate: number;
}

interface Trader {
  id: TraderId;
  kind: TraderKind;
  name: string;
  /** 交易柱の隣。到着後は動かない（4.2） */
  position: Vector2;
  /** この tick を過ぎたら立ち去る */
  departsAtTick: number;
  /** 商人が渡せるもの */
  offers: TradeOffer[];
  /** 商人が受け取るもの（受け取らない資源は並ばない） */
  wants: TradeOffer[];
}
```

`GameState` への追加は **1つだけ**。

```typescript
interface GameState {
  // ...既存に加えて
  traders: Record<TraderId, Trader>;
}
```

既存型への追加（すべて `[ext]` コメントを付す。本編 4 章と design-phase2.5-animals 2 章と同じ運用）:

| 型 | 追加 | 理由 |
| --- | --- | --- |
| `BuildingType` | `tradingPost` / `frostbloom` | 交易柱と霜花の茂み。既存の建築テーブル3つ（コスト・HP・通行）に行が増えるだけ |
| `AnimalSpecies` | `crystalElk` / `rockeater` | `SPECIES` テーブルに2行 |
| `SpeciesProfile` | `produceType: ResourceType` | 産出の資源型が `'food'` に固定されている（既存6種はすべて `'food'`） |
| `SpeciesProfile` | `diet` に `'lithovore'` | 岩喰いの食性 |
| `Job` | 追加なし | 取引は既存の `haul` で成立する（4.2） |
| `JobType` | 追加なし | 仕事優先度表は 7 列のまま |

**`ResourceType` は増やさない。** 交易も霜花も、既存の4資源だけで成立する。

## 6. バランス初期値

**すべて未実測の出発点**であり、段階ごとに測って直す。

### 6.1 基準価値とスプレッド

| 資源 | 基準価値 |
| --- | --- |
| 木材 | 1 |
| 石 | 1 |
| 食料 | 2 |
| マナ結晶 | 12 |

商人は基準価値の **0.7 倍で買い、1.4 倍で売る**。木材 120 を出してマナ結晶 5 個、という程度
（120 × 1 × 0.7 ÷ (12 × 1.4) = 5.0）。1本の鉱脈が 6 個であることを思うと、
**交易は鉱脈の代わりにはならず、足りない分を埋める**位置になる。

### 6.2 来訪

| 項目 | 値 | 意図 |
| --- | --- | --- |
| 判定間隔 | 5日ごと | 移住者（3日）より稀 |
| 滞在 | 1日（3,000 tick） | 運搬が間に合うかどうかが問われる長さ |
| 食料の条件 | 移住者と同じ `ARRIVAL_FOOD_PER_COLONIST` を流用 | しきい値を2つ持たない |
| 冬 | **来る** | 移住者と逆（4.1） |
| 晶商の追加条件 | 供給の通った魔力灯 1つ以上 | フェーズ2の2つ目の見返り |

### 6.3 追加する4種

| 種 | 主な数値（見積もり） |
| --- | --- |
| 霜花 | 地図に 14 株。成長は冬のみ。収穫 `food` 7（ベリー 9 より少ない） |
| 光苔 | 灯りの半径6内で `forage` が回復。速さは草地の 0.6 倍。季節を見ない |
| 晶角鹿 | 3 tick/マス・体力 40・肉 18・手懐け 0.25・成体まで3日・初期数 3。産出 `manaCrystal` 2 / 2,400 tick |
| 岩喰い | 4 tick/マス・体力 90・肉 0・手懐け不可・初期数 2。岩1タイルに 900 tick |

晶角鹿の産出は **1日あたり 2.5 個**（3,000 ÷ 2,400 × 2）で、魔導炉1基の消費（約 1.5 個/日）を
1頭で上回る。**上回りすぎているかもしれない** —— これは測って下げる候補の筆頭で、
受け入れ条件（7 章）に「1頭で炉を賄えないこと」を入れてある。

## 7. 段階と「動いたと言える条件」

本編 10 章と design-phase2.5-animals 10 章と同じく、段階ごとにコミットとテストを完結させる。
**幻想層（F）と交易層（T）は依存しないので、並行して進められる。**

| 段階 | 内容 | 動いたと言える条件 |
| --- | --- | --- |
| **T-A** | 交易柱・行商人の来訪と退去・物々交換（既存4資源） | 柱を建てて余剰があると商人が現れ、木材を出して食料を得られ、1日で去る |
| **T-B** | 晶商・マナ結晶の売買 | 魔力灯が点いている植民地にだけ晶商が来て、結晶を買える。灯りが無くても行商人は来る |
| **F-A** | 霜花 | 冬にだけ育ち、冬に収穫でき、収穫量がベリーを上回らない |
| **F-B** | 光苔 | 灯りの下で冬に放牧できる。灯りを消すと `forage` の回復が止まる |
| **F-C** | 晶角鹿 | 手懐けると `manaCrystal` を産み、既存の運搬で倉に入る |
| **F-D** | 岩喰い | 岩を食べて地形が開く。石壁も齧る。鉱脈に当たると露出する |

### テスト方針（既存のヘッドレステストに追加）

- **T-A**: 商人が去るまでに荷が届かないと取引が流れる（運搬優先度を最低にして確認する）
- **T-A**: 商人が去った後にジョブ・予約・運搬中の荷が取り残されない（`death.test.ts` / `zones.test.ts` と同じ形の後始末検査）
- **T-A**: セーブを読み直すと同じ商人が同じ品を同じ値で持ってくる
- **T-B**: 鉱脈ゼロの世界でも交易でフェーズ2に入れる／灯りが無くても行商人は来る（4.1 の輪が開いていること）
- **F-A**: 霜花は冬以外に育たない／1年通した食料の総量が、霜花なしより増えるが畑を上回らない
- **F-B**: 灯りの下の囲いが冬を越せる／灯りを消すと越せない
- **F-C**: **晶角鹿1頭では魔導炉1基を賄えない**（6.3 の懸念を明示的に固定する）
- **F-D**: 岩喰いが石壁を齧る／入植者と家畜を襲わない／地形が開いた後の到達可能領域ラベルが正しく再構築される
- **性能**: 商人は経路探索をしない。岩喰いを含めても 1 tick あたりの A\* 実行本数が既存の上限を超えない
- **1年計測**: 交易も幻想層も使わない植民地の1年計測が、導入前と一致する

## 8. セーブ互換・性能方針・アセット

**セーブ**: `schemaVersion` を**実装した時点の値に1を足し**、対応する移行を1段足す
（本書の執筆時点では 11 → 12 だが、フェーズ6も同じことを言うので、先に実装されたほうが 12 を取る。
現在値は `src/persistence/saveFile.ts` を見ること）。補うのは `traders: {}` のみ。新しい `BuildingType` と `AnimalSpecies` は

design-notes.md が `MANA_OUTPUT` / `MANA_DRAW` について書いた判断と同じ）。

**性能**: 商人は動かないので経路探索をしない。岩喰いは既存の動物と同じ

`forageDepleted`（既存の派生キャッシュ）と同じく**変化のあったタイルにしか触らない**。

決定論生成）を踏襲。追加は約 7 枚（交易柱・霜花2段階・光苔・晶角鹿・岩喰い・商人）。
商人は入植者の歩行スプライトを色替えで流用する（本編 12 章の個体差の方式）。

## 9. 提案1（燃料の持続性）との相互作用

本設計案は [design-next.md](design-next.md) の**提案1を置き換えない**。ここは誤解しやすいので明示する。

交易（T-B）と晶角鹿（F-C）は、どちらもマナの**再生経路**になる。すると
「もう提案1の下限保証も再生規則も要らないのでは」と読めるが、**要る**。

| 経路 | 何を要求するか | 鉱脈ゼロの世界で使えるか |
| --- | --- | --- |
| 晶商から結晶を買う | 交易柱＋食料の余剰 | **使える**（灯りは条件でなく格上げ、4.1） |
| 晶角鹿を飼う | 牧場＋手懐け＋世話 | **使える** |
| 提案1(a) 生成時の下限 | なし | — |
| 提案1(b) 鉱脈の再生 | なし | — |

交易と晶角鹿は**プレイヤーが動いて初めて手に入る**もので、しかもどちらも
「植民地が既に食料と牧場を回している」ことを前提にする。序盤にそこへ到達できなかった植民地は、
依然としてフェーズ2に触れないまま終わる。**提案1(a) の下限保証は、交易が入っても最も安い保険のまま**である。

一方 **提案1(b)（鉱脈の再生）は、本設計案が入るなら優先度を下げてよい** ——
再生経路が2つできるので、地形そのものを再生させる必要は薄れる。
（この判断は F-C の実測後に確定させる。晶角鹿の産出が 6.3 の懸念どおり強すぎた場合、
下げた結果として (b) がまた必要になりうる。）

**依存順**: T-B は魔力灯を条件に使うのでフェーズ2 段階B（実装済み）が前提。F-B も同じ。
段階C（自動採掘）とは互いに前提を持たない。

## 10. リスクと非目標

| リスク | 対策 |
| --- | --- |
| 交易が「余った木材をマナに変える機械」になる | 買値と売値のスプレッド（6.1）。交易は損失を伴う |
| 晶角鹿がマナの希少性を壊す | 産出を炉の消費より下に置く。受け入れ条件で明示的に固定（7 章 F-C） |
| 鉱脈ゼロの世界が交易でも救われない | 灯りを条件ではなく格上げにして輪を開く（4.1） |
| 商人が去った後に荷とジョブが残る | ゾーン撤去・入植者の死と同じ後始末検査を書く（7 章 T-A） |
| ファンタジー要素がただの賑やかしになる | 4種すべてを「実測で分かっている穴」に紐付けた（3 章）。紐付かないものは足さない |
| スコープ膨張 | 下記の非目標を守る |

**非目標（この段階では入れない）**:

- **キャラバン・世界地図・地図の外への移動**（1 章。土台を変える）
- **通貨・銀行・価格の履歴**（4.3）
- **商人との評判・派閥・関係値**（物語生成の領域。まず取引が成立してから）
- **研究ツリー**（design.md 9 章の非実装リストのまま）
- **魔法の詠唱・呪文・戦闘魔法**（戦闘はフェーズ4。マナは今のところ**インフラであって武器ではない**）
- **知性のある種族（エルフ・ドワーフ等）との交渉**（商人は品揃えを持った来訪者であって、対話相手ではない）
- 新しい `ResourceType`・新しい `JobType`（5 章）
