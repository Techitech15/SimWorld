## 1. 位置づけ — 文字列は3系統に散っている

i18n の仕組みは現在**一切存在しない**（`i18n` / `locale` / `translation` に該当する識別子は 0 件）。
プレイヤーが読む英語は、調査の結果 **3系統**に分かれて存在する。系統ごとに寿命と置き場所が違うので、
翻訳のやり方も系統ごとに変える必要がある。

| 系統 | 例 | 特徴 |
| --- | --- | --- |
| ① JSX 直書き | `<h3>Build</h3>`（`Toolbar.tsx:71`）、操作ヒント段落（`Toolbar.tsx:108-115`） | 静的。表示の瞬間にしか存在しない |
| ② 散在するラベル表 | `RESOURCE_LABELS`（`constants.ts:158`）、`SKILL_LABELS`（`skills.ts:34`）、`TRAITS[*].label`（`traits.ts`）、`BUILDING_LABEL`（`SelectionPanel.tsx:15`）ほか計 12 表 | 半ば整理済み。ただし**表ごとに置き場所が違い、建物名は2箇所で別の名前**（Toolbar は `'Wall'`、SelectionPanel は `'Wooden wall'`） |
| ③ コアが組み立てる英文 | `addLog` 33箇所（調査時点）、`alerts.ts` のアラート文、`goals.ts` の目標文、`gameStore.ts` の状態メッセージ | **動的**。`plural(count, 'colonist is', 'colonists are')` のように英語の文法が関数シグネチャに入り込んでいる |

系統③のうち**ログだけが特別**である。アラートと目標は毎回状態から導出されるので保存されないが、
ログ（`GameState.log`）は組み立てた英文がそのまま**セーブに入る**。ここが 3 章の主題になる。

## 2. 方針 — 言語は表示の性質であって、ゲーム状態ではない

### 2.1 言語設定は `GameState` に入れない

言語を変えてもシミュレーションは1 tick も変わらない。したがって言語は
フェーズ6のサイドバー開閉と同じ扱いにする —— **`localStorage` に置き、セーブと移行の対象にしない**。
同じセーブを英語でも日本語でも開けるし、セーブに言語の痕跡は残らない。

初期値は `navigator.language` が `ja` で始まれば日本語、それ以外は英語。判定はこの1行だけで、
地域別の凝った解決はしない。

### 2.2 ライブラリは入れない

i18next 等が解く問題（複数形規則・書式・辞書の遅延読み込み・翻訳ワークフロー）は、
**2言語・数百キー・全文字列同梱**（単一 HTML ビルドが前提）のこの規模ではほぼ発生しない。
代わりに TypeScript の型で完全性を強制する:

```typescript
// すべてのキーを列挙するインターフェース。en と ja の両方がこれを実装する
interface Strings {
  buildMenuTitle: string;
  // パラメータを持つ文言は関数。語順と単複の差は辞書の側に閉じる
  populationLabel: (count: number) => string;   // en: '3 colonists' / ja: '入植者 3人'
  // ...
}
const STRINGS: Record<Language, Strings> = { en: {...}, ja: {...} };
```

**訳し漏れは実行時ではなくコンパイルエラーで捕まる。** `plural()` のような英語文法のヘルパは
辞書の `en` 側の実装詳細になり、コアと UI から消える。

### 2.3 辞書は1つ、ラベル表12個を吸収する

系統②の 12 表は辞書に統合する。これは翻訳のためだけでなく、既にある不具合の種を消す ——
建物名が `Toolbar.tsx` と `SelectionPanel.tsx` で**別々に定義されて食い違っている**
（`'Wall'` / `'Wooden wall'`）。辞書化すると定義は1箇所になり、この食い違いは型ごと消える。

固有名詞（入植者名・動物の個体名）は翻訳しない。`deaths[].name` も同様。

## 3. 核心の設計判断 — コアは文章を作らない

現在、コア（`alerts.ts` / `goals.ts` / `addLog` 呼び出し元）は**英語の文章を組み立てて返す**。
これを「**キーとパラメータを返し、文章は表示の瞬間に導出する**」に変える。

| 対象 | 保存されるか | 変更 | 言語切替で |
| --- | --- | --- | --- |
| アラート | されない（毎 tick 導出） | `message: string` → `{ key, params }` | **既に出ているアラートも即座に翻訳される** |
| 目標 | されない（同上） | 同上 | 同上 |
| 状態メッセージ | されない | 同上 | 同上 |
| **ログ** | **される**（`GameState.log`、100件リングバッファ） | `LogEntry` を構造化（4 章） | 新しいエントリは翻訳される。**過去のエントリは原文のまま** |

これは翻訳のための都合ではなく、既存の原則の適用である —— **「導出できるものは保存しない」**
（design.md 4 章）。保存すべきは出来事（何が・誰に・いつ）で、文章はそこから導出できる。
現在のログは導出値（英文）を保存しているので、原則の側に寄せる。

**過去のエントリを翻訳しないのは手抜きではなく判断である。** 保存済みの英文を構文解析して
出来事に逆変換する処理は、書けるが必ず漏れる。移行は旧エントリを
`{ key: 'legacy', params: { text } }` に包み、原文のまま表示する。100件のリングバッファなので
数日分のプレイで自然に押し出される。

## 4. データモデル

`GameState` に増えるフィールドは**無い**。変わるのは `LogEntry` の中身だけ。

```typescript
type Language = 'en' | 'ja';
// localStorage キー 'simworld.language'。GameState には入れない（2.1）

// 変更前: interface LogEntry { tick: number; message: string; kind?: 'incident' }
// 変更後:
interface LogEntry {
  tick: number;
  kind?: 'incident';                             // 既存のまま。襲撃などの行の別表示に使う
  key: LogKey;                                   // 'skillLevelUp' | 'raidArrived' | ... | 'legacy'
  params?: Record<string, string | number>;      // { name: 'Ash', skill: 'mining', level: 3 }
}
```

- `LogKey` は文字列 union。`Strings` インターフェース（2.2）が全キーの文言を要求するので、
  キーを足して訳を書き忘れるとコンパイルエラーになる
- 既存の任意フィールド `kind?: 'incident'` は変えず、移行でもそのまま引き継ぐ
- `params` の値はプリミティブのみ。ID を入れる場合も文字列（プレーンデータの原則そのまま）
- UI 側の言語状態は `gameStore` とは別の小さなストアに置く（シミュレーションの購読と混ぜない）
- `schemaVersion` は**実装した時点の値に1を足す**（フェーズ5 8 章の規約。現在値は
  `src/persistence/saveFile.ts` を見ること）。移行は `log` の各エントリを `legacy` に包む1段だけ

## 5. フォントと CSS

調査の結果、**日本語グリフの表示に構造的な障害は無い**。テキストはすべて DOM で描画され、
PixiJS 側にテキストは1文字も無い（`Text` / `BitmapText` 未使用、`fillText` 0件）。
対応が要るのは以下だけ。

| 箇所 | 現状 | 対応 |
| --- | --- | --- |
| フォント指定 | `body` の1箇所のみ。`'Inter', 'Segoe UI', system-ui, sans-serif`（`styles.css:29`）。`@font-face` 無し | フォールバックに日本語系（`'Hiragino Sans'`, `'Noto Sans JP'`, `'Yu Gothic UI'`）を挟む。**フォントは同梱しない**（下記） |
| `text-transform: uppercase` | 3箇所（パネル見出し2 + `.mana__label`） | 日本語には無効（無害）。放置してよい |
| `text-transform: capitalize` | `.resource__name` | 同上 |
| `letter-spacing: 0.08em` | 見出し | 日本語でも許容範囲。実ビルドで見て判断 |
| 固定幅 | サイドバー 260px / 300px、`.inspect__row dt` 74px | 日本語ラベルは英語より短いことが**多い**が、これは主張であり実ビルドで測る |
| `<html lang="ja">` | 中身は英語なのに `ja` 固定 | 切替に追随させる |

**フォントを同梱しない理由**: 単一 HTML ビルド（`build:single`）に日本語フォントを埋め込むと、
サブセット化した Noto Sans JP でも数百 KB 増える（見積もり）。システムフォントで日本語が
表示できない環境は現実的にほぼ無いので、まず同梱なしで出し、実ビルドで見た目を確認してから判断する。

## 6. 段階と「動いたと言える条件」

本編 10 章と同じく、段階ごとに「動いたと言える条件」を先に決め、テストにしてから実装する。
段階は依存順に A → B → C。**A だけでも出せる**（UI の骨格が日本語になり、ログとアラートは英語のまま残る）。

| 段階 | 内容 | 動いたと言える条件 |
| --- | --- | --- |
| **A** | 辞書機構・言語切替 UI（TopBar のシナリオ選択の隣）・系統①②の静的文言 | 切替でリロードなしに全ラベルが変わる／`en` と `ja` のキーが型で一致する／建物名の定義が1箇所になる／切替が `localStorage` に残り、再訪時に効く |
| **B** | 導出文言（アラート・目標・状態メッセージ・入植者の活動ラベル） | **発生済みの**アラートと目標が切替で即座に翻訳される（導出だから可能なこと）／テストが文章でなくキーを検証している |
| **C** | ログの構造化と移行（`schemaVersion` +1） | 移行前のセーブが読める／旧エントリは原文のまま表示される／新エントリは切替で両言語に出る／リングバッファ100件の性質は変わらない |

### テスト方針

- 既存テストのうち**アラート・目標・ログの英文に依存しているもの**を、キー検証に書き換える。
  これは B・C の作業の一部であって前置きではない（文章依存のテストは翻訳と同時に必ず壊れるため）
- 移行テスト: 既存の移行チェーン（`saveFile.ts`、1段ずつテスト済み）に1段を同じ形で足す
- 1年計測: 導入前後で一致すること。文字列処理は tick に影響しないはずで、「はず」をここで測る
- バンドルサイズ: `build:single` の前後を測って記録する（辞書2言語ぶんの増分を数値で残す）

## 7. リスクと非目標

| リスク | 対策 |
| --- | --- |
| 日本語ラベルが固定幅からあふれる | 実ビルドで全パネルを両言語で目視し、あふれた箇所だけ直す（5 章）。CSS の全面改修はしない |
| テストが英文に依存していて大量に壊れる | キー検証への書き換えを B・C の受け入れ条件に含めた（6 章） |
| 辞書キーの粒度を細かくしすぎて書きにくくなる | 「1画面の1文言 = 1キー」を出発点にし、共有はあとから括る（先回りで抽象化しない） |
| `legacy` エントリが残り続けて見た目が混ざる | リングバッファ100件なので数日で押し出される（3 章）。積極的な変換はしない |

**非目標（この段階では入れない）**:

- **3言語目**。構造（`Record<Language, Strings>`）は許すが、辞書は増やさない
- **ブラウザ言語の凝った自動判定**（2.1 の1行判定だけ）
- **ドキュメント（`docs/`）の翻訳**。もともと日本語である
- **コード・コメント・識別子・キー名の日本語化**。CLAUDE.md の言語方針で変わるのは
  「UI 文言」の1行だけで、コードは英語のまま
- **フォントの同梱**（5 章。実ビルドで見てから判断）
- **canvas 内テキスト描画**（存在しないものを作らない）
