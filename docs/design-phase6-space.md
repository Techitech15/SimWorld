## 1. 位置づけ — なぜマップと画面が同じフェーズなのか

この2つは別々の要望に見えるが、**同じ一つの事実の裏表**である ——
植民地が、最初に与えられた枠に収まらなくなった。

- 地図は 60×60 のまま。MVP 当時の入植者3人・仕事5種・建築6種に対しては十分だったが、
  いまは入植者8人・仕事9種・建築12種・動物6種・牧場・魔力網が同じ盤面に載っている
- 画面も当時のまま。右サイドバーは幅 300px の1列に**11個のパネルを縦積み**していて、
  `overflow-y: auto` で下へ流れている

どちらも「機能が増えたのに、それを置く場所は増えなかった」結果である。そして両者は**互いに影響する** ——
地図が4倍になれば、ミニマップ・アラートからの現場移動・目標パネルの重要性が上がり、
画面上の場所の奪い合いはさらに厳しくなる。片方だけ直すと、もう片方が悪化する。

**このフェーズは、既存のゲーム内容を1つも増やさない。** 増えるのは盤面と、見え方だけである。

## 2. 実測: マップを4倍にすると何が起きるか

`MAP_WIDTH` / `MAP_HEIGHT` を 120 に変えて実際に回した。
**条件**: seed 8101・無操作・3日（9,000 tick）。地形の構成比のみ 20 シードの平均。

| 項目 | 60×60 | 120×120 | 比 |
| --- | --- | --- | --- |
| タイル数 | 3,600 | 14,400 | 4.0× |
| **1 tick あたり** | **0.732 ms** | **2.791 ms** | **3.8×** |
| セーブ（JSON） | 0.48 MB | 1.86 MB | 3.9× |
| ベリーの茂み / 1000タイル | 7.2 | **1.8** | **0.25×** |
| 動物 / 1000タイル | 9.2 | **2.3** | **0.25×** |

地形の構成比（20 シード平均）:

| 地形 | 60×60 | 120×120 |
| --- | --- | --- |
| 草地 | 51.96% | 51.11% |
| 森 | 30.96% | 31.84% |
| 岩 | 15.74% | 15.81% |
| 結晶 | 1.34% | 1.25% |

読み取れることは3つ。

**性能は問題にならない。** 1 tick あたり 2.79 ms は tick 長 200 ms の 1.4% で、
10倍速（毎秒 50 tick）でも 1 コアの約 14% にとどまる（60×60 では約 3.7%）。
コストはタイル数にほぼ線形で、跳ね上がる項は無かった。**この拡張を止める理由は性能ではない。**

**地形は比例して拡大するので、地形生成には手を入れなくてよい。** 草地・森・岩・結晶の比率は
どれも1ポイント以内で一致している。ノイズはタイル座標で引いているため、広い地図は
「同じ世界の、より広い範囲」になる。

**壊れるのは絶対数で置かれたものだけ。** ベリー26株・動物35頭（`initialCount` の合計。うち捕食者2頭は2日目以降に湧くので初日は33頭）はどちらも定数なので、
面積が4倍になると**密度が 1/4 になる**。これは「広い世界」ではなく「同じ植民地が置かれた、
4倍がらんとした世界」で、歩く距離だけが伸びて手に入るものは変わらない。
**トラックAの実質的な作業は、この絶対数を密度に直すことである。**

## 3. トラックA: マップ拡張（60×60 → 120×120）

### 3.1 マップ寸法を `GameState` へ移す（この作業の中心）

`MAP_WIDTH` / `MAP_HEIGHT` はモジュール定数で、**12ファイル・77箇所**から参照されている
（`pathfinding.ts` の座標↔添字変換、`derived.ts` の領域ラベル `Int32Array`、`camera.ts` の
ワールド寸法、`Minimap.tsx` の `ImageData`、`worldgen.ts`、`animals.ts`、`state.ts` ほか）。

定数を 120 に書き換えるだけでは**既存のセーブが壊れる** —— 保存されている 60×60 のタイル集合に対して、
領域ラベルの配列も経路の添字計算も 120 幅で走る。しかも 8 章の「移行できない古いセーブは黙って読まず
拒否する」に照らすと、**拒否するしかない**セーブが全部になる。プレイヤーの植民地を捨てさせる変更は採らない。

したがって寸法は `GameState.width` / `GameState.height` に持たせ、参照元はすべて state から引く。
これは 4 章の「導出できるものは保存しない」に反しない —— **地図の寸法は導出値ではなく、
その世界を定義する事実**である（`worldSeed` や `scenario` と同じ位置づけ）。

移行は `width: 60, height: 60` を補うだけで、
**既存のセーブは 60×60 の世界としてそのまま遊べる**。新しい世界だけが 120×120 で生成される。

`schemaVersion` は**実装した時点の値に1を足す**。ここに具体的な数字を書かないのは、
フェーズ5も同じことを言うからで、未実装の設計案が2つとも特定の番号を主張すると、
先に実装されなかった側が黙って間違う。現在値は `src/persistence/saveFile.ts` を見ること。

これが済むと副産物として、**マップサイズをプレイヤーが選べる**ようになる（3.5）。

### 3.2 絶対数を密度にする

2 章で測ったとおり、面積に比例すべきものが定数で置かれている。棚卸し:

| 定数 | 現在 | 直し方 |
| --- | --- | --- |
| `BERRY_BUSH_COUNT` | 26 | 1000タイルあたり 7.2 株として面積から算出 |
| `SPECIES[*].initialCount` | 計 35 頭 | 同じく密度から算出（種ごとの比は変えない） |
| `WILDLIFE_MIN_SPAWN_DISTANCE` | 18 | 地図の短辺に対する比率へ |
| `PREDATOR_MIN_SPAWN_DISTANCE` | 20 | 同上 |
| インシデントの出現距離（22 / 14 / 3） | 絶対タイル | 同上。ただし「camp の近く」の 3 は意味が距離そのものなので据え置き |
| `arrivalSpot` の探索半径 3〜14 | 絶対タイル | camp の近くを探す規則なので**据え置き**（広い地図でも移住者は camp に来る） |
| `GameState.forestCapacity` | 生成時の森タイル数 | **直さなくてよい**（既に生成結果から導いている） |

`forestCapacity` が既に正しい形になっているのは偶然ではなく、あれは「地図ごとの容量」として
入れたものだからである。**同じ考え方を他にも広げる**、というのがこの節の全部。

**狼の上限だけは注意が要る。** シナリオごとの上限（1 / 2 / 4）は面積ではなく**難易度**の表現なので、
機械的に4倍にすると `Hard frontier` が狼16頭になる。密度で置くか難易度で置くかを種別ごとに決める必要があり、
捕食者は**難易度側**に置く。

### 3.3 性能は据え置きでよい（ただし1箇所だけ見ておく）

2 章のとおり余裕がある。ただし `src/core/jobs/generator.ts` は**毎 tick 全タイルを走査**して
伐採・採掘・撤去の指定を探しており、ここが 3,600 → 14,400 回/tick になる。
測定上は問題が出ていないので**今回は手を入れない**。指定タイルの索引を持つのは、
毎 tick の全走査がもう1つ増えたときに検討する（早すぎる最適化を避ける）。

### 3.4 セーブと配布

セーブは 0.48 MB → 1.86 MB になる。IndexedDB には十分収まるが、
**1日ごとのオートセーブが毎回 1.86 MB を書く**ことになる点は測っておく（`longrun` に追加）。
単一HTMLビルド（`dist/simworld.html`）の大きさは地図に依らないので影響しない。

### 3.5 マップサイズの選択（任意段階）

3.1 で寸法が state に入れば、生成時に選ばせるのは表を1つ足すだけになる。
シナリオ（開始条件3種）と同じ形で、**規則ではなく盤面**を変える選択肢になる。

| 名前 | 寸法 | タイル | 位置づけ |
| --- | --- | --- | --- |
| Vale（狭い谷） | 60×60 | 3,600 | 従来どおり。既存の計測値が生き続ける |
| Frontier（辺境） | 120×120 | 14,400 | 既定 |
| Wilds（大荒野） | 180×180 | 32,400 | 見積もり: 1 tick あたり約 6 ms（線形外挿。**未実測**） |

180×180 は外挿値なので、採るなら実測してから。

## 4. トラックB: 画面の再配置

### 4.1 現状の棚卸し

右サイドバー（幅 300px・`overflow-y: auto`）に **11個のパネルが縦積み**されている
（`src/ui/App.tsx`）。どれも常に開いていて、畳む手段が無い。

| パネル | 見たい頻度 | 常に中身があるか |
| --- | --- | --- |
| Minimap | 常時 | あり |
| AlertPanel | 常時（ただし普段は空） | 危機のときだけ |
| ResourcePanel | 常時（数字を横目で） | あり |
| GoalPanel | ときどき | あり |
| SelectionPanel | 選択したときだけ | タイル選択時のみ |
| ColonistDetail | 選択したときだけ | 入植者選択時のみ |
| AnimalDetail | 選択したときだけ | 動物選択時のみ |
| ColonistPanel | ときどき | あり |
| WorkPriorityTable | まれ（設定するとき） | あり |
| AnimalPanel | ときどき | あり |
| EventLog | ときどき | あり |

**すぐ分かる無駄が1つある。** `ColonistDetail` と `AnimalDetail` は**排他**で、
決して同時には出ない（`gameStore` の `selectColonist` は `selectedAnimalId` を null にし、
`selectAnimal` は逆をする）。それが独立した2つのパネルとして縦に並んでいる。

### 4.2 3つの行き先に振り分ける

**規則**: 「常に見たいが小さい」ものは画面の隅へ、「見たいときだけ」のものはサイドバーで畳む。

| 行き先 | 何を置くか | 理由 |
| --- | --- | --- |
| **左上オーバーレイ** | 資源（アイコン＋数字）、アラート（アイコン＋件数バッジ） | 数字と警告は横目で見るもの。ここが最も視線が通る |
| **右上オーバーレイ** | ミニマップ | 地図の上の地図。位置が固定なら目が覚える |
| **サイドバー（折り畳み）** | 目標・入植者一覧・仕事優先度・動物・ログ | 開いて読むもの |
| **サイドバー（文脈枠・1つ）** | 選択の詳細（タイル／入植者／動物） | 3つを**1枠**に統合する（4.1） |

**オーバーレイは畳めるようにする。** 隅に置いたものが畳めないと、
今度は地図の四隅が永久に使えなくなる。アイコンだけの状態（数字なし）まで縮められるようにする。

**アラートは空のとき消える。** 現在は常に枠があるが、危機が無いときに「危機はありません」と
書かれた箱を出しておく価値は無い。オーバーレイに移すなら**0件のときは何も描かない**。

### 4.3 折り畳みの状態をどこに置くか

**`GameState` には置かない。** UI の設定はゲームの状態ではなく、そこへ入れると
セーブに入り、`schemaVersion` の移行対象になり、他人のセーブを読むとパネルの開閉まで
付いてくることになる。4 章・8 章の原則（`GameState` はそのままセーブになる）を守るなら、
**開閉状態は `localStorage`** に置き、セーブとは無関係にブラウザ側の設定として持つ。

既定値は「初回は全部開いた状態」ではなく、**状態から決める**（目標パネルと同じ考え方）——
入植者が3人以下なら仕事優先度表は畳んでおく、家畜が0頭なら動物パネルは畳んでおく、など。
一度プレイヤーが操作したパネルは、以後その選択を優先する。

### 4.4 選択を範囲にし、詳細をその場に出す

現在の選択は**1マス単位**で、結果は右サイドバーの `SelectionPanel` に出る。
つまり**目は地図の左下を見ているのに、答えは画面の右端に出る**。地図が4倍になれば、
この視線の往復はそのぶん長くなる。

**範囲選択は、機構を作るのではなく除外を外す作業である。** 矩形ドラッグの仕組み
（`dragStart` / `dragCurrent` と矩形ハイライト）は既にあり、伐採・採掘・建築・ゾーンの各ツールが
使っている。`src/render/renderer.ts` の1行が

```ts
if (this.dragStart && this.dragCurrent && tool.kind !== 'select') {
```

と書いていて、**Select ツールだけが明示的に除外されている**。ここを外すのが実装の中心になる。

範囲を選べるようになると、出すべき中身が変わる。1マスなら `describeTile` が行の配列を返して終わりだが、
範囲は**集計**が要る（木12・岩4・アイテム3スタック・入植者2人、のように）。
`describeTile` と同じくフラットな文字列配列を返す純粋関数 `describeArea` を1つ足す
（`useShallow` が効く形を崩さない）。

**ポップアップは選択範囲の近くに出す。** 出す位置は範囲の外側の角で、画面の端に寄ったときは
内側へ反転させる。ポップアップ自身がクリックを吸わないようにし、Esc と選択解除で閉じる。

**これは B-1 の答えを変える。** B-1 は当初「選択詳細の3パネルを1枠に統合する」だったが、
ポップアップが入るなら統合先はサイドバーではない。ただし**全部をポップアップに移すのは誤り**で、
入植者シート（7スキル＋レベル進捗＋特性＋実効速度）はポップアップに収まる分量ではない。分け方は次のとおり:

| 情報 | 行き先 | 理由 |
| --- | --- | --- |
| タイル・範囲の中身（地形・建築・アイテム・動物・指定） | **ポップアップ** | 見た瞬間に分かればよく、読み続けるものではない |
| 入植者シート・動物シート | **サイドバーの文脈枠** | 読む分量がある。ポップアップからワンクリックで開く |

したがって B-1 は「3パネルを1枠へ」から「**軽い情報をポップアップへ移し、残った2つ（入植者・動物）を
1枠に統合する**」に読み替える。5 章の段階表もその形にしてある。

### 4.5 やらないこと（トラックB）

- **パネルの自由配置・ドラッグ＆ドロップ・ドッキング。** 得るものに対して機構が大きすぎる
- **モーダルウィンドウ。** シミュレーションが裏で進むゲームで、画面を塞ぐものは扱いが難しい
- **サイドバーの左右入れ替え、複数タブ列。** まず畳めることの効果を測ってから

## 5. 段階と「動いたと言える条件」

トラックA と トラックB は独立で、並行して進められる。

| 段階 | 内容 | 動いたと言える条件 |
| --- | --- | --- |
| **A-1** | 寸法を `GameState` へ。既定は 60×60 のまま | 既存セーブが読めて遊べる。全テストが通る。**この段階では見た目が何も変わらない** |
| **A-2** | 絶対数を密度へ | 60×60 の密度が現状と一致する（回帰）。120×120 で 1000タイルあたりのベリー・動物が 60×60 と一致する |
| **A-3** | 既定を 120×120 に | 1年（20日）無操作で植民地が生き残る。1 tick あたりが 200 ms 予算の 5% 以内 |
| **A-4**（任意） | マップサイズの選択 | 3種が実際に別の広さで生成され、それぞれセーブ往復できる |
| **B-1** | 範囲選択と、その場に出るポップアップ | Select ツールで矩形を引ける。範囲の中身が**集計されて**選択の近くに出る。画面端で反転する |
| **B-2** | 入植者・動物シートを1枠に統合 | どちらを選んでも同じ枠に出る（store 上で排他なので同時には出ない） |
| **B-3** | サイドバーの折り畳み（`localStorage`） | 畳める・開ける・再読み込みで維持される。**セーブファイルに開閉状態が入らない** |
| **B-4** | 資源とアラートを左上へ、ミニマップを右上へ | 隅で畳める。アラート0件のとき何も描かれない |

### テスト方針

- **A-1**: 60×60 のセーブと 120×120 のセーブを同一プロセスで往復させ、混線しないこと
- **A-2**: 密度の回帰テスト（1000タイルあたりの数を両サイズで比較）
- **A-3**: `longrun.test.ts` を 120×120 で1年。tick 予算・セーブ往復・ジョブ滞留
- **A-3**: `chaos.test.ts` を 120×120 でも回す（不変条件は寸法に依らないはず）
- **B-1**: `describeArea` が範囲内の中身を数え落とさない（1マスの範囲なら `describeTile` と一致する）
- **B-1**: 空の範囲を選んでも「何も無い」と言える（黙って何も出ないのは失敗と区別がつかない）
- **B-2**: 入植者を選んでから動物を選ぶと、枠の中身が入れ替わる（両方出ない）
- **B-3**: 開閉して保存したセーブを読み、**`JSON.stringify(state)` に UI の語が含まれないこと**
- **B-4**: `Minimap.test.ts` は寸法非依存に書き換える（現在 60 を前提にしている箇所がある）

## 6. リスクと非目標

| リスク | 対策 |
| --- | --- |
| 77箇所の定数置換で1箇所だけ直し忘れる | A-1 を「見た目が変わらない」段階として独立させ、全テストを通す。旧サイズのままなら差分は検出可能 |
| 広い地図で植民地が孤立し、何も起きない年が続く | A-2 の密度化がそのまま対策。加えて 120×120 で1年計測し、移住・インシデント・捕食の頻度を 60×60 と比較する |
| オーバーレイが地図を隠す | 畳めること（4.2）と、四隅だけを使うこと |
| 折り畳み状態がセーブに漏れる | B-2 の受け入れ条件で機械的に固定（`JSON.stringify` を検査する） |
| 既存の実測値がすべて無効になる | 既定サイズを変える A-3 で、`design-notes.md` の1年計測を**取り直して追記**する（過去の値は消さない） |

**非目標**:

- **複数マップ・マップ間移動**（design.md 9 章の非実装リストのまま。広い地図はその代わりではなく、別の答え）
- **地形の種類を増やすこと**（2 章のとおり地形は比例して拡大するので、拡張のために新地形は要らない）
- **パネルの自由配置・ドッキング・モーダル**（4.4）
- **ズーム倍率の追加や描画方式の変更**（性能に余裕がある以上、今回の理由にはならない）
- **`GameState` に UI 設定を持たせること**（4.3）

## 実装メモ（提案からの差分）

**この節より上は提案時のまま凍結してある**（CLAUDE.md「ドキュメントの分担」）。
現況の仕様は [design.md](design.md) 11 章、決め手と実測値は [design-notes.md](design-notes.md)。

### 3.1 寸法を state へ — 定数は「改名」した

案は「参照元をすべて state から引く」だけを書いていたが、実装では
`MAP_WIDTH` / `MAP_HEIGHT` を **`DEFAULT_MAP_WIDTH` / `DEFAULT_MAP_HEIGHT` に改名**した。
6 章がリスクに挙げた「77箇所の置換で1箇所だけ直し忘れる」は、名前を残したままでは
**コンパイルが通ってしまう**（古い定数を読み続けるだけ）。改名すれば全箇所が型エラーになる。

`SimContext` にも `width` / `height` を持たせた。案は触れていないが、領域ラベルは寸法で添字を作るので、
**別サイズの state を渡された context は落ちずに静かに間違う**。

### 3.2 密度化 — `perArea` と `perSpan` の2つで足りた

案の棚卸し表どおり。実測で 1000タイルあたりのベリー 7.2 / 霜花 3.9 / 動物 10.6 が
両サイズで一致することを確認した（[design-notes.md](design-notes.md)）。
狼の上限を難易度側に残す判断も案のまま。

**霜花は案の表に無い**（フェーズ5 がこの案より後に実装されたため）。同じ扱いで密度化した。

### 3.3 性能 — 見積もりより高いが、結論は変わらない

案 2 章の見積もりは 0.732 → 2.791 ms。実測は **1.0 → 6.4 ms**。
差の理由は、案を書いた時点よりコードが増えていること（マナ層・襲撃・交易・幻想層はその後）と、
測定がテストランナー内であること。予算 200 ms に対して 3.2% なので A-3 の受け入れ条件は満たすが、
**10倍速では 1 コアの約 32%** になる。案が言った「性能はこの拡張を止める理由ではない」は変わらないが、
余裕は見積もりほど大きくない。案 3.3 の「`runJobGenerator` の全走査は今回触れない」は踏襲した。

### テストの寸法 — 案が書いていなかった判断

案の 5 章は `longrun` と `chaos` を 120×120 で回すと書いていたが、**残りをどうするかを書いていない**。
実装では**ハーネスの既定を 60×60 に固定**した。4倍の実行時間もあるが、決め手は別で ——
[design-notes.md](design-notes.md) の実測値はすべて 60×60 で取ったものなので、
ハーネスが黙って広がると**それらが一行も書き換えられないまま一斉に無効になる**。
「過去の測定を消さない」は、消さないことだけでなく**意味を変えない**ことでもある。

出荷される寸法は `longrun`（1年）・`chaos`（不変条件）・`roundtrip`（2寸法の同一プロセス往復）が受け持つ。

### 4.x 画面 — 案どおり

3つの行き先、選択詳細の1枠化、`localStorage` の折り畳み、状態から決まる既定値。
アラートの「0件のとき何も描かない」は**すでにそうなっていた**（`AlertPanel` は元から `null` を返す）ので、
隅に移した結果として自然に満たされた。

折り畳み状態がセーブに漏れないことは、案 6 章のリスク表どおり
**`JSON.stringify(state)` を検査するテスト**で機械的に固定した。
